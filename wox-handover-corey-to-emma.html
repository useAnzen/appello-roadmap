3 Four conflict points and how I resolved them

These are the four places our two views diverged. For each I've recorded both positions, the resolution, and the WOX doc that captures it. None of these are final — push back tomorrow if any feel wrong.

C1

Dispatch board scope for V1

Emma's view

Kanban (unscheduled WOs left, user columns right, drag-to-assign) + calendar hybrid. Open question: does just adding a "WO vs Job" toggle to the existing scheduler ship V1?

My view

Full Kanban is too much for 1.33. Ship the toggle now (your fallback). Use the breathing room to design 3 industry-leading dispatch concepts (ServiceTitan / Jobber / Map-First) and pick one for 1.34.

Resolution — your toggle wins V1, Kanban deferred to 1.34 with 3 concepts to pick from

V1 = WOX-01 (the toggle, scoped to jobType = WORK_ORDER) + WOX-13 (your noted "filter likely needs fix"). Post-V1 = WOX-16 with all three concept mockups + a comparison table. I'm recommending Concept B (Jobber-style Day-Strip Timeline) for 1.34 — clean for both service and project users.

C2

WO pricing visibility — is there a permission gate in V1?

Emma's view

Defer pricing visibility permissions to post-V1. V1 keeps it simple: "no prices until invoicing."

My view

"No prices in V1" leaves admins blind on the WO they're managing. Use what we already have — job.financialView permission — to gate pricing in V1. No new permission to build. Add a dedicated workOrder.viewPricing later.

Resolution — gate on existing job.financialView for V1, dedicated permission post-V1

V1 = WOX-11 wraps WO pricing columns/totals in <PermissionGate permission="job.financialView">. Zero new permission work; matches how Job pricing already works. Post-V1 = WOX-24 adds the dedicated permission with auto-migration (any role with job.financialView gets workOrder.viewPricing on by default — zero-disruption rollout). This one I'd flag as the most important to confirm — it changes whether techs see $ on V1 WOs.

C3

Pre-fill labor on WO — V1 or post-V1?

Emma's view

Defer. "Templates can describe '4 guys × 2hrs' but timesheets need dates, so this can only materialize on schedule, not on template-load. Defer until dispatch board flow is settled."

My view

The "needs dates" constraint is real but not blocking. Add a LaborLine.kind = PLACEHOLDER | ACTUAL field. Placeholders carry trade level + qty + hours but no userId or workDate. They resolve to actual lines on tech check-in or schedule confirm. Lets templates pre-fill from day one.

Resolution — V1 with the placeholder pattern, captured in WOX-05

WOX-05 spells out the placeholder model + 5 decisions including "what triggers resolution" (rec: scheduled crew check-in OR manual user assignment) and "do placeholder lines flow into estimates before resolution" (rec: yes for estimates, never for actual billing). Honors the user-first time-allocation rule because the placeholder isn't a timesheet — actual LaborLine rows tied to specific users still drive timesheets and payroll. If you're nervous about the complexity, we can defer this back to your post-V1 cut and just allow templates to suggest hours without auto-creating labor lines.

C4

Customer payment gateway — V1 or post-V1?

Emma's view

Post-V1. Helix vs Stripe selection + integration is too much for 1.33.

My view

Agreed on the live feature being post-V1 — but scaffold it now (data models, permission, hidden settings page, feature flag) so 1.34 implementation is purely UI + gateway integration, not data-model migration.

Resolution — V1 ships scaffold-only; live UI + gateway is post-V1

WOX-14 defines the V1 scaffold: PaymentMethod, CustomerPayment, PaymentGatewayConfig models + migrations + a hidden Settings → Payments page behind a feature flag. No live "Pay now" button until 1.34. Recommended provider: Stripe (broadest reach + best Canadian support), but final decision can wait until activation.
