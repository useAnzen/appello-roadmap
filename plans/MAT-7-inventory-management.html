Overview & Outcome

Inventory tracks what stock is on hand and where, and records every change as an append-only movement ledger. The model is deliberately shaped to mirror Shopify’s inventory objects so the future PR #7394 integration is a near-direct field map. After this lands:

  • Three new tables — InventoryLocation (a stockable place → a required Location address + a PropertyValue type), InventoryLevel (the per-location balance of one polymorphic thing; Shopify’s InventoryLevel), and InventoryMovement (the change ledger). All three extend BaseModel.
  • Stock is tracked per (inventoryLocation, thing): 2000 brackets at A + 1000 at B + 2000 at C = three InventoryLevel rows; company total is their sum.
  • Three custom mutations — checkoutToJob, transferBetweenLocations, adjustInventory — each write a movement through the model layer and apply the balance delta to the affected InventoryLevel(s). Receiving (MAT-6) auto-creates a Receive movement.
  • InventoryLevel exposes computed quantityAvailable (on-hand − open MAT-4 reservations), status (OK / LOW / OVER from min/max), and a polymorphic Material/Equipment resolver.
  • Notes on locations and movements use the existing Note + NoteReferences system (threaded comments + assets), so the three models are seeded into ReferenceModel.
  • Inventory is gated by a dedicated inventory permission behind the RESTRICT_MATERIAL env gate.
Decisions baked into this plan (settled with the user this session — see the spec’s reconciliation callout).
  • Shopify-aligned shape. Material/Equipment = Shopify InventoryItem (the thing); InventoryLocation = Shopify Location; InventoryLevel = Shopify InventoryLevel (per-location quantities).
  • The per-location row is InventoryLevel, not “InventoryItem” (which would collide with Shopify’s meaning = our Material/Equipment).
  • Polymorphic InventoryLevel (referenceModel+referenceId, FK→ReferenceModel.model): Material wired now, Equipment shape-ready (anticipates the bulk-equipment requirement, PR #7427).
  • Movements reference the two locations (fromInventoryLocationId/toInventoryLocationId), not the level rows; the engine resolves and updates the matching InventoryLevel balances.
  • InventoryLocation.locationId → Location is REQUIRED (stock is always stored somewhere; even a van has a home base).
  • typeId is a plain-category PropertyValue (the jobType/companyType precedent) — NO Instance anchors (unlike a workflow status).
  • quantityOnHand is stored (running balance kept in sync by movement writes; ledger = source of truth); quantityAvailable is computed = on-hand − open MAT-4 reservations.
  • v1 quantity states = on_hand + available only. Shopify’s other 6 states (committed/reserved/damaged/…) deferred.
  • sourceDocumentModel/sourceDocumentId (Shopify referenceDocumentUri) is OUT of v1 — add later if the receipt→movement drill-back or Shopify needs it.
  • No instanceId (single-instance app). No MAT-x identifiers in migration names or code comments.

InventoryLevel — the per-location balance (Shopify’s InventoryLevel). One row per (inventoryLocation, thing) enforced by the @@unique; this is HOW per-location stock is tracked (2000@A / 1000@B / 2000@C = three rows, total = their sum). Polymorphic referenceModel+referenceId = the stocked thing (Material now, Equipment later). quantityOnHand is the stored running balance the ledger keeps in sync; quantityAvailable is computed at query time (Step 8).

  isDeleted          Boolean   @default(false)

  inventoryLocationId String   @db.VarChar(21)

InventoryMovement — append-only ledger line: “move quantity of thing from A to B.” References the two locations directly + the thing. Receive = to only; Checkout = from only; Transfer = both (from ≠ to); Adjustment = one side. Both location columns are nullable (every type nulls at least one side); per-type requiredness, “at least one set,” and quantity > 0 (direction = which side is populated, not a signed number) are enforced at the model layer (Step 6), not as DB constraints.

class InventoryLevelModel extends BaseModel<IInventoryLevel> {
    public name = "InventoryLevel";
    name_plural = "InventoryLevels";
    protected prisma = prisma.inventoryLevel;

    protected modelFields: IField<IInventoryLevel>[] = [
        { name: "inventoryLocationId", type: "string", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "referenceModel", type: "string", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "referenceId", type: "string", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "quantityOnHand", type: "float", options: { canCreate: true, canEdit: true } },
        { name: "minQuantity", type: "float", options: { canCreate: true, canEdit: true } },
        { name: "maxQuantity", type: "float", options: { canCreate: true, canEdit: true } },
        { name: "unitCost", type: "float", options: { canCreate: true, canEdit: true } }
    ];

    // find-or-create the balance row for (location, thing); returns it
    public async upsertLevel(
        inventoryLocationId: string, referenceModel: string, referenceId: string, userId: string
    ): Promise<IInventoryLevel> {
        const existing = await prisma.inventoryLevel.findFirst({
            where: { inventoryLocationId, referenceModel, referenceId, isDeleted: false }
        });
        if (existing) return existing as IInventoryLevel;
        return this.createItem(
            { inventoryLocationId, referenceModel, referenceId, quantityOnHand: 0 }, userId
        );
    }

    // apply a signed delta to the stored balance through the model (perm checks + audit)
    public async applyDelta(levelId: string, delta: number, userId: string): Promise<void> {
        const level = await prisma.inventoryLevel.findFirstOrThrow({ where: { id: levelId } });
        await this.editItem(levelId, { quantityOnHand: Number(level.quantityOnHand) + delta }, userId);
    }
}

export { InventoryLevelModel };
Stored balance, model-method writes. quantityOnHand is the fast read; the InventoryMovement ledger is the audit source of truth. applyDelta goes through editItem (never raw prisma.update) so it runs perm checks + audit. quantityAvailable, status, deficit are not here — they are computed in the resolver (Step 8).

Goal

new apps/api/src/models/InventoryMovement.ts

One private recordMovement does the work; the three public verbs set type + which side(s) are populated. quantity is always positive; direction is encoded by which side is set.

class InventoryMovementModel extends BaseModel<IInventoryMovement> {
    public name = "InventoryMovement";
    name_plural = "InventoryMovements";
    protected prisma = prisma.inventoryMovement;

    protected modelFields: IField<IInventoryMovement>[] = [
        { name: "type", type: "string", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "referenceModel", type: "string", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "referenceId", type: "string", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "quantity", type: "float", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "fromInventoryLocationId", type: "string", options: { canCreate: true } },
        { name: "toInventoryLocationId", type: "string", options: { canCreate: true } },
        { name: "jobId", type: "string", options: { canCreate: true } },
        { name: "costCodeId", type: "string", options: { canCreate: true } },
        { name: "performedByUserId", type: "string", options: { isRequiredOnCreate: true, canCreate: true } }
    ];

    public async recordMovement(
        input: {
            type: InventoryMovementType;
            referenceModel: string; referenceId: string; quantity: number;
            fromInventoryLocationId?: string | null; toInventoryLocationId?: string | null;
            jobId?: string | null; costCodeId?: string | null; note?: string | null;
        },
        userId: string
    ): Promise<IInventoryMovement> {
        const { type, referenceModel, referenceId, quantity, note } = input;
        const from = input.fromInventoryLocationId ?? null;
        const to = input.toInventoryLocationId ?? null;

        // ---- per-type invariant (model-layer; from/to are nullable in the DB) ----
        if (!(quantity > 0)) throw new ValidationError("Quantity must be positive");
        if (!from && !to) throw new ValidationError("Movement must set a from and/or to location");
        if (type === "Receive" && (from || !to)) throw new ValidationError("Receive sets only a destination");
        if (type === "Checkout" && (!from || to)) throw new ValidationError("Checkout sets only a source");
        if (type === "Transfer" && (!from || !to)) throw new ValidationError("Transfer needs both locations");
        if (type === "Transfer" && from === to) throw new ValidationError("Transfer source and destination must differ");

        const levels = new InventoryLevelModel();

        // ---- stock check on the source ----
        if (from) {
            const src = await levels.upsertLevel(from, referenceModel, referenceId, userId);
            if (Number(src.quantityOnHand) < quantity) {
                throw new ValidationError(`Insufficient stock: ${src.quantityOnHand} on hand, ${quantity} requested`);
            }
        }

        // ---- write the movement, then apply deltas (model methods, sequential, not atomic) ----
        const movement = await this.createItem(
            { type, referenceModel, referenceId, quantity,
              fromInventoryLocationId: from, toInventoryLocationId: to,
              jobId: input.jobId ?? null, costCodeId: input.costCodeId ?? null,
              performedByUserId: userId },
            userId
        );

        if (from) {
            const src = await levels.upsertLevel(from, referenceModel, referenceId, userId);
            await levels.applyDelta(src.id, -quantity, userId);
        }
        if (to) {
            const dst = await levels.upsertLevel(to, referenceModel, referenceId, userId);
            await levels.applyDelta(dst.id, +quantity, userId);
        }

        if (note) {
            await new NoteModel().createItem(
                { title: `${type} note`, body: note, isDraft: false,
                  noteReferenceData: { referenceModel: "InventoryMovement", referenceId: movement.id } },
                userId
            );
        }
        return movement;
    }

    public checkout(i: ICheckoutInput, userId: string) {
        return this.recordMovement(
            { type: "Checkout", referenceModel: i.referenceModel, referenceId: i.referenceId,
              quantity: i.quantity, fromInventoryLocationId: i.inventoryLocationId,
              jobId: i.jobId, costCodeId: i.costCodeId, note: i.note }, userId);
    }
    public transfer(i: ITransferInput, userId: string) {
        return this.recordMovement(
            { type: "Transfer", referenceModel: i.referenceModel, referenceId: i.referenceId,
              quantity: i.quantity, fromInventoryLocationId: i.fromInventoryLocationId,
              toInventoryLocationId: i.toInventoryLocationId, note: i.note }, userId);
    }
    public adjust(i: IAdjustmentInput, userId: string) {
        // positive delta -> increase (to); negative -> decrease (from); quantity stored positive
        const increase = i.quantity >= 0;
        return this.recordMovement(
            { type: "Adjustment", referenceModel: i.referenceModel, referenceId: i.referenceId,
              quantity: Math.abs(i.quantity),
              toInventoryLocationId: increase ? i.inventoryLocationId : null,
              fromInventoryLocationId: increase ? null : i.inventoryLocationId,
              note: i.note }, userId);
    }
}

export { InventoryMovementModel };
Model methods, not raw prisma — and sequential, not atomic. The movement and both balance edits go through createItem/editItem. BaseModel can’t enlist in a prisma.$transaction, so a mid-sequence failure can leave the ledger and the stored balance briefly out of step — the same trade-off MAT-6 accepts. Mitigations: validate & do the stock check before writing; write the movement first (it’s the source of truth) so a failed delta is recoverable; the InventoryLevelReconciliation view (Step 10) surfaces drift. Do not drop to raw tx to force atomicity.
Adjustment sign convention. The mutation input carries a signed delta for UX (e.g. −15); the model stores quantity positive and routes it to from (decrease) or to (increase). Confirm the frontend sends a signed delta (not a target count); if product wants “enter the new count,” compute delta = newCount − quantityOnHand in the resolver before calling adjust.

8a — polymorphic Material/Equipment (on InventoryLevel and InventoryMovement)

Material: async ({ referenceModel, referenceId }) =>
    referenceModel === "Material"
        ? prisma.material.findFirst({ where: { id: referenceId, isDeleted: false } })
        : null,
Equipment: async ({ referenceModel, referenceId }) =>
    referenceModel === "Equipment"
        ? prisma.equipment.findFirst({ where: { id: referenceId, isDeleted: false } })
        : null,

8b — computed quantityAvailable / status / deficit (on InventoryLevel)

quantityAvailable: async (lvl) => {
    // available = on-hand − open reservations against this level.
    // MAT-4 reservation link not built yet -> reserved = 0 -> available === on-hand.
    const reserved = 0; // TODO(MAT-4): sum open MaterialOrderLineItem reservations for (location, thing)
    return Number(lvl.quantityOnHand) - reserved;
},
status: (lvl) => {
    const oh = Number(lvl.quantityOnHand);
    if (lvl.minQuantity != null && oh < Number(lvl.minQuantity)) return "LOW";
    if (lvl.maxQuantity != null && oh > Number(lvl.maxQuantity)) return "OVER";
    return "OK";
},
deficit: (lvl) => {
    if (lvl.minQuantity == null) return null;
    const d = Number(lvl.minQuantity) - Number(lvl.quantityOnHand);
    return d > 0 ? d : null;
},

Queries: inventoryLevels(inventoryLocationId), lowStockLevels (quantityOnHand < minQuantity via a filtered read), inventoryMovements(inventoryLocationId, referenceId). Mutations checkoutToJob/transferBetweenLocations/adjustInventory call the Step 6 verbs after the permission check; createInventoryLocation/update/delete and upsertInventoryLevel call the Step 4/5 models. InventoryLocation.InventoryLevels/Notes and InventoryMovement.FromLocation/ToLocation/PerformedBy/Notes are straightforward FK/NoteReferences resolvers (Notes: prisma.noteReferences.findMany({ where: { referenceModel, referenceId } }) → notes).

Step 9 — MAT-6 seam: receiving creates a Receive movement

Goal
When a PO is received, add stock to the right InventoryLocation.
Files
MOD apps/api/src/models/PurchaseOrderReceipt.ts (MAT-6’s receiveAgainstPO) or its line afterCreate

After each ReceiptLineItem is written (good qty = receivedQty − damagedQty), call:

await new InventoryMovementModel().recordMovement(
    { type: "Receive", referenceModel: "Material", referenceId: materialId,
      quantity: goodQty, toInventoryLocationId: destInventoryLocationId }, userId);
Two mappings to resolve (flag for the user / MAT-6 author):
  • Which InventoryLocation? The PO has deliveryLocationId → Location (MAT-5). Resolve the InventoryLocation whose locationId = po.deliveryLocationId. If none exists, either (a) skip inventory creation and warn, or (b) require an inventory location to be configured for that delivery Location. Recommendation: (a) skip + warn in v1 (receiving must not hard-fail because inventory isn’t set up), and surface a “link this delivery location to inventory” affordance later.
  • Which referenceId? The PO line carries materialAttributePriceId (a MAT-0 source/price row), not a Material id. Resolve the owning Material from the MaterialAttributePrice and use that as referenceId (referenceModel = "Material"). Confirm the MAP→Material path on the live schema.
Keep this seam one-directional and best-effort: a failure to mirror into inventory should be logged, not roll back the receipt.

Step 12 — Job costing: checkout → material actuals

Goal
A Checkout with jobId+costCodeId contributes to that job’s material actuals.
Files
MOD apps/api/src/…/JobFinancialSummaryService.ts
Touch carefully — this is the one cross-cutting financial edit. Per MAT-6 grounding, JobFinancialSummaryService derives material actuals from expense line items and has no inventory concept. Adding inventory checkouts as a material-actual source means summing Checkout movements (cost = quantity × InventoryLevel.unitCost at the source) per jobId/costCodeId. Confirm this doesn’t double-count if a checked-out material is also later logged as WO material consumption (MAT-2a). If the reconciliation is non-trivial, split this into a small follow-up and ship Steps 1–11 first — inventory mechanics don’t depend on it.

Step 13 — No new-instance bootstrap needed

Unlike MAT-6 (which added Instance anchor columns needing a per-instance bootstrap), MAT-7’s location-type PropertyValues are global rows and there are no Instance anchors. The Step 2 migration (INSERT IGNORE) seeds them once for all data. New instances inherit them; nothing to bootstrap. State this explicitly in the PR so a reviewer doesn’t expect an anchor-seeding step.

Step 14 — End-to-end smoke test

  1. Create two InventoryLocations (each linked to a Location, typed Warehouse/Trailer).
  2. upsertInventoryLevel for a Material at Warehouse A with min/max; confirm status/quantityAvailable resolve.
  3. Receive a MAT-6 PO into A → a Receive movement appears, A’s quantityOnHand increases.
  4. checkoutToJob 25 from A (with job + cost code) → balance drops, movement has from=A / to=null / job set; rejects if qty > on-hand.
  5. transferBetweenLocations A→B → one movement, A down + B up; rejects from === to.
  6. adjustInventory −15 at A with a note → from=A, positive quantity, a Note attached via NoteReferences.
  7. lowStockLevels returns the level once below min; InventoryLevelReconciliation shows zero drift.
  8. Permission: a user without inventory is rejected on every query/mutation.

Downstream impacts (for awareness, NOT this PR)

  • MAT-8 (Vendor Credits): a return creates an inbound Return movement (to = the location stock comes back to).
  • Bulk equipment (PR #7427): when Equipment gains a quantity-tracked mode, stock it via InventoryLevel(referenceModel = "Equipment") — no MAT-7 schema change needed.
  • Shopify (PR #7394): map InventoryLevel→InventoryLevel, InventoryLocation→Location, Material/Equipment→InventoryItem; add sourceDocument* (= referenceDocumentUri) and the remaining quantity states when the integration lands.
  • MAT-4 reservations: wiring open material requests to reserve stock turns the quantityAvailable reserved = 0 TODO (Step 8b) into a real subtraction.
