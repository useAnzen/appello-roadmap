External Documents · SharePoint Phase 1 (Paste-Link MVP)

An "External documents" widget on Job, Project, and WO detail pages. Users paste a URL (typically a SharePoint / OneDrive / Google Drive link), label it, and click to open in a new tab. No iframe, no OAuth — just stored strings + provenance metadata. Phase 2 (in-app iframe) is post-V1. Solves "where's the latest scope doc?" with ~2 days of work. Path B build of WOX-15.

Estimate: 1.5-2 days Sequence: 1.33, independent Requires: WO-3 / WO-4 (host) Enables: Future WOX-17 SharePoint iframe

1. Business Case

Customers like Mak Surveying and Owens Insulation operate in SharePoint. The latest scope doc, the field-survey PDF, the customer's spec sheet — all live in SharePoint folders, and the workflow today is "DM the link in chat or email." That works until someone joins the WO mid-week and can't find it.

Phase 1 ships the smallest possible solution: an "External documents" widget on the entity detail pages where anyone with edit access can paste a URL with a label. Click → opens in a new tab in the user's signed-in browser session (which already has SharePoint / OneDrive / Drive auth, so no integration required). The platform does not dereference the URL, does not preview it, does not embed it.

Phase 2 (WOX-17) is in-app iframe via Microsoft Graph OAuth — meaningfully bigger; deferred. The model in this spec is provider-agnostic so Phase 2 extends rather than replaces.

Security invariant: the platform stores URL strings as user-pasted text. We never server-fetch a stored URL — that's an SSRF vector. Favicon / preview is client-side only. This rule is encoded in the resolver tests and shouldn't be relaxed casually.
Distinct from the file/folder system. Appello already has a file/folder system (Asset + Folder + AssetReference) for uploaded assets that Appello hosts. External documents are intentionally not part of that system — they're a flat list of pasted URLs at the entity level (Job / Project / WO). Different concerns, different lifecycles. A future phase that brings the two together (e.g., "treat a SharePoint link as a synthetic asset") would be a separate spec.

2. Scope

Already Built

  • DONE Job detail page (/jobs/[id]) — host for the widget on the project-job side
  • DONE Project detail page (/projects/[id])
  • DONE WO detail page (WO-3 / WO-4) — host for the widget on WOs (WO is a Job, so the widget reuses the Job-side mount point)
  • DONE Audit log infrastructure (existing) — used to record add / remove events
  • DONE Polymorphic-reference patterns in the schema (e.g., AssetReference, MaintenanceThreshold) as precedent

In Scope (WO-20)

  • IN New ExternalDocument Prisma model with polymorphic referenceModel + referenceId (values: Job, Project) — WOs are Jobs so they use Job
  • IN Server-side URL format validation (RFC-3986). Reject malformed URLs in the resolver
  • IN Server-side sourceDomain derivation at write time (parse the URL host) — used for the source badge in the UI
  • IN Widget on Job detail page (renders for both Project Job and Work Order classifications), Project detail page, and the mobile Job/WO detail page
  • IN Add / edit / remove flows. Adding requires URL + label; editing changes URL or label; removing soft-deletes
  • IN Permission model: anyone with edit access on the parent entity (same gate as adding a comment) can add / edit / remove
  • IN Audit log entries for add / edit / remove (uses existing audit infrastructure; no new schema)
  • IN Client-side source-domain badge: SP (SharePoint) / OneDrive / Drive / Dropbox / "?" fallback. Pure presentation — derived from sourceDomain

Out of Scope

  • OUT Integration with the existing file/folder system. External documents are a top-level flat list on the entity (Job / Project / WO) — they do not live inside Folder rows, do not appear in the Files tab, do not interact with Asset / AssetReference models. Different lifecycle (pasted URLs vs uploaded assets), different ownership (external host vs Appello), different auth model. Keeping them separate avoids "is this folder mine to delete or just a link?" ambiguity.
  • OUT Server-fetching the URL for any reason (SSRF prevention) — favicon / preview is client-side only
  • OUT In-app iframe / embed of the document — that's WOX-17 (Phase 2)
  • OUT OAuth integration with Microsoft Graph / Google Drive / Dropbox — Phase 2
  • OUT Document permission propagation (Appello can't enforce SharePoint ACLs; the linked URL's auth is the source's responsibility)
  • OUT Granular per-document permissions (anyone with parent-entity edit can manage; finer-grained is over-engineering for V1)
  • OUT Lock / immutable mode for compliance — flag for future if a customer asks; audit log covers most needs
  • FUTURE Phase 2 (WOX-17): iframe viewer, OAuth, in-app preview / edit

4. Data Model

4.1 New model: ExternalDocument

model ExternalDocument {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  // Polymorphic parent — values are Appello model names. V1 supports
  // "Job" (covers Project Jobs + WOs since WO is a Job classification)
  // and "Project". Validated at write time against a fixed allowlist.
  referenceModel String @db.VarChar(50)
  referenceId   String @db.VarChar(21)

  url    String  @db.VarChar(2000)            // RFC-3986 validated at write
  label  String  @db.VarChar(200)

  // Cached at write time from URL parse — drives the source badge in the
  // UI without needing to re-parse on every render. Lowercased.
  sourceDomain String? @db.VarChar(255)

  addedByUserId String? @db.VarChar(21)
  AddedByUser   User?   @relation("ExternalDocumentsAdded",
                                    fields: [addedByUserId],
                                    references: [id],
                                    onDelete: SetNull)

  @@index([referenceModel, referenceId, isDeleted, isArchived],
          map: "ExternalDocument_reference_idx")
  @@index([addedByUserId], map: "ExternalDocument_addedBy_idx")
}

4.2 Inverse on User (existing model)

// Added to existing User model:
ExternalDocumentsAdded ExternalDocument[] @relation("ExternalDocumentsAdded")

4.3 Migration

CREATE TABLE `ExternalDocument` (
    `id`               VARCHAR(21)   NOT NULL,
    `isDeleted`        BOOLEAN       NOT NULL DEFAULT FALSE,
    `isArchived`       BOOLEAN       NOT NULL DEFAULT FALSE,
    `createdAt`        DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    `updatedAt`        DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    `referenceModel` VARCHAR(50)   NOT NULL,
    `referenceId`   VARCHAR(21)   NOT NULL,
    `url`              VARCHAR(2000) NOT NULL,
    `label`            VARCHAR(200)  NOT NULL,
    `sourceDomain`     VARCHAR(255)  NULL,
    `addedByUserId`    VARCHAR(21)   NULL,
    PRIMARY KEY (`id`),
    INDEX `ExternalDocument_reference_idx` (`referenceModel`, `referenceId`, `isDeleted`, `isArchived`),
    INDEX `ExternalDocument_addedBy_idx` (`addedByUserId`),
    CONSTRAINT `ExternalDocument_addedBy_fkey`
        FOREIGN KEY (`addedByUserId`) REFERENCES `User`(`id`) ON DELETE SET NULL
);
Why polymorphic instead of two tables (or three FKs): the same widget shows on Job, Project, and (via WO-as-Job) WO detail pages. Polymorphic keeps the widget code path uniform and matches existing Appello patterns (AssetReference, MaintenanceThreshold). The allowlist validation in the resolver prevents arbitrary referenceModel values.

  referenceId: String!,

  id: String!,
  url: String,                  # re-validated if provided
  label: String

5.3 Permissions

All mutations check that the calling user has edit access on the parent entity (same gate as adding a comment to that entity). Read access on the parent entity grants list access.

7. Acceptance Criteria

  1. The External Documents widget renders on the Job detail page (desktop) for Project Jobs and Work Orders, and on the Project detail page.
  2. A user with edit access on the parent entity can add a document with URL + label; resolver rejects malformed URLs (RFC-3986 violation).
  3. The server derives sourceDomain from the URL host at write time and stores it lowercased; UI uses it to render the source-domain badge.
  4. The server never fetches the stored URL — favicon / preview is client-side only. This is asserted by a unit test on the resolver.
  5. Click on a row opens the URL in a new browser tab; tap on mobile opens in the device's default browser.
  6. A user with edit access can edit a document's URL or label; URL changes re-validate.
  7. A user with edit access can remove a document; removal is a soft-delete (isArchived = true) and is logged in the audit log.
  8. Users without edit access on the parent entity see the document list but cannot add / edit / remove (UI controls hidden, API calls rejected).
  9. Mobile renders a compact version of the same data; long-press paste from clipboard is supported in the URL field.
  10. The referenceModel field accepts only the allowlisted values "Job" and "Project"; arbitrary values are rejected.
