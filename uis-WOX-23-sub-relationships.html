Job/WO Sub-Relationships (Project → Job → WO → Task)

Today the entity hierarchy is shallow: Project → Job. With WOs added, we need to formalize the full hierarchy (Project → Job → WO → Task) and let users drill down/roll up at every level. Resolves Emma's gap about "what is a Task vs a WO and how do they nest".

Status: Concept · Deferred Effort: Architectural · post-1.34 Extends: WO-1 · uis-15A Master ref: #39

1. Where this lives in the app

Pages affected: apps/frontend/src/pages/projects/[id]/index.tsx, apps/frontend/src/pages/jobs/[id]/index.tsx, WO detail (path TBD — built in V1 per WO-3)
Components touched: apps/frontend/src/components/DetailsPage/ProjectDetailPage/index.tsx, apps/frontend/src/components/DetailsPage/JobDetailsPage/index.tsx, financial overview tabs (existing rollup queries)
New components: <EntityBreadcrumb />, <ChildrenPanel />, <EntityRollupTab />, <TaskList />
API surface: Prisma — new Task model with workOrderId FK; updates to Job/WorkOrder for parent FKs; materialized view for rollups (per uis-15A pattern); new tasks, workOrders list resolvers using BaseModel

This is an architectural spec, not a single-page UI feature. It touches every detail page (Project, Job, WO) and the rollup/financial views. The core change is formalizing a 4-level hierarchy and giving every level (a) a parent breadcrumb, (b) a children panel, and (c) a financial/labor rollup.

Backend: introduce a real Task model that's a sub-entity of WO (separate from WorkOrderChecklistItem — checklists are intra-WO ticks, tasks are real entities with assignees, dates, billable line items, status). Existing Project→Job nesting stays unchanged for back-compat.

3. Key decisions for Emma + Corey to discuss

D1 Separate Task model or reuse WorkOrderChecklistItem?
Recommended: Separate Task model. Checklists are intra-WO ticks (item + done flag); tasks are full sub-entities with assignees, due dates, billable line items, status transitions. Conflating them caps WO ambition forever.
D2 Max nesting depth?
Recommended: 4 — Project / Job / WO / Task. Deeper nesting confuses the rollup math and the breadcrumb UI. If Emma later needs sub-tasks, model them as a flat list inside Task (not a 5th level). Hard cap at the schema level.
D3 Rollup performance strategy?
Recommended: Materialized view per the uis-15A equipment-job-pl pattern. Refresh on write triggers (Project/Job/WO/Task save). Avoids real-time recursive queries; keeps Project detail load <200ms even on 100+ child entities.
D4 Mobile parity?
Recommended: Yes — every level surfaces breadcrumb-up and children-down. Mobile uses swipe gestures (swipe up = parent, tap child). Critical for field techs jumping between Project → WO → Task without losing context.
D5 Migration from current data?
Recommended: Existing Project→Job data stays unchanged. WO and Task are net-new tables — no backfill needed. Add a one-time admin tool that lets customers convert legacy "task-shaped" custom fields into real Tasks, but that's opt-in.
