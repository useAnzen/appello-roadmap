Work Order Templates · Schema & Load Engine

Foundation spec for the Work Order Templates feature. Defines the seven new Prisma models that capture template content (name, fields, forms, checklist, materials, labor plans, equipment plans), the audit FK on Job, and the previewWorkOrderTemplate resolver that returns a snapshot package consumed by the create flow. No UI in this spec — settings UI lives in WO-15b, apply UI lives in WO-15c.

1. Business Case

Service contractors run the same kinds of work orders week after week — annual inspection, generator service, boiler PM, leak diagnosis, refrigerant recharge. Today every WO is built from scratch: the dispatcher types the description, attaches the right forms, builds the checklist, lists the expected materials, and notes the trade levels and equipment categories needed. That work is repetitive, error-prone (a missed form is a compliance gap), and consumes the office staff's morning.

Work Order Templates capture this institutional knowledge once. An admin defines "HVAC Annual Inspection" once — the standard 12-step checklist, the inspection form, the consumables, the planned trade levels and equipment categories — and from then on, dispatchers create that WO with one click that snapshots the template's content into the new WO. The dispatcher edits anything that's job-specific (customer, address, notes) and saves. Field workflow follows.

This spec is the data foundation only — the seven new Prisma models, the load preview resolver, the audit FK on Job, and the snapshot semantics. The Settings UI for editing templates is WO-15b; the apply UI on the WO create form is WO-15c. The reverse "save WO as template" flow is post-1.33 (matches Corey's WOX-21).

2. Scope

Maps WOX-05 (Placeholder Labor Lines): Corey's WOX-05 proposed a "pre-fill labor on a WO before assigning users" pattern (e.g., "2 × Journeyman × 4hrs") that resolves to actual labor on schedule/check-in. WorkOrderTemplateLaborPlan in this spec is exactly that mechanism, scoped to template-driven pre-fill: structured plans (with tradeLevelId) display as advisory; actual labor records are still created via the normal scheduling flow once dated. WOX-05 is satisfied by this spec — no separate Path B build needed.

  • IN Job.appliedWorkOrderTemplateId — optional audit FK set at WO creation when a template was applied; never changes after creation

  • IN previewWorkOrderTemplate(templateId) query that returns the full template snapshot package (used by WO-15c at apply time)
  • IN Extension of createJob input to accept a workOrderTemplateApplication payload that creates child records (forms, checklist, materials) atomically with the new Job
  • IN Atomic side-effect: when createJob applies a template, also bumps WorkOrderTemplate.lastUsedAt in the same transaction
  • IN Server-side sanitization of rich field default values (reuse WO-14 sanitization config)
  • IN Permission gate: template CRUD checks InstanceSetting___edit; previewing/applying checks workOrder.create (or equivalent on Job)

Out of Scope

  • OUT Settings UI for editing templates — WO-15b
  • OUT Apply UI on the WO create form — WO-15c
  • OUT Schedule tab + Equipment Assignment surface on WO detail page — WO-16 (sibling, parallel to WO-13's forms surface — covers both the post-save scheduling UI and the EquipmentAssignment management surface in one spec)
  • OUT "Save this WO as a template" reverse flow — post-1.33 (matches WOX-21)
  • OUT Per-customer default template — dropped (workflow is "open form → load template", customer is selected later)
  • OUT Apply on edit (only on create); applying twice on the same WO; live-link semantics — snapshot only, one apply per WO
  • OUT Pre-creation of TimeSheetRecord / EquipmentTimeEntry rows from labor / equipment plans — date-tied, never templated
  • OUT Pre-creation of EquipmentAssignment rows — the equipment plan is category-level advisory; specific equipment selection happens during apply (WO-15c) and creates EquipmentAssignment rows on save, not at template-load
  • OUT Template versioning / change history — snapshot semantics make this unnecessary for V1
  • FUTURE AI / MCP-driven template generation (matches WOX-22)

Pending Business Decisions

1. What happens to applied WOs when a template is archived?

Lean: Job.appliedWorkOrderTemplateId uses SetNull on archive, so historical WOs lose the audit pointer but keep all their snapshotted content (the WO is intact). Alternative: keep the FK but archive cascades nothing on the Job. Confirm.

2. What happens when a template references a Material / TradeLevel / EquipmentCategory that's later archived?

Lean: SetNull on the template's child row's FK to the upstream model. Apply UI surfaces the broken row with an inline warning ("Material no longer available — pick a replacement or remove this row"). Alternative: Restrict upstream archive when in use. Confirm.

3. Default value resolution at form-render time

Lean (per prior conversation): instance value > template value (if template applied) > DAA defaultValue. Confirmed — this spec implements the "template tier" that supersedes DAA defaults at form-render time, not as a stored hierarchy.

3. UI Concepts

No UI in this spec. WO-15a is pure backend foundation — schema, mutations, the load preview resolver. Settings UI for editing templates is WO-15b; the apply UI on the WO create form (template picker, "select specific equipment for each plan", overridable field defaults) is WO-15c.

4. Data Model

4.1 New models — overview

WorkOrderTemplate — top-level: name, description, estimatedDuration, isActive, lastUsedAt. Untyped — any template can be applied to any WO regardless of jobType.
WorkOrderTemplateChecklistItem — mirror of WorkOrderChecklistItem: label, sanitized HTML description, orderNo, photoRequired
WorkOrderTemplateMaterialItem — mirror of WorkOrderMaterialItem: materialId (generic Material — variant + price selected at runtime), quantity, description, orderNo. Description-only rows are permitted (no FK).
WorkOrderTemplateLaborPlan — tradeLevelId (nullable), qtyOfWorkers, plannedSeconds, description (optional), orderNo. With FK = advisory display; without FK + with description = creates a free-form WorkOrderLaborItem on apply. Never creates TimeSheetRecord rows.
WorkOrderTemplateEquipmentPlan — equipmentCategoryId (nullable), quantity, plannedSeconds, description (optional), orderNo. With FK = advisory + drives apply UI's specific-equipment prompt; without FK + with description = creates a free-form WorkOrderEquipmentItem on apply.
WorkOrderTemplateFormWrapper — join: formWrapperId, orderNo. Copied to JobSafetyFormWrapper on apply.
WorkOrderTemplateFieldDefault — default value for a field via documentAttributeAssignmentId + value. Renders as form default when this template is applied; supersedes DAA defaultValue.

4.2 Default value resolution — runtime tiers

TierSourceWhen
3. Instance value DocumentAttributeValue.value on the WO Always wins once the WO has been saved at least once with a value
2. Template value WorkOrderTemplateFieldDefault.value Form-render time, if a template was applied to this WO and this field has a template default
1. DAA default DocumentAttributeAssignment.defaultValue / overrideDefaultValue Form-render time, if no template was applied or the template has no value for this field

This is a render-time resolution. Once the user types a value and saves, the value lives in DocumentAttributeValue as the WO's instance value — no further resolution is needed. The template tier is only consulted when the form first renders (or when a field is reset).

model WorkOrderTemplate {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)

  // WorkOrderTemplateLaborPlan rows; not derived here.

model WorkOrderTemplateMaterialItem {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  workOrderTemplateId String            @db.VarChar(21)
  WorkOrderTemplate   WorkOrderTemplate @relation(
    fields: [workOrderTemplateId], references: [id], onDelete: Cascade)

  // Templates point at the generic Material, not a specific priced
  // variant. The variant (and therefore unit price) is selected at
  // runtime once the actual size / SKU is known — e.g. an insulation
  // fitting template specifies the fitting type; the tech picks 1" or
  // 2" depending on the pipe encountered. Null is permitted for
  // description-only rows ("custom-cut gasket per spec").
  materialId  String?    @db.VarChar(21)
  Material    Material?  @relation(fields: [materialId], references: [id],
                                    onDelete: SetNull)

  description String?  @db.VarChar(500)
  quantity    Decimal? @db.Decimal(10, 2)
  orderNo     Int      @default(0)

  @@index([workOrderTemplateId, isDeleted, orderNo],
          map: "WOTplMat_template_order_idx")
  @@index([materialId], map: "WOTplMat_material_idx")
}

model WorkOrderTemplateLaborPlan {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  workOrderTemplateId String            @db.VarChar(21)
  WorkOrderTemplate   WorkOrderTemplate @relation(
    fields: [workOrderTemplateId], references: [id], onDelete: Cascade)

  // Two modes:
  //   A) Structured advisory — tradeLevelId is set. The plan describes
  //      planned crew composition; description (if any) is an annotation.
  //      On apply: NO runtime record is created (TimeSheetRecord rows are
  //      created later via the normal scheduling flow once dated).
  //   B) Unstructured pre-fill — tradeLevelId is null and description is
  //      set. The plan represents an expected free-form labor line.
  //      On apply: a WorkOrderLaborItem row is created on the new Job
  //      with qtyOfWorkers, submittedDuration (= plannedSeconds), and
  //      description copied across; rate is left NULL for the user to
  //      fill at runtime.
  // Resolvers reject create/edit when both tradeLevelId and description
  // are null (a plan with neither is meaningless).
  tradeLevelId String?     @db.VarChar(21)
  TradeLevel   TradeLevel? @relation(fields: [tradeLevelId], references: [id],
                                      onDelete: SetNull)

  qtyOfWorkers   Int      @default(1)
  plannedSeconds Int      @default(0)
  description    String?  @db.VarChar(500)
  orderNo        Int      @default(0)

  @@index([workOrderTemplateId, isDeleted, orderNo],
          map: "WOTplLab_template_order_idx")
  @@index([tradeLevelId], map: "WOTplLab_tradeLevel_idx")
}

model WorkOrderTemplateEquipmentPlan {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  workOrderTemplateId String            @db.VarChar(21)
  WorkOrderTemplate   WorkOrderTemplate @relation(
    fields: [workOrderTemplateId], references: [id], onDelete: Cascade)

  // Two modes (mirrors WorkOrderTemplateLaborPlan):
  //   A) Structured — equipmentCategoryId is set. Drives the apply UI's
  //      "select specific equipment" prompts; user selections become
  //      EquipmentAssignment rows on the new Job. No runtime line item.
  //   B) Unstructured pre-fill — equipmentCategoryId is null and
  //      description is set. On apply: a WorkOrderEquipmentItem row is
  //      created on the new Job with quantity and description copied
  //      across; unitRate is left NULL for the user to fill at runtime.
  //      plannedSeconds is not copied (WorkOrderEquipmentItem has no
  //      time field separate from quantity); admins should reflect time
  //      in the description if needed.
  // Resolvers reject create/edit when both equipmentCategoryId and
  // description are null.
  equipmentCategoryId String?            @db.VarChar(21)
  EquipmentCategory   EquipmentCategory? @relation(
    fields: [equipmentCategoryId], references: [id], onDelete: SetNull)

  quantity       Int      @default(1)
  plannedSeconds Int      @default(0)
  description    String?  @db.VarChar(500)
  orderNo        Int      @default(0)

  @@index([workOrderTemplateId, isDeleted, orderNo],
          map: "WOTplEq_template_order_idx")
  @@index([equipmentCategoryId], map: "WOTplEq_category_idx")
}

model WorkOrderTemplateFormWrapper {

5.4 Mutations — apply at WO creation

# createJob is extended to accept an optional template application
# payload. When present, the resolver:
#   1. Validates the template is not archived (templates are untyped —
#      no jobType compatibility check).
#   2. Creates the Job with appliedWorkOrderTemplateId set.
#   3. Atomically creates child rows from the application payload:
#        - WorkOrderChecklistItem rows (from template + any user edits
#          made in the apply UI before submit). photoRequired carries
#          through from the template item to the runtime item; no
#          AssetReference rows are created at apply time — the runtime
#          item is unticked until the user actually ticks it with
#          captured photos (per WO-14).
#        - WorkOrderMaterialItem rows — structured rows carry materialId
#          (MAP picked at runtime); free-form rows (no materialId, just
#          description) carry description only. unitPrice NULL in both
#          cases.
#        - JobSafetyFormWrapper rows (one per formWrapperId)
#        - EquipmentAssignment rows (from user-selected specific equipment
#          per structured equipment plan)
#        - WorkOrderLaborItem rows (only for unstructured labor plans:
#          tradeLevelId null, description set)
#        - WorkOrderEquipmentItem rows (only for unstructured equipment
#          plans: equipmentCategoryId null, description set)
#        - DocumentAttributeValue rows for any field defaults the user
#          accepted without editing
#   4. Bumps WorkOrderTemplate.lastUsedAt to now().
#
# Structured labor plans (with tradeLevelId) and structured equipment
# plans (with equipmentCategoryId) are NEVER materialized into TimeSheetRecord,
# EquipmentTimeEntry, WorkOrderLaborItem, or WorkOrderEquipmentItem rows —
# they remain advisory metadata on the template, surfaced in the apply UI
# as planning guidance and (for equipment) as the "select specific
# equipment" prompts that drive EquipmentAssignment creation.

input WorkOrderTemplateApplicationInput {
  templateId: String!
  # Snapshot diff — what the user kept / edited in the apply UI before
  # submitting. Mirrors the snapshot package from previewWorkOrderTemplate
  # with the user's adjustments applied.
  checklistItems:  [WorkOrderTemplateChecklistDraftInput!]
  materialItems:   [WorkOrderTemplateMaterialDraftInput!]
  formWrapperIds:  [String!]
  equipmentSelections: [WorkOrderTemplateEquipmentSelectionInput!]
  fieldDefaults:   [WorkOrderTemplateFieldDefaultDraftInput!]
}

# Selection per equipment plan: user picks specific equipment (or skips,
# leaving the plan as advisory text on the WO).
input WorkOrderTemplateEquipmentSelectionInput {
  equipmentPlanId: String!         # id of the plan being fulfilled
  equipmentIds:    [String!]!      # specific Equipment instances chosen
}

extend input CreateJobInput {
  workOrderTemplateApplication: WorkOrderTemplateApplicationInput
}
Why apply lives on createJob, not a separate applyWorkOrderTemplate mutation: a separate apply mutation would create the Job in one transaction and the template-derived rows in another, opening a window where a half-applied WO exists. Embedding the application into createJob keeps everything atomic — either the WO and all its template-derived content land together or nothing does.

7. Acceptance Criteria

  1. All seven new Prisma models migrate cleanly with the standard conventions (nanoid IDs, soft-delete flags, timestamps, indexes).
  2. Templates can be created, edited, archived, and restored via GraphQL mutations gated by InstanceSetting___edit.
  3. All six template child collections support full CRUD + reorder via uniform mutation patterns.
  4. Templates are untyped — any active template can be applied to any WO regardless of its jobType; no compatibility validation runs at apply time.
  5. previewWorkOrderTemplate returns a complete snapshot package without any database writes.
  6. createJob with a workOrderTemplateApplication payload creates the Job, child rows (checklist, materials, forms, equipment assignments, field defaults), sets appliedWorkOrderTemplateId, and bumps WorkOrderTemplate.lastUsedAt in a single transaction; failure of any step rolls everything back.
  7. Structured labor plans (tradeLevelId set) and structured equipment plans (equipmentCategoryId set) are not materialized into TimeSheetRecord, EquipmentTimeEntry, WorkOrderLaborItem, or WorkOrderEquipmentItem rows — they remain advisory metadata on the template.
  8. Unstructured labor plans (no tradeLevelId, description set) materialize as a WorkOrderLaborItem row on the new Job: qtyOfWorkers, submittedDuration (= plannedSeconds), and description are copied; rate is NULL.
  9. Unstructured equipment plans (no equipmentCategoryId, description set) materialize as a WorkOrderEquipmentItem row on the new Job: quantity and description are copied; unitRate is NULL; plannedSeconds is intentionally not copied.
  10. Resolvers reject creating a labor or equipment plan row with both the FK and description null.
  11. Structured equipment plan rows drive the apply UI's "select specific equipment" prompts; user selections result in EquipmentAssignment rows on the new Job (created on save, not at preview time).
  12. Form-render time field default resolution: when a template is applied, that template's WorkOrderTemplateFieldDefault.value supersedes DocumentAttributeAssignment.defaultValue; instance values still win once present.
  13. Archiving a template sets Job.appliedWorkOrderTemplateId to NULL on referencing Jobs without altering any other content of those Jobs.
  14. Archiving a referenced Material, TradeLevel, EquipmentCategory, or FormWrapper SetNulls the template child row's FK; the template itself remains valid; preview surfaces the broken row for the apply UI to warn about.
  15. WorkOrderTemplateMaterialItem rows are dual-mode: structured rows carry a generic Material reference (no materialAttributePriceId at the template tier); free-form rows carry only a description (no Material reference). Both modes materialize on apply as WorkOrderMaterialItem rows with materialAttributePriceId NULL and unitPrice NULL — variants and prices are filled in at runtime.
  16. Rich-text values on WorkOrderTemplateChecklistItem.description and rich-text-targeted WorkOrderTemplateFieldDefault.value are sanitized server-side using the same allowlist as WO-14.
  17. WorkOrderTemplateChecklistItem.photoRequired defaults to false; on apply the value carries through to the runtime WorkOrderChecklistItem.photoRequired. No AssetReference rows are created at apply time — the runtime item stays unticked until the user actually completes it with captured photos (per WO-14).
  18. Once a WO is created, subsequent edits to its source template do not propagate to the WO (snapshot semantics).
  19. The WO can never have a template applied a second time — applying is a create-only operation.
