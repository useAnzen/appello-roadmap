A/R Reminder Engine

Configurable reminder schedules per customer. When an invoice goes overdue (or is approaching its due date), Appello automatically sends a reminder email using the TTC-2 send pipeline and a TTC-3 reminder-letter template. Every fired reminder is logged. Admins see a single "what's about to go out" panel to predict the day's nudges.

Customer drivers: Mak (commitment), every billing customer Effort: 3 days · 1 engineer (after scheduler decision) Dependency: TTC-2 + TTC-3 must ship first

1. Why this matters

Today, when an invoice goes unpaid, Appello does nothing. The admin has to remember, on a Monday morning, to pull up an aging spreadsheet, sort by days overdue, then manually email each customer the same "friendly reminder" they emailed last week. Most shops don't do this consistently — invoices age, cash slows, and chase calls happen way too late.

"Send the invoice and letter to the client's email - reminder emails as well." — Mak Surveying (May 5, 2026 commitment call)

Existing data already contains everything needed: JobBill.dueByDate is set on every invoice, JobBill.paidValue tracks what's collected, and configurable payment terms (Q21030-9309) are already in production. The missing piece is the loop that wakes up daily, finds bills past a configurable offset, and fires off the right reminder via TTC-2's send pipeline using a TTC-3 cover-letter template.

This is the single biggest cash-flow lever in the Time-to-Cash story. Even a simple "+14 day friendly nudge" rule typically pulls Days Sales Outstanding down by 5-10 days for trade-services shops.

2. Who this is for

  • Office managers / owners — set the reminder schedule once, monitor it via a dashboard, intervene only on the customers that don't respond.
  • Billing admins — get back the Monday-morning aging spreadsheet hour. Their role shifts from "send the same email 30 times" to "follow up on the 3 customers the system flagged."
  • Customers (recipients) — get a polite, branded nudge before the situation escalates to a phone call.
  • Project managers — see "this customer is 30 days behind on three invoices" before signing the next change order.

As an office manager

As a billing admin
I want to see "what's going out today / this week" in a queue, so I can suppress a reminder that I know is in dispute before it embarrasses us.
As a billing admin
I want to pause reminders on a single bill with a one-click toggle and a note, so I can stop the loop while a customer disputes a charge.
As a billing admin
I want reminders to stop automatically when a bill is marked paid, so I never accidentally chase someone who already paid.
As an owner
I want a weekly digest email summarizing what reminders went out, who's still overdue, and which accounts need a phone call, so I have a "Monday morning A/R briefing" delivered to me.
As an admin
I want to see the full reminder history per bill in the bill flyout, so I have a paper trail of every nudge sent.

4. A day in the life: today vs. tomorrow

Sarah is the office manager at a 50-person mechanical contractor. She has 80 open invoices in flight at any time, with ~20 of them overdue.

Today (no TTC-4)

  1. Monday 8 AM: open the AR Aging spreadsheet (manually exported from Sage)
  2. Sort by days-overdue descending
  3. For each overdue bill, decide whether to send a reminder, call, or skip
  4. Open Outlook, paste the customer's address, type a "friendly reminder" body, attach the invoice (which she has to find first)
  5. Send
  6. Update a separate spreadsheet to track "I reminded them on May 5"
  7. Repeat 20 times
  8. Forget to follow up two weeks later
~2 hours weekly · uneven coverage · DSO drift

Tomorrow (with TTC-4)

  1. Once at setup: configure "+7 / +14 / +30" schedule, assign templates
  2. Daily processor finds eligible bills and fires reminders automatically
  3. Every Monday Sarah gets a digest: 12 reminders sent last week, 3 customers still overdue, 1 dispute flagged
  4. Sarah skims the digest in 5 min, calls only the 1 customer that needs a human
  5. Bill flyout shows the reminder history; admin can pause individual bills if needed
~10 min weekly · consistent coverage · DSO drops 5-10 days

6. What's in / out of scope

✓ In scope (v1)

  • Reminder schedule definition: name + ordered list of (offsetDays, tone, templateId)
  • Schedules at instance level (defaults) and customer level (overrides)
  • Daily processor that runs once per day, finds eligible bills, fires reminders via TTC-2
  • Auto-stop when bill is marked Paid or fully Voided
  • Per-bill suppression toggle ("Pause reminders") with optional note
  • Reminder timeline panel on the bill flyout (sent + scheduled events)
  • "Today's Reminders" page under A/R for admins to skim and skip
  • Weekly digest email to a configurable distribution list
  • Reuse of TTC-3 templates (with new kind = ReminderLetter)
  • Reuse of TTC-2 send pipeline + audit trail (each reminder is a JobBillEmailRecord)
  • Permission gate: jobBillReminder.configure for schedule editing

✗ Out of scope (later)

  • Customer-facing payment portal / "pay now" link in the email
  • SMS reminders
  • Per-bill custom schedules (only customer-level + suppress in v1)
  • Escalation to humans (Slack pings, calendar tasks) — separate spec
  • Configurable cadence based on customer payment behavior (ML scoring)
  • Multi-currency edge cases beyond what TTC-2 already handles
  • Auto-pause on dispute (requires a Dispute model that doesn't exist yet)

7. Decisions needed

D1 · Scheduler infrastructure (the big one)
Appello has no scheduler library installed today — verified via codebase search. Three options:
(a) add node-cron in the existing metrics Hono server (lowest cost, runs once per day from a single instance — fine for v1);
(b) add BullMQ + Redis (most robust but new infra);
(c) external trigger (Digital Ocean scheduled function or AWS EventBridge) calling a new POST /internal/run-ar-reminders endpoint.
Recommend (c) for v1 — zero new infra, externally scheduled, easy to disable per-instance, and the per-instance worker process is just a normal API mutation. (a) is the fallback if (c) is awkward operationally.
D2 · Time-of-day for reminders
Recommend a single configurable instance-wide send hour (default 9 AM in the instance's timezone). Per-customer scheduling is overkill for v1.
D3 · What counts as "overdue" if no dueByDate?
Recommend skip — bill needs an explicit due date or it's never eligible. Surface "missing due date" in the digest so admins can fix it.
D4 · Should reminders go from the original sender, the office manager, or a generic A/R address?
Recommend configurable per schedule, defaulting to the bill's original sender (so the customer recognizes the email). Schedule definition includes a fromUserId override.
D5 · Auto-pause when bill is "Sent" but not yet past the original due date?
Recommend yes — only fire reminders for bills where status = Sent AND dueByDate < today - offsetDays AND paidValue < totalValue. Bill must have been delivered (delivered Mailgun event from TTC-2) — don't remind on bills that bounced.

8. Acceptance criteria

  1. "A/R Reminders" page exists under Settings for users with jobBillReminder.configure.
  2. Admin can create a schedule: name + ordered list of (offsetDays, tone, templateId).
  3. Templates pickable from the list are DocumentTemplate rows with kind = ReminderLetter.
  4. Customer detail page lets the admin assign one of the schedules (or "no reminders").
  5. The daily processor runs once per day at the configured hour (per Decision D2).
  6. The processor finds bills where: status = Sent, last delivery succeeded, dueByDate is past by exactly N days for some rule N in the assigned schedule, no reminder for that rule has been sent yet, bill not Paid, bill not paused, customer has a schedule assigned.
  7. For each match, a reminder email goes out via the TTC-2 send pipeline using the rule's template, and a JobBillReminderEvent row is written.
  8. Bill flyout shows a "Reminder timeline" panel with sent + scheduled events.
  9. One-click "Pause reminders" toggle on a bill stops further reminders for that bill (with optional note).
  10. Marking a bill as Paid auto-cancels all scheduled reminders.
  11. "Today's Reminders" admin page lists everything firing today/this week with skip actions.
  12. Weekly digest email is sent to a configurable list with: count of reminders sent, top overdue customers, bills missing due dates, bills with bounced sends.
  13. Permission denial returns a clear error.
  14. If TTC-2's send fails (Mailgun down, bounce), the reminder event is logged with status FAILED and is retried by the next day's run.
  15. Reminders never fire on the same bill+rule twice (idempotent on (jobBillId, ruleId)).

Engineering notes

Data model

Three new models. Schedules and rules are configuration; events are the audit log of every fired reminder.

model JobBillReminderSchedule {
  id           String  @id @db.VarChar(21)
  isDeleted    Boolean @default(false)
  isArchived   Boolean @default(false)
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  name         String  @db.VarChar(191)
  description  String? @db.Text
  fromUserId   String? @db.VarChar(21)   // null = use bill's original sender
  isInstanceDefault Boolean @default(false)

  Rules    JobBillReminderRule[]
  Companies Company[]   // customers using this schedule
}

model JobBillReminderRule {
  id          String  @id @db.VarChar(21)
  scheduleId  String  @db.VarChar(21)
  Schedule    JobBillReminderSchedule @relation(fields: [scheduleId], references: [id], onDelete: Cascade)

  offsetDays  Int           // positive = past due, negative = pre-due (future)
  tone        ReminderTone
  templateId  String        @db.VarChar(21)
  Template    DocumentTemplate @relation(fields: [templateId], references: [id])

  sortOrder   Int

  @@index([scheduleId])
}

enum ReminderTone { FRIENDLY SECOND_NOTICE FINAL CUSTOM }

model JobBillReminderEvent {
  id          String   @id @db.VarChar(21)
  jobBillId   String   @db.VarChar(21)
  JobBill     JobBill  @relation(fields: [jobBillId], references: [id], onDelete: Cascade)

  ruleId      String   @db.VarChar(21)
  Rule        JobBillReminderRule @relation(fields: [ruleId], references: [id])

  scheduledFor DateTime
  firedAt      DateTime?
  status       ReminderEventStatus @default(SCHEDULED)
  emailRecordId String?  @db.VarChar(21)   // links to JobBillEmailRecord (TTC-2)
  EmailRecord   JobBillEmailRecord? @relation(fields: [emailRecordId], references: [id])
  failureReason String?  @db.VarChar(500)

  @@unique([jobBillId, ruleId])  // idempotency guarantee
  @@index([scheduledFor, status])
}

enum ReminderEventStatus { SCHEDULED SENT SKIPPED PAUSED FAILED CANCELLED }

model Company {
  // ...
  reminderScheduleId String? @db.VarChar(21)
  ReminderSchedule   JobBillReminderSchedule? @relation(fields: [reminderScheduleId], references: [id])
}

model JobBill {
  // ...
  pauseReminders         Boolean @default(false)
  pauseRemindersNote     String? @db.VarChar(500)
}

Daily processor (JobBillReminderModel.runArReminders)

One pass per day per instance. Pseudocode:

async runArReminders(instanceId, today = new Date()) {
  // 1. Find candidate bills
  const bills = await prisma.jobBill.findMany({
    where: {
      isDeleted: false,
      pauseReminders: false,
      paidValue: { lt: prisma.jobBill.fields.totalValue },
      Job: { Customer: { reminderScheduleId: { not: null } } },
      EmailRecords: { some: { status: "DELIVERED" } },  // bill was actually delivered
      dueByDate: { not: null }
    },
    include: { Job: { include: { Customer: { include: { ReminderSchedule: { include: { Rules: true } } } } } } }
  });

  // 2. For each bill × rule, check eligibility
  for (const bill of bills) {
    const rules = bill.Job.Customer.ReminderSchedule.Rules;
    for (const rule of rules) {
      const targetDate = addDays(bill.dueByDate, rule.offsetDays);
      if (!isSameDay(targetDate, today)) continue;

      // Idempotency: skip if event already exists
      const existing = await prisma.jobBillReminderEvent.findUnique({
        where: { jobBillId_ruleId: { jobBillId: bill.id, ruleId: rule.id } }
      });
      if (existing) continue;

      // 3. Fire via TTC-2
      try {
        const emailRecord = await JobBillModel.sendJobBill({
          jobBillId: bill.id,
          coverLetterTemplateId: rule.templateId,
          fromUserId: rule.Schedule.fromUserId ?? bill.lastSentByUserId,
          // subject/body resolved from template via TTC-3 merge engine
        }, SYSTEM_USER_ID);

        await prisma.jobBillReminderEvent.create({
          data: { jobBillId: bill.id, ruleId: rule.id, scheduledFor: today,
                  firedAt: new Date(), status: "SENT", emailRecordId: emailRecord.id }
        });
      } catch (err) {
        await prisma.jobBillReminderEvent.create({
          data: { jobBillId: bill.id, ruleId: rule.id, scheduledFor: today,
                  status: "FAILED", failureReason: err.message }
        });
      }
    }
  }
}

Scheduler invocation (per Decision D1)

Recommended v1: external scheduled trigger. Add a new authenticated endpoint POST /internal/ar-reminders/run that is called once per day at the configured hour by an external scheduler (DigitalOcean scheduled function, GitHub Action cron, or AWS EventBridge). Authenticated via a service-account token. The endpoint just calls JobBillReminderModel.runArReminders(). This avoids introducing Redis, BullMQ, or in-process cron.
