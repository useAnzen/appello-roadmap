Work Order Templates · Settings UI

Admin UI for managing the templates defined in WO-15a. Lives at Property Settings → Work Orders → Templates. Templates list with create/edit/archive/restore; per-template detail page with tabbed editors for each child collection (description, checklist, materials, labor plans, equipment plans, forms, field defaults). Permissions gated on InstanceSetting___edit. No backend changes — this spec consumes the WO-15a GraphQL surface.

Estimate: 4-5 days Sequence: 1.33, after WO-15a Requires: WO-15a Enables: WO-15c

1. Business Case

WO-15a established the seven Prisma models that capture template content and the GraphQL surface to read/write them. This spec is the admin UI: where dispatch leads and ops managers actually build, refine, and retire templates. Without it, the template system is invisible to its primary user — admins armed only with raw GraphQL clients.

The shape draws from Corey's Path A sketch (WOX-02): templates list at /settings/work-orders/templates, "+ New template" button top-right, drilling into a detail page to edit content. The list page is a near-1:1 borrow from WOX-02 (minus the per-customer-default column we dropped). The detail page is new — WOX-02 stubbed it; we build it for real.

2. Scope

Already Built

  • DONE WO-15a — all seven Prisma models, GraphQL queries / mutations, sanitization, permission gating. This spec is purely a UI consumer.
  • DONE Property Settings shell with tabbed sections (matches the existing JobSettingsTabs / PropertySettings pattern)
  • DONE ListTable / TableFeed for sortable, paginated settings lists
  • DONE AsyncMultiselect + CustomCombobox pickers (used for Material, FormWrapper, TradeLevel, EquipmentCategory, DAA selection)
  • DONE TipTap editor (reused for rich field defaults, checklist descriptions, template description)
  • DONE PermissionGate wrapper for InstanceSetting___edit

In Scope (WO-15b)

  • IN New "Templates" tab in Property Settings → Work Orders
  • IN Templates list page — name, description preview, item counts (forms/checklist/materials/plans), estimated duration, last used, active toggle, kebab menu (archive / duplicate-stub / restore-when-archived)
  • IN "+ New template" entry that creates an empty template and routes to its detail page
  • IN Per-template detail page at /settings/work-orders/templates/{id} — header with name + description (TipTap) + estimated-duration + active toggle + last-used badge
  • IN Tabbed child collection editors on the detail page:
    • Checklist — drag-reorder list with TipTap descriptions (mirrors the WO-14 Settings tab editor)
    • Materials — Material picker per row + quantity + description (description-only rows allowed)
    • Labor — TradeLevel picker OR description (dual-mode toggle), qty, planned hours
    • Equipment — EquipmentCategory picker OR description (dual-mode toggle), qty, planned hours
    • Forms — FormWrapper multi-select, drag-reorder
    • Field Defaults — DAA picker per row + value editor (TipTap when DAA target is rich-text)
  • IN Archive flow with confirmation modal that surfaces a count of Jobs that have appliedWorkOrderTemplateId = this template
  • IN "Show archived" toggle on the list page; restore action on archived rows
  • IN Permission gate on the entire surface using InstanceSetting___edit

Out of Scope

  • OUT Backend changes — schema, mutations, sanitization (all WO-15a)
  • OUT Apply UI on the WO create form — WO-15c
  • OUT "Save WO as template" reverse flow — post-1.33 (matches WOX-21)
  • OUT Duplicate-template action — out for V1; the kebab menu shows it as a stub. Easy add in 1.34.
  • OUT Mobile editing — templates are desktop-only management
  • OUT Bulk operations (multi-archive, export/import) — single-row only in V1
  • FUTURE Template builder MCP / AI assistance (matches WOX-22)
  • FUTURE Per-customer default template (the Corey concept we dropped) — revisit if usage data shows the picker workflow isn't enough

Other editors

All four follow the same row-list-with-add-button skeleton as Mockup 2's Labor tab. Implementation will lift heavily from existing components — exact picker / input choices are an implementation-plan concern. The sketches below convey layout and information hierarchy only.

Checklist editor

Mirrors the WO-14 Settings tab editor 1:1 — same component, same drag-reorder, same TipTap descriptions, same per-row "Photo required" toggle. See WO-14 · Mockup 1 — Desktop · WO Settings tab (full management). The template-side editor writes WorkOrderTemplateChecklistItem rows; on apply the photoRequired flag carries through to the runtime WorkOrderChecklistItem per WO-15a.

Materials editor (dual-mode, mirrors Labor / Equipment)

Each row has a Material / Free-form toggle. Both modes write to the same WorkOrderTemplateMaterialItem model and on apply create a WorkOrderMaterialItem on the new WO — the difference is whether the runtime row carries a materialId reference (specific variant picked later) or just a description (truly ad-hoc).

4. Data Model

No schema changes. Every model and FK consumed by this UI is defined in WO-15a. This spec wires the front-end against that schema.

5. API Surface

No new GraphQL types, queries, or mutations. The settings UI consumes the surface defined in WO-15a:
  • workOrderTemplates / workOrderTemplate for the list / detail reads
  • create / edit / archive / restoreWorkOrderTemplate for top-level CRUD
  • Six sets of CRUD mutations for the child collections (create / edit / archive / reorderWorkOrderTemplate{Checklist|Material|Labor|Equipment|FormWrapper|FieldDefault}Item)
One GraphQL extension that lives in this spec's frontend code only: a count field on WorkOrderTemplate for the list page's content pills (12 checks · 2 forms · 3 mat · 2 plans) — implemented as a server-side aggregate to avoid N+1 child fetches per row. The aggregate type WorkOrderTemplateCounts is added to WO-15a's API surface as a small follow-up rather than a separate spec.

7. Acceptance Criteria

  1. Property Settings → Work Orders has a new Templates tab visible only to users with InstanceSetting___edit.
  2. The list page shows active templates by default; toggling "Show archived" reveals archived rows.
  3. Each list row shows accurate content counts for checklist items, forms, materials, and labor + equipment plans, served by the server-side counts aggregate.
  4. "+ New template" creates an empty template via createWorkOrderTemplate and routes the user to the detail page.
  5. The detail page header lets the admin edit name, description (TipTap), estimated duration, and the active toggle; saves go through editWorkOrderTemplate.
  6. The detail page exposes six tabs (Checklist, Materials, Labor, Equipment, Forms, Field Defaults) with row counts displayed in tab labels.
  7. The Checklist editor mirrors the WO-14 Settings tab editor — same component code path; supports drag-reorder, TipTap descriptions, per-row "Photo required" toggle, and add/edit/archive on each row. Photo-required setting carries through to the runtime WorkOrderChecklistItem on apply.
  8. The Materials editor uses the existing Material picker; rows can be description-only (no Material selected); quantity is editable.
  9. The Labor editor renders each row with a Trade Level / Free-form toggle; switching modes clears the previously-set FK or description as appropriate.
  10. The Equipment editor mirrors the Labor editor's dual-mode pattern with EquipmentCategory in place of TradeLevel.
  11. The Forms editor is a reorderable multi-select bound to FormWrapper; saving writes to the join model.
  12. The Field Defaults editor uses the DAA picker; the value input renders TipTap when the picked DAA's target type is rich-text and a plain input otherwise.
  13. Archiving a template that has been applied to live WOs surfaces the applied-job count in the confirmation modal; archive proceeds with user confirmation; Job.appliedWorkOrderTemplateId is SetNull on referencing Jobs (per WO-15a behavior).
  14. Restoring an archived template returns it to the active list; subsequent applies bump lastUsedAt normally.
  15. All write operations happen through the WO-15a mutation surface; this spec adds zero new GraphQL operations beyond the counts aggregate.
  16. The Templates tab is hidden entirely (not just disabled) for users without InstanceSetting___edit.
