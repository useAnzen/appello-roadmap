Labor Billable Rate as Markup % · LEM-1 extension

Extends LEM-1's TradeLevelRate.billableValue with an optional markupPercent. Admins can enter "60% markup over cost" instead of a flat dollar amount; the UI computes billable from cost + markup at save time. Smallest possible lift — billable is still the runtime source of truth, no rate-resolution path changes. Action item from the 2026-05-07 Kris × Corey × Emma demo call.

1. Business Case

LEM-1 (in QA) gives every TradeLevelRate a billableValue field — admins type the absolute billable rate per trade level. That's how customers like Thermogenics actually think about pricing internally though: cost-plus-markup. Asking an admin to do "$48 × 1.6" in their head and type the result is friction; a slow walk-back when they later change cost and forget to re-derive billable.

This spec adds the smallest UI affordance for that mental model — admins toggle the rate row to "Markup %" mode, type a percentage, and the UI computes the billable for them. Persisted output stays the same: billableValue. No downstream invoicing/timesheet code changes.

"It would be sick if I could just say, this trade is at 60% over cost — instead of typing the number for every region." — Kris Grant (Thermogenics), 2026-05-07 demo call

2. Scope

Already Built / In Flight

  • DONE LEM-1 — TradeLevelRate.costValue + TradeLevelRate.billableValue (in QA)
  • DONE Labor rate admin UI — table of trade levels × wage regions with cost / billable cells

In Scope (WO-24)

  • IN New optional column on TradeLevelRate: markupPercent Decimal? @db.Decimal(8,4) — stored for round-trip / display, not authoritative for runtime pricing
  • IN Labor rate admin UI · per-row mode toggle: Billable $ | Markup %
  • IN When the row is in Markup % mode and the admin types a percentage, the UI computes billableValue = round(costValue × (1 + markupPercent/100), 2) and shows it in a read-only derived field
  • IN On save, both billableValue (computed) and markupPercent (entered) are persisted
  • IN When opening a row that was last saved in Markup % mode, the UI re-renders in that mode (i.e., remembers the admin's preferred entry shape)
  • IN Toggling a row from Markup % back to Billable $ clears markupPercent on save (keeps state coherent — no orphan markup left behind)

Out of Scope

  • OUT Bulk "apply X% markup to all trade levels" — single-row only in V1
  • OUT Auto-recompute billableValue when costValue changes outside this row's edit (e.g., wage-region cost roll) — see Pending Decision below
  • OUT Markup % on equipment rates — different model (EquipmentRateValue); could mirror later if needed
  • OUT Markup % on materials — Materials uses MaterialAttributePrice; out of LEM scope
  • FUTURE Stored markup as runtime source of truth (billable always derived) — bigger lift, not justified by current ask

4. Data Model

4.1 TradeLevelRate — markupPercent addition

// Added to existing TradeLevelRate model (delivered by LEM-1):
markupPercent Decimal? @db.Decimal(8, 4)
//   Optional admin-facing percentage. When set, billableValue was last
//   computed from costValue × (1 + markupPercent/100). Round-trip only —
//   billableValue remains the runtime source of truth.

4.2 Migration

ALTER TABLE `TradeLevelRate`
    ADD COLUMN `markupPercent` DECIMAL(8, 4) NULL;

No backfill needed. Existing rows have markupPercent = NULL and render in Billable $ mode (status quo).

Why an optional stored field and not UI-only state: if the admin saves a row in Markup % mode, closes the page, and comes back tomorrow, they expect to see the same percentage they typed — not a "best-effort reverse-engineered" markup from cost ÷ billable that may not divide cleanly (rounding). Persisting the input the admin typed avoids that lossy round-trip.

5. API Surface

5.1 Type extension

extend type TradeLevelRate {
  markupPercent: Float
}

5.2 Mutation input extensions

extend input UpsertTradeLevelRateInput {
  markupPercent: Float    # null/omitted clears the field on save
}

No new mutations. Existing upsertTradeLevelRate (or whatever LEM-1 named it — to be confirmed at impl) gains the optional markupPercent input.

5.3 Validation

  • markupPercent must be ≥ 0 if provided. Negative markup is rejected (real users do enter loss-leader rates by typing a small billable, not a negative %).
  • No constraint that billableValue ≈ costValue × (1 + markupPercent/100) on the server — UI is responsible for the relationship; server stores what's sent. Keeps server agnostic to admin entry mode.

7. Acceptance Criteria

  1. TradeLevelRate.markupPercent is added as a nullable Decimal(8,4) column.
  2. Existing TradeLevelRate rows render in Billable $ mode (status quo) since markupPercent = NULL.
  3. The labor rate admin row UI shows a Billable $ / Markup % mode toggle.
  4. In Markup % mode, the billable field is rendered read-only and equals round(costValue × (1 + markupPercent/100), 2).
  5. Saving a row in Markup % mode persists both billableValue (the computed value) and markupPercent (the typed value).
  6. Reopening a row that was saved in Markup % mode renders it in Markup % mode by default.
  7. Toggling from Markup % back to Billable $ and saving clears markupPercent on the row.
  8. The server rejects markupPercent < 0 with a validation error.
  9. No invoicing / timesheet / payroll output changes for rows that don't use markup mode.

9. Pending Decisions

9.1 Recompute billable when cost changes elsewhere?

If admin sets a row to "60% markup" against cost $48 = billable $76.80, then later the wage region cost is updated to $50, should billableValue auto-recompute to $80.00? Lean: no, V1 keeps the relationship as a UX affordance only — billable is whatever was last saved. Admin sees the markup% on next open and can re-save to refresh. Auto-recompute means subscribing to costValue changes and back-propagating to every TradeLevelRate row using markup, which is a much bigger lift.

9.2 Show markup % readout on rows saved in Billable $ mode?

If a row is in Billable $ mode (markupPercent = NULL), should the UI still display the implied markup as a hint ("≈ 60% over cost")? Lean: yes, low cost — pure read-side computation, no schema impact. Helps admins eyeball sanity without forcing them into Markup % mode.

9.3 Naming — markupPercent vs markupRate?

Convention check: do we call it markupPercent (entered as 60.0 = 60%) or markupRate (entered as 0.6 = 60%)? Lean: markupPercent with whole-number input — matches what admins type and matches how Kris talks about it ("60% markup"). UI / API both expose the same shape; computation divides by 100 internally.
