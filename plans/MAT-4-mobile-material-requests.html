MAT-4: Mobile Material Requests (Implementation Plan)

Self-contained execution plan. Another agent should be able to pick this up cold, run the steps in order, and ship a PR. File paths are relative to the monorepo root (apps/api, apps/frontend, apps/mobile). Read Pre-flight first. Companion spec: uis-MAT-4-mobile-material-requests.html (this is the plan; that is the spec + decision log). Code blocks are drop-in starting points — match surrounding style, don’t reformat neighbours.

Overview & Outcome

MAT-4 gives the field a phone-friendly way to ask for materials, by reusing the existing MaterialOrder engine rather than building a parallel MaterialRequest model. A field “request” is a MaterialOrder in an early status. After this lands:

  • A field worker submits a request from mobile — one or many lines, each a catalog pick (materialId) or free text (description), plus quantity, unit, optional photos — scoped to the current Job.
  • The submit creates a MaterialOrder in a Requested status (auto-numbered, lands on the existing system board) with a new child line type, MaterialOrderLineItem, and photos linked via AssetReference.
  • The office sees it in the existing /material-orders board/list, opens the detail, and triages it through status. The free-text/catalog lines render in the detail + PDF and roll into getTotalCost.
The vast majority is reuse. MaterialOrder already provides the job link, status workflow + system board (afterCreate drops a card), priority, required-by date, auto-numbering ({job.fullJobNumber}-{n}), the desktop detail page, the PDF, and getTotalCost. The genuinely new code is: one child model + table, a submitMaterialRequest mutation, line-item handling threaded into the existing upsertFullMaterialOrder / child-lifecycle / cost methods, and the mobile form.
Structurally independent of MAT-0 / MAT-10. Unlike MAT-9, MAT-4 adds no foreign key into the new supply-chain tables — it only touches MaterialOrder, Material (catalog), and Asset, all of which exist today. It can ship in parallel with the rest of the MAT chain. (The only soft coupling: per-line cost in getTotalCost reads Material cost, which MAT-0 later enriches — see Step 5.)

Conventions

  • Golden rule: logic in models/ + services/; resolvers stay thin.
  • No instanceId — single-instance app; the existing MaterialOrderRecord/Value carry none, and neither does this.
  • No slice identifiers (“MAT-4”) in migration names or code comments — they only mean something in the planning interface.
  • gql definitions at the bottom of files; no triple-quote GraphQL descriptions; React components as FC arrow fns; boolean/shorthand JSX props last.

What you are NOT doing

  • No new MaterialRequest / MaterialRequestItem model — the CEO draft’s parallel models are dropped; the request is a MaterialOrder.
  • No change to the structured spec grid (MaterialOrderRecord / MaterialOrderRecordValue / the JobSpecificationArea×axis flow). The wrong-spec-guard mobile wizard is a future slice.
  • No convert-to-PO (one request → many supplier POs is MAT-1 / MAT-5), no inventory fulfillment (MAT-7), no approval workflow. Leave a disabled “Convert to PO” affordance only.
  • No per-line notes (the order has Note threads + header notes); no new permission (reuse materialorder.create).
Decisions carried from the spec (defaults below; confirm with user if they object).
  • D1 — RESTRICT_MATERIAL × mobile: the mobile request entry point is not gated by RESTRICT_MATERIAL (publicRuntimeConfig.n); that flag keeps gating the heavyweight desktop surfaces only. (Step 7.)
  • D2 — submitter: reuse orderedByUserId as the field submitter; no new requestedByUserId this slice.
  • D3 — mobile-friendly create: default description/name and default statusId to the Requested PropertyValue, so a submit needs only job + lines (Step 5).

Step 4 — Model: MaterialOrderLineItem.ts

Goal

Files
apps/api/src/models/MaterialOrderLineItem.ts (NEW) NEW

Copy the shape of MaterialOrderRecordValue.ts. The one bit of real logic is the exactly-one-of guard.

import { BaseModel } from "./base/_BaseModel";
import prisma from "./_prismaClient";
import { ValidationError } from "../errors";
import type { FullModel, IField, IMaterialOrderLineItem } from "../types";

class MaterialOrderLineItemModel extends BaseModel<IMaterialOrderLineItem> {
    public name = "MaterialOrderLineItem";
    name_plural = "MaterialOrderLineItems";

    protected prisma = prisma.materialOrderLineItem;
    protected modelFields: IField<IMaterialOrderLineItem>[] = [
        { name: "materialOrderId", type: "string", options: { isRequiredOnCreate: true } },
        { name: "materialId", type: "string" },
        { name: "description", type: "string", options: { maxLength: 500 } },
        { name: "quantity", type: "float", options: { isRequiredOnCreate: true } },
        { name: "unitOfMeasure", type: "string" }
    ];

    // exactly one of materialId / description must be present
    public assertCatalogXorFreeText(item: Partial<IMaterialOrderLineItem>): void {
        const hasMaterial = !!item.materialId;
        const hasText = !!item.description && item.description.trim().length > 0;
        if (hasMaterial === hasText) {
            throw new ValidationError(
                "A line must be either a catalog material or a free-text description, not both or neither."
            );
        }
    }

    public async createManyItems(
        data: Partial<FullModel<IMaterialOrderLineItem>>[],
        currentUserId: string
    ): Promise<FullModel<IMaterialOrderLineItem>[]> {
        data.forEach((d) => this.assertCatalogXorFreeText(d));
        return super.createManyItems(data, currentUserId);
    }

    public async archiveChildren(): Promise<void> {
        return Promise.resolve();
    }
}

export { MaterialOrderLineItemModel };
Why a guard, not a DB constraint: MySQL can’t express “exactly one of two nullable columns” portably via Prisma, and the team’s pattern is model-layer validation. Call assertCatalogXorFreeText from both createManyItems and the upsert path (Step 5).

5.1 — submitMaterialRequest (the mobile entry point)

One method: resolve the Requested status, create the order (auto-numbering + board card come free via the existing createManyItems/afterCreate), create the line items, attach photos. Permission is enforced by the base createItem → materialorder.create.

public async submitMaterialRequest(
    input: {
        jobId: string;
        priorityId?: string;
        requiredByDate?: string;
        notes?: string;
        lineItems: Partial<IMaterialOrderLineItem>[];
        assetIds?: string[];
    },
    currentUserId: string
): Promise<FullModel<IMaterialOrder>> {
    const lineItemModel = new MaterialOrderLineItemModel();
    input.lineItems.forEach((li) => lineItemModel.assertCatalogXorFreeText(li));

    const requestedStatusId = await this.resolveRequestedStatusId();

    // createItem runs checkPermissions(userId, "create") -> materialorder.create
    const order = await this.createItem(
        {
            jobId: input.jobId,
            statusId: requestedStatusId,
            priorityId: input.priorityId,
            requiredByDate: input.requiredByDate,
            notes: input.notes,
            orderedByUserId: currentUserId,           // D2: submitter
            name: "",                                 // D3: defaulted
            description: ""                           // D3: defaulted (non-null col)
        },
        currentUserId
    );

    await lineItemModel.createManyItems(
        input.lineItems.map((li) => ({ ...li, materialOrderId: order.id })),
        currentUserId
    );

    if (input.assetIds?.length) {
        await new AssetModel().attachReferences(
            input.assetIds.map((assetId) => ({
                assetId,
                referenceTable: "MaterialOrder",
                referenceId: order.id
            })),
            currentUserId
        );
    }

    return order;
}
Confirm two names on your branch before coding: (1) the AssetModel bulk-attach method — it exists (an assetReference.upsert over {assetId, referenceTable, referenceId, folderId?} keyed on the compound unique); use the real method name. (2) resolveRequestedStatusId() — helper that finds the MaterialOrder-status PropertyValue named/slugged Requested. See the status seeding note below.

5.4 — getTotalCost

After the existing record/value loop, add catalog line items: for each line with a materialId, add quantity × materialCost; free-text lines contribute 0 at the request stage.

Flag — line-item cost basis. For materialCost, use the canonical material cost helper on your branch (LEM-3a’s MaterialPricingService.bestAvailableCost(materialId); MAT-0 later makes that distributor-source-aware — no change needed here). Request-stage costing is best-effort and informational; authoritative cost comes at the PO step (MAT-1 / MAT-5). If MaterialPricingService isn’t present on your branch yet, fall back to Material.unitCost and leave a // TODO-free note in the plan, not the code.

Step 9 — Smoke test & acceptance

Manual smoke

  1. As a field role with materialorder.create: submit a request with one catalog line + one free-text line + a photo. → A MaterialOrder appears in Requested on the board, auto-numbered, with both lines and the photo.
  2. Submit a line with both materialId and description → rejected with the XOR ValidationError. Same for neither.
  3. Desktop: open the order — line items + photo render; acknowledge moves status + notifies submitter; PDF shows the lines; cost reflects the catalog line.
  4. Confirm an existing structured (record/value) material order still loads, edits, and prices exactly as before.
  5. With RESTRICT_MATERIAL on: desktop material-orders stays hidden; the mobile request flow still works.

Acceptance criteria

  • Mobile submit creates a MaterialOrder in Requested, linked to the Job, auto-numbered.
  • Lines are catalog (by name/SKU) or free-text; mixed lines allowed; XOR enforced at the model.
  • Photos attach via AssetReference (referenceTable="MaterialOrder") and render on the desktop detail.
  • Request appears on the existing board/list, filterable by status / job / priority; acknowledge notifies the submitter.
  • Detail + PDF show line items; getTotalCost includes catalog lines.
  • Submitting requires materialorder.create; the permission group is role-configurable; no new permission added.
  • The structured spec-grid path is unchanged and still functions.

Downstream & deferred

  • Spec-driven mobile selection (the wrong-spec guard): the next slice surfaces MaterialOrderRecord/Value in mobile as an area → system → size → qty wizard. The line-item path stays as the off-spec / unspec’d-job fallback.
  • Convert to PO (MAT-1 / MAT-5): one request → many supplier POs. The disabled affordance from Step 8 becomes live.
  • Fulfill from inventory (MAT-7): “have stock vs need PO” triage on the request.
  • Decisions to confirm: D1 (mobile vs RESTRICT_MATERIAL), D2 (orderedByUserId vs requestedByUserId), D3 (defaulted header fields), and the status-seeding approach (Step 7).
Net new surface: 1 table + 1 child model, 1 submit mutation, line-item threading into 4 existing MaterialOrder methods, 1 mobile form, and small desktop/PDF additions. Everything else — numbering, board, status, notifications, detail page, permissions — is inherited from MaterialOrder.
