Supplier Purchase Orders

Outbound POs to suppliers built on the shared PurchaseOrder model with a type=SupplierPO discriminator: auto-numbered SPO-####, a new PurchaseOrderLineItem child table, line-item cost pulled from the supply chain model, an HTML/Tailwind PDF via the pdf-export endpoint, and a JWT email-link to download (no PDF attachments).

Parent: Release 1.33 Slice: MAT-5 Est: 7–9 days

Reconciliation Note (grounded against repo-2 / Release-v1.33.0)

The original CEO draft assumed a greenfield model, a PurchaseOrderLineItem that already existed, and dead supply-chain entities. Grounding against the live backend reshaped this spec:

  • Builds on MAT-1's shared model, not a new one. MAT-1 brought PurchaseOrder into BaseAuditableModel and deferred type / status / PurchaseOrderLineItem / SPO-#### here. MAT-5 adds exactly those. Existing customer-PO rows default to type=CustomerPO; supplier POs get type=SupplierPO on the same table.
  • Dead FKs collapsed. The line item's manufacturerProductId + distributorPriceId (both deleted in the MAT-0 collapse) become a single materialAttributePriceId FK — the MAT-0 source row that locks variant + cost + SKU at PO time. The line item mirrors the live WorkOrderMaterialItem exactly (catalog XOR free-text, stored cost snapshot, recalculateTotal).
  • No PDF attachments emailed (anti-spam). PDF generation is the normal HTML+Tailwind → pdf-export → PSPDFKit flow (a new DownloadablePDF React template + a reportType case). The "send to supplier" path emails a JWT link to download, reusing the generic emailAction pipeline (PR #7385, Q21030-11893) — with rfi-download/form-download as the existing token-route precedent.
  • Dedicated supplier-PO permission, resolver-enforced. PurchaseOrder stays OUT of permissionsByReferenceModel (adding it would regress customer-PO parent-authorization). Supplier-PO mutations gate on a new supplierPurchaseOrder permission checked explicitly at the resolver.
  • Committed-cost visibility deferred. JobFinancialSummaryService has no "committed cost" concept today; the roll-up of issued-PO totals is split into a follow-up MAT task, not built here.

1 · Business Case & Customer Evidence ▼

The most critical procurement gap. Today “Purchase Order” in Appello means the customer’s PO number — an inbound reference. Contractors need outbound POs to suppliers — formal documents listing materials, quantities, agreed prices, and delivery terms. The November 2025 prototype demonstrated PO creation with an e-commerce metaphor: browse a supplier catalog, add items to a cart, and generate a formal PO document.

Customer Evidence

"Select supplier, browse products with filters, add items to cart, generate PO." — Corey Shelson (Nov 2025 prototype)
"Take 6 material requests, generate 8 POs grouped by supplier." — Corey Shelson (auto-PO vision)
"You'll be able to cut purchase orders, receive shipments..." — DM Industries pricing call

2 · Scope ▼

In Scope

  • IN Add type enum (CustomerPO | SupplierPO, system discriminator) + a customizable statusId → PropertyValue (like jobStatusId; default values Draft → Issued → Closed / Cancelled seeded per instance) to the shared PurchaseOrder; migration defaults existing rows to type=CustomerPO
  • IN Supplier-specific columns: deliveryLocationId (FK → Location), shippingMethod, expectedDeliveryDate (supplier companyId / contactId / issuedDate / amount / terms reuse MAT-1's columns)
  • IN New PurchaseOrderLineItem child table (mirrors WorkOrderMaterialItem: catalog XOR free-text, materialAttributePriceId, stored cost snapshot, recalculateTotal)
  • IN SPO-#### auto-numbering for Supplier POs (global sequence, RFI-## precedent); customer poNumber stays user-entered
  • IN Combined upsert mutation (header + line items, delete-unlisted / create-or-edit sync — upsertWorkOrderLineItems precedent)
  • IN Line-item cost pre-fill from the supply chain model (bestAvailableCost / MAT-0 source row, MAT-9 discount), editable
  • IN Supplier PO form with supplier (Company) picker + material catalog line items
  • IN PO list page filtered to type=SupplierPO with status + supplier filters; PO detail page
  • IN Supplier-PO PDF: new DownloadablePDF React template + a "supplierPO" reportType case; download via pdf-export
  • IN Email a JWT download link to the supplier contact (reuse the emailAction pipeline / PR #7385; token-route precedent rfi-download)
  • IN Supplier PO tab on Company detail page
  • IN New supplierPurchaseOrder permission, enforced at the resolver; gated by env RESTRICT_MATERIAL

Out of Scope

  • OUT Committed-cost roll-up into the Job Financial Summary — no "committed" concept exists in JobFinancialSummaryService today; split to a follow-up MAT task
  • OUT Receiving + Partially/Fully-Received statuses — those statuses and the receipt flow are MAT-6
  • OUT Emailing the PDF as an attachment (anti-spam — link-to-download only)
  • OUT Auto-PO generation from material requests (grouping MAT-4 requests into POs)
  • OUT EDI/API transmission to suppliers; PO approval workflow; mobile PO creation

4 · Data Model ▼

PurchaseOrder — new columns (MAT-5)

MAT-1 brought PurchaseOrder into BaseAuditableModel and added companyId / contactId / issuedDate / amount / terms / description. MAT-5 adds the discriminator, the supplier lifecycle, and three supplier-specific columns. For a Supplier PO, the reused MAT-1 columns mean: companyId = the supplier Company, contactId = the supplier contact, amount = the line-item total.

FieldTypeNotes
typePurchaseOrderType @default(CustomerPO)Hardcoded enum CustomerPO | SupplierPO (a system discriminator, not user-facing). Migration backfills existing rows → CustomerPO.
statusIdString? @db.VarChar(21)FK → PropertyValue (@relation("purchaseOrderStatus")) — customizable per instance, exactly like jobStatusId. Default values seeded (Draft/Issued/Closed/Cancelled, group propertyName="purchase-order-status"). Supplier POs only (null for customer POs). Received values are MAT-6.
deliveryLocationIdString? @db.VarChar(21)FK → Location (the structured-address model used by Company / Job / Contact) — the job-site or warehouse delivery address
shippingMethodString? @db.VarChar(100)e.g. “Will Call”, “Freight”, “Courier”
expectedDeliveryDateDateTime?Requested or promised delivery date
PurchaseOrderLineItemsPurchaseOrderLineItem[]New back-relation (below)

Only type is a Prisma enum (repo convention: enum + const array/type in types/, imported into the model and GraphQL SDL). status is a PropertyValue so instances can rename/recolor/reorder their PO statuses — the same machinery as jobStatus/rfiStatus. Because labels are customizable, the lifecycle code can’t hardcode them: it resolves specific states through new Instance anchor FKs — purchaseOrderDefaultStatusId (create), purchaseOrderIssuedStatusId (issue), purchaseOrderCancelledStatusId (cancel) — mirroring rfiDefaultStatusId/rfiSentStatusId. Job linkage stays via the polymorphic PurchaseOrderAssignment (no direct jobId FK), so a supplier PO rolls up under a Job like customer POs do.

PurchaseOrderLineItem — new child model

New table; mirrors the live WorkOrderMaterialItem (catalog XOR free-text, stored cost snapshot, recalculateTotal). The dead-entity FKs from the CEO draft (manufacturerProductId, distributorPriceId) collapse to a single materialAttributePriceId — the MAT-0 source row that pins the variant, distributor cost, and SKU at PO time.

FieldTypeNotes
id / isDeleted / isArchived / createdAt / updatedAt—Standard base columns
purchaseOrderIdString @db.VarChar(21)FK → PurchaseOrder (the parent)
materialIdString? @db.VarChar(21)FK → Material (catalog mode); null for free-text lines
materialAttributePriceIdString? @db.VarChar(21)FK → MaterialAttributePrice — the chosen variant / MAT-0 source row; locks cost + SKU
descriptionString? @db.VarChar(500)Free-text line description (XOR catalog)
quantityDecimal?Ordered quantity
unitPriceDecimal? @db.Decimal(10, 2)Cost per unit, locked at PO time (pre-filled from bestAvailableCost − MAT-9 discount, editable)
totalDecimal? @db.Decimal(10, 2)Computed quantity × unitPrice via afterCreate/afterEdit → recalculateTotal
orderNoInt @default(0)Row ordering within the PO

No costPrice/unitPrice split as on WorkOrderMaterialItem — a PO line is the buy price, so one unitPrice (cost) suffices. instanceId intentionally omitted (single-instance app).

Numbering

SPO-#### for Supplier POs — a global sequence (company-wide procurement docs, not job-scoped). Generated on create with the RFI-## precedent: SELECT MAX(CAST(SUBSTRING(poNumber, 5) AS UNSIGNED)) … WHERE type = 'SupplierPO' AND poNumber REGEXP '^SPO-[0-9]+$', then SPO-${padStart(4)}. Customer poNumber remains user-entered.

5 · API Surface ▼

Added to the existing PurchaseOrderResolvers object (already spread into graphql/schema.ts — no new registration). Mutations gate on the new supplierPurchaseOrder permission at the resolver.

Extended Types

extend type PurchaseOrder {
  type: String                    # CustomerPO | SupplierPO (enum)
  statusId: String                # FK → PropertyValue (customizable)
  status: PropertyValue           # resolved value (label / color / orderNo)
  deliveryLocationId: String
  DeliveryLocation: Location
  shippingMethod: String
  expectedDeliveryDate: DateTime
  PurchaseOrderLineItems: [PurchaseOrderLineItem!]
}

type PurchaseOrderLineItem {
  id: ID!
  purchaseOrderId: String!
  materialId: String
  Material: Material
  materialAttributePriceId: String
  MaterialAttributePrice: MaterialAttributePrice
  description: String
  quantity: Float
  unitPrice: Float
  total: Float
  orderNo: Int
}

Input Types

One combined upsert (header + line items) following the upsertWorkOrderLineItems sync pattern: delete line items not in the payload, create those without an id, edit the rest; totals recompute in afterCreate/afterEdit.

input UpsertSupplierPOInput {
  id: ID                          # null = create (assigns SPO-####)
  companyId: String!              # supplier
  contactId: String
  jobId: String                   # optional — links via PurchaseOrderAssignment
  statusId: String                # PropertyValue id; omitted → instance default (Draft)
  issuedDate: DateTime
  deliveryLocationId: String       # FK → Location
  shippingMethod: String
  expectedDeliveryDate: DateTime
  terms: String
  description: String
  lineItems: [SupplierPOLineItemInput!]!
}

input SupplierPOLineItemInput {
  id: ID                          # null = new line
  materialId: String
  materialAttributePriceId: String
  description: String             # XOR catalog
  quantity: Float!
  unitPrice: Float                # omitted → resolved from bestAvailableCost
  orderNo: Int
}

Queries & Mutations

extend type Query {
  supplierPurchaseOrders(options: GetListOptions): GetListResult!   # type=SupplierPO
  supplierPurchaseOrder(id: ID!): PurchaseOrder!
  purchaseOrdersForCompany(companyId: ID!): [PurchaseOrder]         # MAT-1 query, reused for the supplier tab
}

extend type Mutation {
  upsertSupplierPurchaseOrder(input: UpsertSupplierPOInput!): PurchaseOrder!
  issueSupplierPurchaseOrder(id: ID!): PurchaseOrder!              # Draft → Issued
  cancelSupplierPurchaseOrder(id: ID!): PurchaseOrder!
  # Email a JWT download link (no attachment) — reuses the emailAction pipeline (PR #7385)
  sendSupplierPurchaseOrderLink(id: ID!, recipientEmail: String!, message: String): Boolean!
}

PDF generation itself is not a GraphQL mutation — the frontend POSTs { reportType: "supplierPO", id } to /api/pdf-export and downloads the returned blob (same as every other document). The public token route (/api/po-download/[token], modeled on rfi-download) validates the JWT and streams that same PDF for emailed links.

7 · Acceptance Criteria ▼

  • Existing PurchaseOrder rows are backfilled to type=CustomerPO by the migration; customer-PO behaviour (number, assignments, roll-up, dropdowns) is unchanged
  • A Supplier PO can be created by selecting a supplier (Company) and adding line items; saving assigns the next SPO-####
  • Catalog line items pre-fill unitPrice from bestAvailableCost (MAT-0 source row, less any MAT-9 discount); the price is editable and free-text lines accept a manual price
  • Line-item total computes as quantity × unitPrice via recalculateTotal; the PO amount reflects the line-item sum
  • The combined upsert syncs line items (deletes omitted, creates new, edits the rest) in one mutation
  • Statuses are customizable PropertyValues (group purchase-order-status), seeded per instance as Draft / Issued / Closed / Cancelled; create/issue/cancel resolve their target value via the new Instance anchor FKs (Received values are MAT-6)
  • PDF generates through pdf-export with company logo, PO number, supplier + ship-to address blocks, itemized table, subtotal/tax/total, terms, signature line; downloadable via the Download button
  • "Send to supplier" emails a JWT download link (no attachment) to the supplier contact; the public token route streams the PDF; expired links can be refreshed
  • A dedicated supplierPurchaseOrder permission is enforced at the resolver for create/edit/issue; PurchaseOrder is NOT added to permissionsByReferenceModel (customer-PO passthrough preserved); surfaces gated by env RESTRICT_MATERIAL
  • Validation: supplier required, ≥1 line item, quantity > 0, catalog XOR free-text per line
  • PO list page filters to type=SupplierPO with status + supplier filters; detail page shows line items with subtotal and grand total
  • Supplier PO tab on the Company detail page lists that supplier’s POs (reuses purchaseOrdersForCompany, filtered to SupplierPO)

Deferred (follow-up MAT task): committed-cost roll-up of issued supplier POs into the Job Financial Summary — requires a new "committed" notion in JobFinancialSummaryService.
