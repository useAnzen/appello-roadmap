Calendar Filter Fix — WO + Project

The scheduling calendar's "Job type" filter is broken — selecting Work Order hides everything instead of showing only WO events. Fix the filter logic and add a Project multi-select alongside it so dispatchers can scope to a project + WO type combo in one move.

Status: Concept · Bug + Polish Effort: ~1d (fix) + ~0.5d (project chip) Extends: WOX-01 · scheduling/calendar Master ref: #22 — Calendar filter fix

1. Where this lives in the app

Page / route: apps/frontend/src/pages/scheduling/calendar.tsx
Components touched: components/Scheduling/CalendarScheduleFilterOptions.tsx · components/Scheduling/JobScheduleCalendarView.tsx · components/Scheduling/CalendarEventPopover.tsx
New components: ProjectFilterChip.tsx (small multi-select chip rendered inside the existing filter rail)
API surface: GraphQL — extend existing scheduledEvents query where filter to accept jobType: [WORK_ORDER] and projectIds: [String]

The CalendarScheduleFilterOptions component already renders a Job Type filter, but the predicate that feeds JobScheduleCalendarView is mismatched against scheduled WO events (WO status is a separate property from job status, and the filter only queries jobStatus). Fixing the predicate is a one-line change; the meaningful work is adding a Project multi-select chip beside it and wiring the chip's selection back through the same query.

3. Key decisions for Emma + Corey to discuss

D1 Multi-select or single-select on Job Type?
Recommended: Multi-select. Dispatchers commonly want WO + Project Job at once (a project tech doing a WO punch-out today). Cost is one chip, value is real.
D2 Saved filter state — per-user, per-instance, or none?
Recommended: Per-user via localStorage. Server-side preference is overkill for V1 and would invent a new UserPreference surface. Start client-side; promote later if customers ask for it across devices.
D3 Default filter on first load?
Recommended: None — show all events. A pre-applied filter on first load makes the calendar look empty for users who don't yet have WOs. Empty calendar reads as broken (the exact bug we're fixing).
D4 Should Project detail "Schedule" tab pre-apply the project filter?
Recommended: Yes. That's the natural entry point — the user already chose the project. Pass ?projectId=... on the calendar route, hydrate the chip, save to localStorage so subsequent visits remember it.
D5 Regression risk — how do we keep this from breaking again?
Recommended: Add 2 e2e tests — (a) "Filter to Work Order only renders WO events", (b) "Filter to Project + WO renders only that project's WOs". Pairs with the WOX-01 dispatch toggle PR — bundle into one review (master plan #22 + #25).
