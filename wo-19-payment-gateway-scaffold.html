Customer Payment Gateway · Scaffold (V1)

Originally scoped as a 1.33 backend-only scaffold (3 Prisma models + feature flag + hidden settings page) so 1.34 activation could be a pure config sprint. Deferred to the 1.34 activation sprint instead — payment gateway models are sensitive to UI-driven edge cases (partial-pay reconciliation, refund / dispute flows, multi-currency, tax handling, fee pass-through behavior, webhook state machine) that don't surface until the UX is built. Shipping schema before UI risks "ship scaffold → reshape scaffold → ship UI" — slower and more disruptive than building data model + UI together. The Path B analysis below is preserved for reference when 1.34 picks this up.

Status: Deferred to 1.34 Original estimate: 1.5-2d (1.33) + ~8-10d (1.34 activation) New estimate: ~10-12d in a single 1.34 sprint (model + UI together)

⚠ Deferred — read this before building

This spec was written for a 1.33 scaffold-only build but is no longer scheduled. The argument for deferring:

  • Premature data modeling risk. Payment gateway integrations have well-established patterns at the surface (Stripe / Square / Helix all expose similar fields), but the long-tail edge cases — partial-payment reconciliation across multiple CustomerPayment rows, refund / dispute flow state machines, tax-inclusive vs tax-exclusive amounts, webhook idempotency, multi-currency rounding — only surface when the UX is built and stress-tested.
  • Scaffold rework cost. Shipping models in 1.33 then discovering during 1.34 UI work that CustomerPayment needs a parent / child relationship for refund linkage (or that amountPaid should be in cents not Decimal, or that we need idempotencyKey for webhook dedup) means migrating real production tables. That's worse than starting fresh in 1.34 with the model shaped correctly the first time.
  • 1.34 activation is the right unit of work. Build the data model and UI together as one ~10-12d sprint. The provider decision (Stripe vs Helix) also lands in 1.34, which means the integration shape can drive the model shape rather than the other way around.

What to do instead in 1.33: nothing. No feature flag, no placeholder mutation, no hidden settings page. The 1.34 spec starts from a clean slate informed by the provider decision and the actual UX requirements.

Sections 1-8 below are the original 1.33 scaffold analysis, kept for reference. Treat as informational, not a build target.

1. Business Case

Customers pay invoices today by check or e-transfer to an email address — slow, manual, hard to reconcile. The long-term play is a "Pay now" button on emailed invoices that takes the customer to a hosted checkout page. Live integration (Stripe Connect Express is the recommended provider) is a 1-2 week activation sprint with config + webhooks + a receipt page.

That activation sprint is much smaller if the data model and permission scaffolding land in 1.33. Otherwise 1.34 starts with a migration → resolver refactor → UI build, all in one sprint. Decoupling the two:

  • 1.33 (this spec): ship the spine — Prisma models, hidden settings page, feature flag, placeholder mutation. Zero customer-visible surface.
  • 1.34 (separate spec): activate — provider config UI, webhook handler, customer-facing checkout, receipt page. Build is purely on top of the spine.
Important: nothing in this spec ships a working payment flow. Customers see no change in 1.33. The deliverable is invisible to anyone outside engineering until 1.34 activation flips the feature flag.

2. Scope

Already Built

  • DONE Existing JobBill model (the invoice entity that will gain the payment link)
  • DONE Feature-flag infrastructure (InstanceSetting values for boolean toggles)
  • DONE Settings page shell (host for the hidden Payments page)
  • DONE InstanceSetting___edit permission (gates the settings page)

In Scope (WO-19)

  • IN Three new Prisma models: PaymentGatewayConfig, CustomerPayment, PaymentMethod (full schema in §4)
  • IN One new nullable column: JobBill.paymentLinkToken (the per-invoice link the future "Pay now" button will resolve)
  • IN Feature flag payments.enabled in InstanceSetting seed (default false)
  • IN Hidden /settings/payments page guarded by both InstanceSetting___edit permission AND the payments.enabled flag — invisible to anyone in 1.33
  • IN Placeholder GraphQL mutation payInvoice(invoiceId, provider) that always returns the error code NOT_IMPLEMENTED — present so 1.34 can flesh it out without changing call signatures
  • IN Models include the fields the activation sprint will need so the migration is one-and-done: amountPaid + amountDue for partial payments (not used in V1, present for forward-compat); passThroughFees Boolean on PaymentGatewayConfig default false (configurable per instance, default absorbed)

Out of Scope

  • OUT Any customer-facing UI — no "Pay now" button on emailed invoices, no checkout page, no receipt page
  • OUT Gateway code — no Stripe SDK integration, no webhook handlers, no callback URL processing
  • OUT Provider selection in V1 — admin can pre-select a provider in the hidden settings page, but selection has no effect until activation
  • OUT Partial payment workflow — fields exist in the model but no resolver / UI consumes them in V1
  • OUT Refund flow, dispute handling, reconciliation reports — all post-activation
  • FUTURE 1.34 activation: provider config UI, hosted checkout page, receipt page, webhook handler, "Pay now" email template button

3. UI Concepts

One UI surface in V1, hidden behind a feature flag. Mockup of both V1 (admin stub) and the future V2 (customer-facing) flow lives in WOX-14 Mockup 1. The V1 deliverable in this spec is just the admin stub.

Hidden Settings → Payments page

  • Route: /settings/payments
  • Visible only when (a) the user has InstanceSetting___edit AND (b) InstanceSetting.payments.enabled = true for the current instance
  • Page contents: provider dropdown (Stripe / Square / Helix — selectable but no live wiring), branding section (placeholder), pass-through-fees toggle (default off), "Activate via Appello support" CTA
  • Saving the form writes to PaymentGatewayConfig but does nothing else
Why the page exists if it's hidden: when 1.34 activation flips the flag, admins have a config target ready. Building it now means activation isn't blocked by needing a settings page built from scratch.

4. Data Model

4.1 New model: PaymentGatewayConfig

model PaymentGatewayConfig {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  // Const-based string per Appello convention; no Prisma enum.
  // Valid values: "STRIPE" | "SQUARE" | "HELIX" (extensible).
  provider    String?  @db.VarChar(50)

  // Externally-provided account id from the gateway (null until activated).
  externalAccountId String? @db.VarChar(255)

  // Pass fees through to the customer (default: absorbed).
  passThroughFees Boolean @default(false)

  // Branding fields (placeholders in V1).
  brandingDisplayName String? @db.VarChar(200)
  brandingSupportEmail String? @db.VarChar(200)

  // Activation flag — only set true by Appello support during 1.34 activation.
  isActivated Boolean @default(false)

  @@index([isDeleted, isArchived], map: "PaymentGatewayConfig_active_idx")
}

4.2 New model: CustomerPayment

model CustomerPayment {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  jobBillId   String   @db.VarChar(21)
  JobBill     JobBill  @relation(fields: [jobBillId], references: [id], onDelete: Cascade)

  paymentMethodId String?        @db.VarChar(21)
  PaymentMethod   PaymentMethod? @relation(fields: [paymentMethodId], references: [id], onDelete: SetNull)

  // Const-based string: "PENDING" | "SUCCEEDED" | "FAILED" | "REFUNDED" | "DISPUTED"
  status        String   @default("PENDING") @db.VarChar(50)

  // Money columns — Decimal(12, 2) per the Appello convention for currency.
  amountPaid    Decimal  @default(0) @db.Decimal(12, 2)
  amountDue     Decimal  @default(0) @db.Decimal(12, 2)

  // Gateway transaction id (null until the future activation populates it).
  externalTransactionId String? @db.VarChar(255)

  // ISO 4217 currency code (e.g., "CAD", "USD").
  currency String @default("CAD") @db.VarChar(3)

  // Fee breakdown (populated by webhook in V2; null in V1).
  feesAmount   Decimal? @db.Decimal(12, 2)

  paidAt DateTime?

  @@index([jobBillId, isDeleted], map: "CustPayment_jobBill_idx")
  @@index([status, isDeleted], map: "CustPayment_status_idx")
}

4.3 New model: PaymentMethod

model PaymentMethod {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  companyId   String   @db.VarChar(21)
  Company     Company  @relation(fields: [companyId], references: [id])

  // Const-based string: "CARD" | "ACH" | "EFT" | "OTHER"
  type        String   @db.VarChar(50)

  // Last 4 digits / masked identifier (no PAN ever stored — gateway tokens only).
  maskedIdentifier String? @db.VarChar(50)

  // Gateway-provided opaque token (null in V1; populated post-activation).
  externalToken String? @db.VarChar(500)

  isDefault   Boolean  @default(false)

  CustomerPayments CustomerPayment[]

  @@index([companyId, isDeleted], map: "PaymentMethod_company_idx")
}

7. Acceptance Criteria

  1. Three Prisma models migrate cleanly with the standard conventions (nanoid IDs, soft-delete flags, timestamps, indexes).
  2. JobBill.paymentLinkToken column is added as nullable; existing JobBill rows are unaffected.
  3. Feature flag payments.enabled is seeded in InstanceSetting with default value false.
  4. The /settings/payments page is unreachable for any user when the flag is false — no link in the settings nav, route returns 404 / forbidden.
  5. When the flag is true AND the user has InstanceSetting___edit, the page renders with a provider dropdown (Stripe / Square / Helix), branding fields, and a pass-through-fees toggle.
  6. Saving the settings form writes to PaymentGatewayConfig via upsertPaymentGatewayConfig with no other side effects.
  7. The payInvoice mutation always returns { success: false, errorCode: "NOT_IMPLEMENTED" } in V1, regardless of inputs.
  8. No customer-facing UI is changed in 1.33 — invoice emails, customer portal, WO detail page all behave identically to before this spec.
  9. No public API behavior change — only the new types / mutations are added; nothing existing is altered.
