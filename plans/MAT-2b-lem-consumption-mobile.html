MAT-2b: LEM Material Consumption — Mobile (Implementation Plan)

Self-contained execution plan. File paths are relative to the monorepo root (apps/mobile, packages/ui). Read Pre-flight first. Companion spec: uis-MAT-2b-lem-consumption-mobile.html. This is a mobile-only, frontend-only slice — the backend is MAT-2a (plan). Code blocks are starting points; match surrounding style.

Overview & Outcome

MAT-2b lets a field worker log material consumption from their phone, by reusing the WO create-flow material editor over the MAT-2a backend. There is no new backend and no new picker. After this lands:

  • From a Job / Work-Order view, the worker opens a “Material” tab, taps Add Entry, and a flyout form opens (mirroring the equipment-time flow).
  • The form embeds MaterialItemEditor (catalog search → size/thickness variant → resolved MAP cost/sell, or a free-text/manual row), wrapped with a work-date picker and a cost-code split.
  • Submit writes the rows via upsertWorkOrderLineItems with status = InReview (stamping the submitter); they appear in the per-job history list and in the desktop MAT-2a table / daily LEM report.
Almost entirely reuse. MaterialItemEditor (packages/ui, wired on mobile as MobileWOMaterialEditor) already does catalog search, X/Y variant resolution, resolveMaterialAttributePrice / resolveMaterialSellPrice, quantity, unit/cost price, total, and a free-text/manual mode. EquipmentCostCodeSubRow already does per-job cost-code allocation. The genuinely new code is a thin flyout form composing these + a work-date field, a history list, and one tab added to SimplifiedJobTasks.
HARD PREREQ — MAT-2a must be merged. MAT-2b writes WorkOrderMaterialItem with the MAT-2a additions (workDate, status, WorkOrderMaterialItemCostCode, the extended upsertWorkOrderLineItems material input, the WorkOrderMaterialItem permission). If MAT-2a isn’t in your branch, this is blocked.

Pre-flight checks

  • Material cost-code AccountCategory slug: equipment uses AccountCategory.slug === "equipment-time" and labour "direct-labour". Find the material slug (grep the cost-code category seeds / config) and use it to scope the cost-code query. Confirm with the user if ambiguous.
  • Permission key on mobile: mobile gates tabs via hasPermissions({...}, permissions). Confirm the obfuscated key MAT-2a’s PermissionMap entry assigns for WorkOrderMaterialItem.create / .approve and use it (do not invent a material: key).
  • Editor free-text + unit: confirm IMaterialRowData carries a unit/UoM field for free-text rows; if not, surface a unit PropertyValue select for blank rows and map it to unitPropertyValueId on submit.

Conventions

  • React components as FC arrow fns; gql at the bottom of files; boolean/shorthand JSX props last.
  • No slice identifiers (“MAT-2b”) in code comments.
  • No new Prisma models, migrations, or resolvers — if you reach for one, stop: it belongs in MAT-2a.

What you are NOT doing

  • No new picker — reuse MaterialItemEditor.
  • No new backend / mutation — status flows through the existing upsertWorkOrderLineItems input.
  • No offline queueing — siblings don’t; out of scope.
  • No standalone route pages — use the flyout pattern, surfaced from a tab.
  • Not the primary approver UI — approval is desktop-primary; only expose mobile approve where the user holds WorkOrderMaterialItem.approve.

Step 1 — Consumption flyout form (compose the reused editor)

Action
NEW apps/mobile/src/components/MaterialConsumption/MaterialConsumptionForm.tsx

Step 2 — Submit → upsertWorkOrderLineItems

Action
NEW apps/mobile/src/components/MaterialConsumption/operations.ts (+ submit handler in the form)

Map each IMaterialRowData + the form’s workDate / cost-code rows into the MAT-2a materialItems input and call the existing mutation. Submit sets status: InReview (the model stamps submittedByUserId on that transition). No new mutation.

mutation UpsertWorkOrderLineItems($input: UpsertWorkOrderLineItemsInput!) {
  upsertWorkOrderLineItems(input: $input)
}

// build per row:
materialItems: rows.map(r => ({
  id: r.id,                               // present when editing
  jobScheduleId,
  workDate,                               // from the date picker
  materialId: r.materialId ?? null,
  materialAttributePriceId: r.priceId ?? null,
  description: r.description ?? null,      // free-text rows
  quantity: r.quantity,
  unitPrice: r.unitPrice,
  costPrice: r.costPrice,
  unitPropertyValueId: r.unitPropertyValueId ?? null,  // free-text UoM only
  status: "InReview",
  costCodes: r.costCodes,                 // [{ costCodeId, quantity }]
}))
Reuse the editor’s price callbacks verbatim. MobileWOMaterialEditor already wires resolveMaterialAttributePrice (variant cost) and resolveMaterialSellPrice (billable). Pull operations.ts from it; only add the workOrderMaterialItems list query (Step 3).

Step 5 — Smoke test & acceptance

  • The reused editor resolves catalog material + variant → MAP price; a free-text/manual row also works.
  • workDate defaults to today and is required; quantity > 0 enforced.
  • Cost-code picker shows only material-typed codes for the job; a line splits across several, writing WorkOrderMaterialItemCostCode rows.
  • Submit writes via upsertWorkOrderLineItems with status = InReview + submitter stamped; it does not auto-approve.
  • Entries appear in the per-job history list and in the desktop MAT-2a table / daily LEM report (same model).
  • History badges show ApprovalStatus; swipe-to-edit re-opens the flyout populated.
  • The “Material” tab is gated on WorkOrderMaterialItem.create; mobile approve appears only with .approve.

Downstream & deferred

  • Offline queueing — deliberately out; revisit only if the mobile timesheet/equipment flows add it first (consistency).
  • Inventory deduction on consumption is MAT-7.
  • Billable accuracy rides on LEM-3a (resolveMaterialSellPrice, already used by the reused editor) and catalog cost on MAT-0 source rows.
