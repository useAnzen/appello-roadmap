Dedicated workOrder.viewPricing Permission

V1 (WOX-11) gates WO pricing on the existing job.financialView permission. This doc adds a dedicated workOrder.viewPricing permission for finer-grained control — e.g. a tech who can see job financials but NOT WO pricing, or vice versa. Default for back-compat: the new permission is ON for any role that already has job.financialView.

Status: Concept · Deferred Effort: ~1-2d · V2 Extends: WOX-11 · WO-3 Master ref: #40

1. Where this lives in the app

Page / route: apps/frontend/src/pages/roles/[id]/edit.tsx (existing role permissions editor)
Components touched: Permission tree component (path TBD — see role edit page), WO pricing components (from WOX-11) — flip hasPermissions(job.financialView) calls to hasPermissions(workOrder.viewPricing)
New components: none — reuses the existing permission tree pattern; just adds a new node
API surface: Prisma migration adds workOrderViewPricing Boolean @default(false) on RolePermission; data migration copies the value from jobFinancialView for every existing role; GraphQL exposes it on the same permissions tree

Surgical permissions split. Today every place in the WO UI that needs to decide "can this user see dollar amounts?" calls hasPermissions({ job: { financialView: true } }, permissions) — that gate was set in WOX-11 explicitly as a temporary back-compat decision. This doc adds the dedicated permission, swaps the call sites, and provides a zero-disruption data migration so no role's effective permissions change at deploy time.

The migration audit row is the safety net: every role gets a system-attributed audit log entry showing exactly what was copied. If something breaks, ops can answer "why does Mike see WO pricing?" in seconds.

2. UI Concept

Role edit page with the permissions tree expanded. Two highlighted rows: existing Job → Financial view stays on, and the new Work Order → View pricing appears (defaulted on with a "migrated" tooltip). Plus a comparison table showing which roles change versus stay the same.

3. Key decisions for Emma + Corey to discuss

D1 Default value on migration?
Recommended: Copy from job.financialView for every existing role. Zero-disruption deploy — every user sees the same thing on day 1 as the day before. Admins opt into the split when they're ready.
D2 Hierarchy — does job.financialView imply workOrder.viewPricing?
Recommended: Independent post-migration. Admins can revoke WO pricing for a role without touching job financials, or vice versa. The whole point of the split is independent control; making one imply the other defeats the purpose.
D3 Deprecation timeline for job.financialView?
Recommended: Never deprecate. The two permissions cover different surfaces — job-level (cost-to-complete, EVB, monthly P&L) vs WO-level (per-visit pricing, T&M log totals). Both exist permanently.
D4 Where to surface in the admin UI?
Recommended: Nested under "Work Order" in the permissions tree (alongside the other WO permissions from V1). Mirrors how job.financialView nests under "Job". Visually obvious which surface each gate controls.
D5 Audit log entry on migration?
Recommended: Yes — one row per role, system-attributed (actorUserId = null, actorSystem = "migration:WOX-24"). Lets ops answer "why does Foreman have this permission?" in one query if there's ever a question.
