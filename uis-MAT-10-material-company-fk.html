Material → Company Relationship

Manufacturer and Distributor on a Material today are free-form attribute picks (MaterialAttributeValue rows pointing at a MaterialAttributeListValue under the manufacturer / distributor attribute) — string labels with no link to the real Company table. This replaces them with a MaterialCompany M:N join keyed to Company, plus a dry-run-first migration that resolves the existing pick-list names against real Companies. Gating prerequisite for the entire supply-chain chain — MAT-0’s priced supply-chain layer (per-source pricing on the material grid) assumes Material→Company is a real link.

1. Business Case

A Material’s manufacturer and distributor look like Companies and behave like Companies — but they are not. They are MaterialAttributeValue rows pointing at a per-attribute pick list (the MaterialAttributeListValue rows whose parent MaterialAttribute.slug is "manufacturer" or "distributor"). They live in a parallel namespace with no foreign key to the real Company table, which causes three concrete pains:

  1. POs and AP can’t link a line back to the material’s supplier. Even though Material and Company sit in the same database, a purchase-order line carrying material X has no way to say “this came from Company Y” via the material itself. The PO’s supplier is independent of the material’s known distributors.
  2. The MAT-0 supply-chain model is blocked. MAT-0 adds per-source pricing — each material cost row carries a manufacturer + distributor Company. That assumes Material→Company is a real relationship. Today it isn’t — so MAT-0 cannot land on top.
  3. Dirty-data drift between the pick list and the Company table. “Grainger” in the manufacturer pick list and “Grainger Industrial Supply” in the Company table are two unrelated things with no link, and nothing keeps them in sync. The Thermogenix import is the live example: it created materials with empty manufacturer/distributor and others whose names match no existing Company.
Also closes the structural half of Q21030-11797. That ticket asks for “validation” of the manufacturer/distributor strings. Once they are FKs to Company, validation becomes “did the user pick a real company” — which the foreign key enforces for free. Recommend resolving Q21030-11797 as “wait for MAT-10, then drop the validation requirement.”
Ticket says 1:N, body recommends M:N — this spec commits to M:N. The same pipe is genuinely bought from two distributors and sometimes made by two manufacturers. A single FK per role would ship and immediately need walking back (see Alternative C).

2. Scope

Backend + the directly-attached read/write surfaces. New join model + migration, the read paths that today resolve the manufacturer/distributor attribute (list view, material-order line items, PDF, facets), the material add/edit form, and the MCP material tools. Priced/SKU’d supplier detail is explicitly not here — that is MAT-0.

In Scope

  • IN MaterialCompany M:N join + MaterialCompanyRole enum, with relations on Material and Company
  • IN Dry-run-first data migration resolving existing manufacturer/distributor pick-list names against real Companies; archive (not drop) the legacy attribute data
  • IN MaterialListFeed view rework to expose comma-joined manufacturer/distributor names, and facet queries resolving to Companies (filter by join-existence)
  • IN MaterialOrderRecordValue + material-order PDF read paths switched from the attribute slugs to the new relation
  • IN Material add/edit form: multi-select Manufacturers / Distributors (flat set, no primary) and inline “+ Add Company”
  • IN MCP create_material / bulk_upsert_materials: accept Company ids; keep a fail-loud string shim for one release

Out of Scope

  • OUT Per-source pricing & SKUs (the priced supply-chain layer) — that is MAT-0
  • OUT Dropping the legacy manufacturer / distributor MaterialAttribute rows (archived now; decommission is a later follow-up — see Q6)
  • OUT A standalone Company-merge/dedup admin tool (the migration creates duplicates conservatively; merging them later is separate)
  • OUT Default-supplier-driven behaviour on requests/POs/estimates — depends on the “primary” decision (Q3) and downstream MAT items

3. Current State — Load-Bearing Givens

Grounded against the Release-v1.33.0 checkout. These are the facts the migration and read-path rework depend on.

1. Manufacturer / Distributor are already structured picks, not raw strings

A material’s manufacturer/distributor is a MaterialAttributeValue whose materialAttributeId points at the MaterialAttribute with slug = "manufacturer" or "distributor"; the selected value is a MaterialAttributeListValue. Dedup within the attribute is already done — one pick-list row per name. So the drift risk is between the pick list and the Company table, not within the pick list. That simplifies the migration: resolve the set of distinct pick-list names to Companies once, then fan out per material.

2. The MaterialListFeed view already returns one manufacturerId / distributorId per material

apps/api/prisma/views/MaterialListFeed.sql LEFT-JOINs the pick-list table once per attribute and exposes manufacturerName / manufacturerId / distributorName / distributorId. The “Id” is a MaterialAttributeListValue.id, not a Company.id — anything downstream treating it as a company id is structurally wrong today. Going M:N forces a decision on what this column becomes (resolved as comma-joined names — see §6).

3. Company.companyTypeId exists but is configurable — not a reliable signal

Company.companyTypeId → PropertyValue in the "company type" property group. These values are customer-configurable — real tenants type companies as “Vendor” / “Customer”, and there is no guarantee a “Manufacturer”, “Distributor”, or “Supplier” value exists at all. So company type cannot drive correctness here.

The authoritative signal is the hardcoded MaterialCompanyRole enum on the join — it is guaranteed to exist and records how this Company relates to this Material, fully independent of the Company’s own type tag. A company that both makes and sells a material gets two rows (different roles); its companyTypeId is irrelevant to that. Company type plays no part in MAT-10 at all (Q2 — decided to ignore it): no filtering, no ordering, no warning, never a migration input. See Q2.

4. MaterialOrderRecordValue reads the attribute slugs by name today

apps/api/src/models/MaterialOrderRecordValue.ts filters attributes notIn: ["distributor", "manufacturer"] (line 184), then separately pulls those two slugs and folds them into a distributorAndManufacture payload (lines 412–440) for the order-item form and PDF. The two-role handling already exists structurally; after migration the data source changes to MaterialCompany + Company.

5. The material list page + facets are keyed to the same ids

The materials list (apps/frontend/src/pages/materials/) renders Manufacturer / Distributor columns and filters via manufacturer/distributor facet queries that pull distinct pick-list names. After migration these pull distinct Companies; filter values move from MaterialAttributeListValue.id to Company.id. Column labels stay; the source moves.

6. MAT-0 is the priced layer above this

MAT-0 adds per-source pricing on the existing MaterialAttributePrice grid — each cost row gains a (distributor + manufacturer) Company source, SKU, and price. MAT-10’s MaterialCompany is the lightweight “this Company makes/sells this material” link; MAT-0 carries the priced detail and keeps MaterialCompany in sync when a source row is created (see Q5). (MAT-0 was collapsed from an earlier ManufacturerProduct/DistributorPrice design.)

4. Data Model Changes

New model + enum

model MaterialCompany {
  id          String              @id @db.VarChar(21)
  isArchived  Boolean             @default(false)
  isDeleted   Boolean             @default(false)
  createdAt   DateTime            @default(now())
  updatedAt   DateTime            @default(now()) @updatedAt

  materialId  String              @db.VarChar(21)
  companyId   String              @db.VarChar(21)
  role        MaterialCompanyRole
  note        String?             @db.VarChar(400)

  Material    Material            @relation(fields: [materialId], references: [id])
  Company     Company             @relation(fields: [companyId], references: [id])

  @@unique([materialId, companyId, role], map: "MaterialCompany_unique_key")
  @@index([materialId])
  @@index([companyId])
}

enum MaterialCompanyRole {
  Manufacturer
  Distributor
  // Supplier intentionally omitted for now — adding a role later is a one-line change (Q1)
}

// + relation MaterialCompanies MaterialCompany[] on both Material and Company
FieldTypePurpose
materialIdVarChar(21)FK → Material
companyIdVarChar(21)FK → Company (the real relationship this whole spec is about)
roleMaterialCompanyRoleManufacturer | Distributor. Same Company may appear under multiple roles. (No Supplier yet — Q1.)
noteVarChar(400)?Optional free note (e.g. “preferred for west region”)
Enum convention. MaterialCompanyRole follows the app’s standard enum pattern (like ApprovalStatus): a Prisma enum with PascalCase values, plus a TS const-array + derived union type in types, exposed as a GraphQL enum via codegen. Implementation detail in the plan (Step 1.1).

Invariants

  • I1. (materialId, companyId, role) is unique — a company can’t appear twice under the same role on the same material. Different roles are allowed.
  • I2. role is authoritative and company type is ignored entirely (Q2). The picker does no company-type filtering, ordering, or warning; the migration never sets or reads companyTypeId. (Types are configurable PropertyValues — a tenant may have only “Vendor”/“Customer” — so they can’t be relied on.)
  • No primary. Each (materialId, role) is a flat set — all manufacturers/distributors are equal and shown together (Q3, Q7); there is no isPrimary column. Flagged for business review (Q3): if a default/primary supplier proves necessary, it’s an additive isPrimary column later, not a reshape.
One migration file — table create + indexes + relations, then the data backfill (next section). Per project convention, one migration per related change. Suggested name: add-material-company-join-and-migrate-attributes.

5. Data Migration

The unique input to resolve is the set of distinct pick-list names per attribute (not per material) — every material that says “Grainger” already points at the same pick-list row. Resolve once, fan out per material. The migration runs in two modes: a dry-run that produces a review CSV and makes no DB changes, and a commit that reads a confirmed CSV and applies it.

PassWhat it does
1 · Build name → company mapFor each pick-list value under the manufacturer / distributor attributes, attempt an exact (case-insensitive, trimmed) match against Company.name. Record match / no-match.
2 · Fuzzy review (dry-run)For near-misses above a similarity threshold, emit a CSV: name | best Company match | similarity | action | materials affected. Human reviews before commit. See Q4.
3 · Create + rewrite (commit)Create Companies for confirmed no-matches — left untyped (companyTypeId = null); the migration never sets or invents company-type PropertyValues (Q2). For every manufacturer/distributor MaterialAttributeValue, insert a MaterialCompany row with the resolved companyId + role (the role carries the meaning). Materials with no value stay empty.
Reviewer in the loop; conservative default. Anything below the match threshold becomes Create, not a fuzzy fold — we’d rather create a duplicate Company that can be merged later than incorrectly fold supplier A’s materials into supplier B. Customers with strong supplier-naming opinions (Thermogenix after the recent import) sign off on the fuzzy matches before commit.
Q4 — scope & threshold need a business + tech review before the plan. The migration’s size hinges on how many customers actually use the materials catalogue at all — current read is “most don’t,” which would make this a small, low-risk backfill, but it needs digging (per-tenant counts of materials with manufacturer/distributor values). The exact fuzzy-match threshold and the review mechanism (CSV vs. admin screen) are decided off the back of that finding.

What happens to the old data (Q6)

  • The manufacturer / distributor MaterialAttribute rows are not dropped — after backfill they get isArchived = true and isDeleted = true so they disappear from live use but the rows are retained for recovery if ever needed.
  • The corresponding MaterialAttributeValue rows (the per-material manufacturer/distributor selections) get the same treatment — isArchived = true + isDeleted = true — preserving the audit trail of each material’s old value through the transition.

6. Read-Path Impacts

MaterialListFeed view — comma-joined names (Q7)

M:N means the view can’t keep a single manufacturerId the way it does today, and with no primary (Q3) every supplier is equal. The view exposes comma-joined name strings — manufacturerNames = GROUP_CONCAT(DISTINCT Company.name) per role, same for distributorNames — so the list cell shows the full set (“JM Eagle, Charlotte Pipe”).

Full set everywhere (list, order item, PDF). This matches the Q3 lean: a material with two distributors should show both wherever it’s displayed, not a single chosen one. If business review later wants a single default, that’s the additive isPrimary path — the view would then also expose a primary* column.

Facets & filters

Manufacturer/distributor facets pull distinct Companies (not pick-list names). Filtering is by join-existence — “materials having a MaterialCompany row with role = Manufacturer and companyId IN (…)” — rather than matching a single id column, since a material can have several. Column labels are unchanged.

Material-order line items & PDF

MaterialOrderRecordValue (lines 184, 412–440) and the material-order PDF read the new MaterialCompany relation instead of the attribute slugs, showing the full comma-joined set per role.

7. API Surface

GraphQL

type MaterialCompany {
    id: String!
    companyId: String!
    Company: Company!
    role: MaterialCompanyRole!
    note: String
}

enum MaterialCompanyRole { Manufacturer  Distributor }

extend type Material {
    MaterialCompanies: [MaterialCompany!]!
    manufacturers: [Company!]!   # role = Manufacturer
    distributors:  [Company!]!   # role = Distributor
}

extend type Mutation {
    createMaterialCompany(input: CreateMaterialCompanyInput!): MaterialCompany!
    updateMaterialCompany(input: UpdateMaterialCompanyInput!): MaterialCompany!
    deleteMaterialCompany(id: String!): Boolean!
}

Material create/edit inputs accept manufacturerCompanyIds: [ID!] and distributorCompanyIds: [ID!] — flat sets, no primary/order semantics (Q3).

MCP tools (Q8)

create_material and bulk_upsert_materials (in apps/api/src/mcp/tools/materialTools.ts) accept manufacturerCompanyIds / distributorCompanyIds as the canonical inputs. For the manufacturer: string / distributor: string shim kept for one release: resolve the name via the Company search MCP; on no match, prompt the user to confirm before creating a new Company — never silently auto-create, never silently fail.

Search → confirm → create; never silent. Silent auto-create is exactly what produced the dirty state this refactor removes. The agent/importer must look the name up (Company search MCP) and, when nothing matches, surface the no-match to the user and wait for an explicit “yes, create it” rather than minting a duplicate on its own.

8. UI — Material Add / Edit

The Material form’s single Manufacturer and single Distributor pick lists are replaced with two multi-select fields — Manufacturers and Distributors — each a Company-backed combobox with an inline + Add to create a new Company.

  • Each field holds a flat set of chips — no primary, no ordering, all equal (Q3). Add/remove only.
  • Any Company is pickable — a plain Company search, no company-type filtering or ordering at all (Q2). No warning, no block.
  • The combobox reuses the existing Company picker pattern; inline “+ Add” opens the standard Company add modal pre-populated with the typed name (company type left to the user / its existing default), then re-resolves the picker on save. No new picker component.
Full set everywhere. Both the list (comma-joined) and the material detail page show all manufacturers/distributors — none singled out.

9. Alternatives Considered

OptionSummaryVerdict
A · MaterialCompany join + role enum One join table with a role discriminator. One query path for “which companies relate to this material and how”; a future role (Supplier, rep, private-label) is one row, not one table. Mirrors existing role-discriminated joins in the codebase. Recommended
B · Two join tables (MaterialManufacturer, MaterialDistributor) One table per role, no enum. Self-describing names, but two of every query/resolver path and a new table per future role. Rejected — roles are structurally identical; divergence fits as nullable columns on the unified join.
C · manufacturerId / distributorId columns on Material Nullable FKs directly on Material (the ticket title’s literal 1:N). Dead simple, no join. Rejected — hard-codes single-supplier; the two-distributors case is real and we’d walk it back immediately.
D · Defer to MAT-0’s priced supply-chain layer Skip MAT-10; treat priced supplier rows as the relationship. Strictly more info per link. Rejected as a replacement — blocked on MAT-0, and forces placeholder SKUs/prices at migration. MAT-10 stays the lightweight link; MAT-0 layers on top.
E · Validate the existing strings (Q21030-11797 path) Keep the attribute strings; add a rule that the chosen name must match a Company.name. Tiny change, zero migration. Rejected — brittle (rename breaks silently), no real relation to query, PO/AP linkage still impossible. MAT-10 is the better answer to Q21030-11797.

10. Decisions & Open Items

Reviewed June 2026. Six decided (baked into the spec above); two flagged for review before the plan locks — Q3 (business) and Q4 (business + tech).

Q1. Supplier as a third role? Decided

Skip Supplier for now — ship Manufacturer / Distributor only. Adding a role later is a one-line enum change, so no cost to deferring.

Q2. Lean on companyTypeId in the picker? Decided

Ignore company type entirely. Plain Company search — no filtering, no ordering, no warning, never a migration input. (Types are configurable; many tenants have only “Vendor”/“Customer”.) role on the join is the sole source of truth.

Q3. Is there a “primary” supplier? Flagged · business review

For now: no primary. Drop the flag; show the full set everywhere (comma-joined). The working assumption is that a material with more than one manufacturer/distributor should surface all of them, not a chosen one.

Needs business review — could go either way. If a default/primary supplier turns out to drive behaviour (default on requests/POs, the one quoted on estimates), we add an isPrimary column later — additive, not a reshape.

Q4. Migration scope, fuzzy threshold & review workflow Flagged · business + tech

Needs digging first. Scope hinges on how many tenants actually use the materials catalogue — current read is “most don’t,” which would make this a small backfill. Pull per-tenant counts of materials carrying manufacturer/distributor values before sizing it.

Interim default holds: exact-match auto-resolve, human review for near-misses, create-new (conservative) below threshold. Exact threshold + review mechanism (CSV vs. admin screen) decided off the usage findings.

Q5. Block on MAT-0, or run first? Decided

MAT-10 first — it’s the gating prerequisite; MAT-0 layers on top. Matches the timeline’s working order.

Q6. What happens to the legacy attribute data? Decided

Archive + isDeleted = true on the manufacturer/distributor MaterialAttribute rows and their MaterialAttributeValue rows — removed from live use, retained for recovery, never hard-dropped.

Q7. List column shape Decided

Comma-joined (full set in the cell) — consistent with no-primary (Q3). Facets filter by join-existence.

Q8. MCP string shim behaviour Decided

Search → confirm → create. When a name is provided, look it up via the Company search MCP; on no match, prompt the user to confirm before creating a new Company. Never silently auto-create, never silently fail.

12. Acceptance Criteria

  • MaterialCompany + MaterialCompanyRole exist with relations on Material and Company; (materialId, companyId, role) is unique (I1)
  • The migration dry-run produces a review CSV and makes no DB writes; commit applies only a confirmed CSV
  • Every manufacturer/distributor MaterialAttributeValue is backfilled into a MaterialCompany row with the resolved Company + role; materials with no value stay empty
  • No-match names create new Companies (left untyped, companyTypeId = null); nothing below the threshold is fuzzy-folded
  • Legacy manufacturer / distributor MaterialAttribute rows and their MaterialAttributeValue rows are set isArchived = true + isDeleted = true (retained, not dropped)
  • No isPrimary column; each (material, role) is a flat set rendered in full everywhere (comma-joined in the list)
  • MaterialListFeed exposes comma-joined manufacturerNames / distributorNames; facets/filters work by join-existence over Companies
  • MaterialOrderRecordValue + the material-order PDF read MaterialCompany instead of the attribute slugs
  • The material add/edit form multi-selects Manufacturers/Distributors (no primary), plain Company search (no company-type filtering), inline “+ Add Company”
  • MCP create_material / bulk_upsert_materials accept Company-id inputs; the string shim searches via the Company MCP and prompts for confirmation before creating on no-match
  • After migration, no live read path resolves manufacturer/distributor from the attribute system
