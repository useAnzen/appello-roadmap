CO-1 · Change Orders with their own Schedule of Values

The job's main contract has a full cost-code SOV — area / system / phase / cost code / value. Large change orders need the same: their own cost-code breakdown, scoped to the CO's bid, sitting beneath the main SOV on the same Planning & Tracking screen. Today CostCode is only keyed to the job, so any code coded against a CO blurs into the main contract totals — and progress invoicing can't separate them. This doc proposes adding CostCode.changeOrderId and rendering each CO's SOV as its own collapsible block.

Jira: Q21030-11809 Companion: CO-2 · Q21030-11812 (mobile filtering) Related: CC-1 · Q21030-11808 (financials rollup) Status: Pre-decision / pre-build Target: v1.33+

The scenario

Source — Q21030-11809 Jira + Rival cost-codes pilot (May 27)

The current Schedule of Values is tied to the original contract only. Change orders are appended below as flat line items, which works when billing is driven purely by % complete on each CO. When cost codes are in play, large change orders need their own cost-code breakdown — a "schedule of values within a schedule of values" — so that time and materials logged against the CO roll up to the right financial buckets and progress billing.

Two practical problems if we don't do this:

  1. Progress invoicing can't separate CO work from base-contract work. JobBillLineItem already has changeOrderId, but CostCode doesn't — so when a JobBill line is generated from a cost-code, there's no way to know if that cost code lived in the base SOV or a CO SOV.
  2. Field labor coded to a CO disappears into the main SOV's totals. If a foreman codes 8 hrs to 2105 Pipe Direct Labor on the change-order portion of the job, that cost code is currently job-scoped only — there's no way for the customer to ask "how much of this base contract code is actually CO work?"

This is the first of the two takeaways from the Rival meeting. CC-1 covers the financials rollup; this doc covers the SOV-per-CO data model and UI.

What's already true (load-bearing givens)

1. The cost-code SOV grid lives on Planning & Tracking

Where: apps/frontend/src/components/DetailsPage/JobDetailsPage/index.tsx · the planning-tracking tab. The SOV editor is apps/frontend/src/components/Forms/CostCode/CostCodeAddEditForm.tsx. The top of the page renders four summary cards (Contract Value, Amount Allocated / Remaining Balance, Total Cost, Total Margin) followed by an Actions row with Import Template and SOV Setup buttons, then the editable cost-code grid. This is the screen the new Change-Order SOV blocks attach to.

2. CostCode is currently scoped only to a job

Where: apps/api/prisma/schema.prisma:4383 — CostCode.
Has jobId, accountItemId, accountCategoryId, area/system/phase/module/component, but no changeOrderId. The unique constraint CostCode_unique_key already includes the area/system/phase/etc tuple plus accountItemId + description — adding changeOrderId to that constraint lets the same logical code exist on both the base contract and a CO without colliding.

3. JobBillLineItem and ProgressReportLineItem already carry changeOrderId

Where: apps/api/prisma/schema.prisma:4360-4374 · JobBillLineItem.changeOrderId + denormalized changeOrderBid, changeOrderSubTitle, changeOrderCustomerReferenceNumber, changeOrderFullEstimateNumber.
Where: apps/api/prisma/schema.prisma:4537 · ProgressReportLineItem.changeOrderId.
So the billing/progress-invoice schema is already aware of change orders — what's missing is the cost-code side. Once CostCode.changeOrderId exists, the existing "is this a CO line?" filter on Progress Report and JobBill generation can read it from the cost code instead of being inferred.

4. EstimateChangeOrderRecord is the CO entity

Where: apps/api/prisma/schema.prisma:3097 — EstimateChangeOrderRecord (used for both Estimates and Change Orders via the type enum).
Has bid (the CO's contract value), fullEstimateNumber, subTitle, includeInJobValue, dateWon, and a status. The "won" filter for CO SOV applicability is "the status maps to Won + includeInJobValue = true". Same record drives the existing JobBillLineItem CO denorm.

5. Cost codes can be imported from templates per job

Where: CostCodeAddEditForm.tsx · the Import Template button opens CopyTemplate which seeds cost codes from a CostCodeTemplate + CostCodeTemplateLineItem. Today this dumps into the base contract. The same flow needs to be reachable for each CO SOV so that customers don't manually rebuild a 30-line CO SOV from scratch.

6. Existing cost-code numbering is free-form per code

From the Jira: "Cost codes used on change orders can reuse the standard cost-code set or use a separate numbering convention (e.g., 3000-series) at the customer's discretion." The data model doesn't enforce ranges — customers can use whatever numbering they like. The collision-avoidance is handled by including changeOrderId in the uniqueness constraint, not by reserving number ranges.

★ Top Option — changeOrderId on CostCode + collapsible Change Order blocks

One column. One UI section. No new join tables. Add a nullable changeOrderId to CostCode; NULL means "base contract" (current behavior). Render the existing SOV grid for the base contract (unchanged), then below it a section labelled Change Orders that lists each won CO as a collapsible block. Each block is the same editor reused — area / system / cost-code rows — scoped to that CO's bid.

How the data flows under this model

  • CostCode.changeOrderId is the only schema change. Nullable FK to EstimateChangeOrderRecord. NULL = base contract. Existing rows backfill to NULL. The unique constraint CostCode_unique_key picks up the new column so the same code/area/system tuple can exist on both base and CO.
  • The CostCode-fed surfaces (Progress Report, JobBill, Financial Forecast) read it through. ProgressReportLineItem.changeOrderId and JobBillLineItem.changeOrderId are already there — when those line items are generated from a cost code, they pull the CO from the cost code rather than from a separately-tracked rule.
  • The UI reuses the existing SOV editor as a sub-component per CO. The Planning & Tracking page becomes: base SOV block (existing editor) → "Change Orders" header → one collapsible CostCodeAddEditForm instance per won CO, each scoped via a changeOrderId prop. Same Import Template / Advanced toggle, same row interactions.
  • Summary cards aggregate. The four top-of-page cards become "Contract Value" = base bid + ∑ won CO bids; "Total Cost" = ∑ allocated across all SOVs; "Total Margin" = derived. Each CO block also shows its own mini-summary inside its collapsible header (CO Value, Allocated, Remaining, Margin).

Why this beats add-a-section-but-keep-cost-codes-flat

  • Filtering is a single column read. WHERE jobId = ? AND changeOrderId IS NULL for base; changeOrderId = ? for a CO. No new tables, no join chain.
  • The existing Progress Report / JobBill filtering logic (which already has changeOrderId on its line items) can collapse to "inherit the CO from the cost code." One less manual selection at invoice time.
  • Existing customers with no cost-coded COs see no behavior change: changeOrderId is NULL everywhere, the base SOV renders exactly as it does today, the Change Orders section is just empty (or hidden — see Q3).
  • Template import works without modification — the same CopyTemplate flow runs with changeOrderId set on each created cost code.

Invariants the system enforces

  • I1. A cost code's changeOrderId is immutable. Confirmed by Emma: a cost code cannot move between base and any CO (or between COs) after creation, regardless of whether referencing rows exist yet. Setup mistakes require delete-and-recreate. Enforced in CostCode.editItem.
  • I2. A cost code with a changeOrderId set must reference a CO on the same jobId. Validated at create time.
  • I3. Only "won" COs (status = Won + includeInJobValue = true) show a CO SOV block. COs in other statuses don't appear — they're not yet contributing to the contract value.
  • I4. The base SOV (changeOrderId IS NULL) is always present even if empty. CO SOVs render only when their CO meets I3.

Cons / tradeoffs

  • Once a TSDRVCC, ProgressReportLineItem, or JobBillLineItem points at a cost code, that cost code can't be moved between base/CO without manual data correction. This is a feature for audit but a constraint for setup mistakes — see Q1.
  • The Planning & Tracking page gets visually busier on jobs with many won COs. Default-collapse all CO blocks except the first to keep scroll length manageable.
  • If a customer's CO has zero cost-coded work (they bill it purely on % complete of the CO bid), the CO block can be left empty — its bid still rolls into the Contract Value summary card via the existing EstimateChangeOrderRecord pipeline, independent of cost codes.

Phase 1Data model + base SOV refactor for CO-awareness

Schema migration

model CostCode {
    // ... existing fields
    changeOrderId String?                    @db.VarChar(21)
    ChangeOrder   EstimateChangeOrderRecord? @relation(fields: [changeOrderId], references: [id])

    // unique constraint gains changeOrderId
    @@unique([jobId, changeOrderId, areaId, systemId, phaseId, moduleId, componentId,
              accountItemId, description, isDeleted], map: "CostCode_unique_key")
}

Backfill is implicit (column defaults to NULL). One Prisma migration. The existing unique-constraint name CostCode_unique_key is replaced with the new tuple — confirm no production data violates the new shape (existing rows all have NULL, so they can't collide on the new column).

Model + resolver changes

  • apps/api/src/models/CostCode.ts — add changeOrderId to modelFields. Validate that the CO exists on the same job at validatePayload.
  • apps/api/src/graphql/models/CostCode.ts — expose changeOrderId on the GraphQL type. Add it to the input shapes (CreateCostCode, EditCostCode).
  • GetCostCodes / GetCostCodesByJob / GetLabourCostCodesByJob — return changeOrderId (and ChangeOrder when needed) so the UI can group rows by CO without an extra query.

SOV editor extraction

Today CostCodeAddEditForm.tsx assumes a job-scoped flat list. Refactor it so it can be invoked with an optional changeOrderId prop. When changeOrderId is set, the form filters its rows to that CO, scopes the Import Template flow to that CO, and writes the value to new rows. When omitted, behavior is unchanged (base contract).

The wrapper that lives on the Planning & Tracking page becomes:

<PlanningTrackingSOV jobId={jobId}>
    <CostCodeAddEditForm jobId={jobId} />                {/* base SOV */}

    <ChangeOrderSOVList jobId={jobId}>
        {wonChangeOrders.map(co => (
            <CollapsibleSOVBlock co={co} key={co.id}>
                <CostCodeAddEditForm jobId={jobId} changeOrderId={co.id} />
            </CollapsibleSOVBlock>
        ))}
    </ChangeOrderSOVList>
</PlanningTrackingSOV>

CollapsibleSOVBlock renders the header (CO label / bid / status / mini-summary / actions). Defaults to collapsed; expand-state is local component state (not persisted) — open the most recent CO by default.

Phase 2Progress Report + Progress Invoice filtering

Progress Report grouping

Today the Progress Report is generated from CostCode rows on a job. With CostCode.changeOrderId populated, the report layout needs to split into:

  • Base Contract section: WHERE costCode.changeOrderId IS NULL
  • One section per CO: WHERE costCode.changeOrderId = $coId

This is a frontend-only change in the Progress Report layout — the data is already there because ProgressReportLineItem carries changeOrderId directly (per the existing schema). The line item's CO is just also derivable from its cost code, which is the load-bearing fact: once cost codes carry the CO, the progress report doesn't need a separate "which CO is this line?" prompt.

Where: apps/api/src/models/ProgressReportLineItem.ts — when a Progress Report is generated from cost codes, the line items already inherit the CO. Confirm the population path uses costCode.changeOrderId rather than re-prompting the user.

JobBill (Progress Invoice) generation

Same story: JobBillLineItem.changeOrderId exists. When the bill is generated from a Progress Report or directly from cost codes, the CO link is read off the cost code. The CO-totals section of the invoice (which today renders from the flat CO line-items at the bottom) becomes a proper "CO progress" sub-table per CO, with its own % complete and total billed-to-date.

Where: apps/api/src/models/JobBill.ts — the generation paths around createManyLineItemsWithTax (line 565) and generateInvoiceFromWorkOrder (line 580). Verify the existing CO denorm logic (changeOrderBid, changeOrderSubTitle, etc.) populates correctly when the source cost code has changeOrderId set.

Summary cards — three options for how CO totals roll up

The four cards at the top of Planning & Tracking today reflect base-contract figures only. Once CO SOVs exist there are three reasonable presentation choices:

A · Single aggregate set of cards (base + all won COs) Recommended

Top cards show "Total Contract Value" = base bid + ∑ won CO bids. "Amount Allocated" = ∑ allocated across all SOVs. "Remaining" = derived. "Total Margin" = weighted average.

Each individual CO block shows its own mini-summary inside its collapsible header (CO Value / Allocated / Remaining / Margin). So users see the rollup at the top and the per-CO numbers when they expand a block.

Why this: matches the existing "Job Value" pill in the page header (which already includes CO value when COs are flagged into job value). One source of truth at the top, drill-down per CO.

B · Separate card sets — one row of cards per SOV (base + each CO)
Heavy UI

The top of the page becomes a vertical stack: base cards, base SOV grid, "CO-001" cards, "CO-001" grid, "CO-002" cards, "CO-002" grid, etc.

Why not: on a job with 5 won COs that's 24 stat cards before the first row of grid. Scroll cost is brutal and the cards repeat the same labels — visual noise.

C · Aggregate cards + a toggle to switch the cards' scope
Med UI

Same single row of cards, but a "Scope: Base / CO-001 / CO-002 / All" pill swaps the numbers in place.

Why not (probably): hidden state (which scope is selected) makes screenshots ambiguous and adds a cognitive step. Option A's expand-block mini-summary delivers the same information without state.

Open for discussion — Option A is the recommendation but worth confirming with Brad / Kate before building.

Alternatives considered

D · New ChangeOrderCostCode table (separate model)
High lift Duplicates schema

Create a parallel ChangeOrderCostCode model with the same shape as CostCode but FK'd to EstimateChangeOrderRecord.

Why we didn't pick it: every consumer of CostCode (TDRVCC, JobBillLineItem, ProgressReportLineItem, JobFinancialForecastLineItem, EquipmentTimeEntryCostCode, TimesheetEntryTemplateCostCode) would need a parallel FK plus a discriminator on every read. The Top Option achieves the same separation with one nullable column.

E · Re-use EstimateChangeOrderRecordValue as the CO line items
Med lift Mismatched semantics

The CO already has EstimateChangeOrderRecordValue rows (description + numeric + accountItemId). Why not just promote those to cost-code-like behavior?

Why we didn't pick it: ECORV is the estimate-time breakdown for pricing the CO. It has different lifecycle constraints (locked once the CO is approved), a different unique key, and doesn't carry area/system/phase/module/component or the cost-code numbering convention. Trying to fork its meaning into a runtime cost-code role would muddle both. Cost codes are operational; ECORV is contractual.

F · Don't add the data field — let customers re-use base codes with a naming convention
No-op Breaks invoicing

Tell customers to prefix CO codes with "CO-" and rely on the name. Group on the frontend by the name prefix.

Why we didn't pick it: string-prefix grouping is fragile (typos, varying conventions, internationalization) and doesn't propagate to JobBillLineItem.changeOrderId which is already structured. The Jira explicitly says: "Each CO line is tied back to the parent change order (so progress invoicing still works — change orders remain their own entity, not merged into the main SOV)." A structured FK is the only way to deliver that.

Open questions for business review

Q1. Can a cost code be moved between base and a CO after creation? ANSWERED · Emma

Immutable. A cost code cannot switch from CO to base contract (or between COs) once created. Setup mistakes require delete-and-recreate. Top Option's design stands as-is — changeOrderId is locked at create time, full stop, regardless of whether TDRVCC / PRLI / JBLI rows exist yet.

Implementation note: validation in CostCode.editItem rejects any update that would change changeOrderId from its current value (including NULL ↔ value).

Q2. Should pending (not-yet-Won) COs show an SOV block?

I3 above says only Won + includeInJobValue = true COs render. But a customer might want to pre-build the SOV on a "Pending" CO so they can hit the ground running on Day 1 of approval.

Why ask: cleanest UX is "hide until approved" so the screen stays focused on active work. But the "draft early" use case is real for large COs. Could expose this as an instance setting if needed.

Q3. Should the Change Orders section be hidden entirely when no COs exist? ANSWERED · Emma

Yes — hide the section header when no COs exist. The exact trigger depends on Q2: if Q2 lands on "Won only," hide when no Won COs exist; if Q2 lands on "Pending too," hide when no Pending-or-Won COs exist. Either way, an empty header is not rendered.

Q4. Summary cards — Option A (aggregate) confirmed? ANSWERED · Emma

Option A confirmed. Single aggregate set of cards at the top of the page (Contract Value = base + ∑ won CO bids; Total Cost = ∑ allocated across all SOVs; Total Margin = derived). Plus the per-CO mini-summary in each collapsible block's header (CO Value / Allocated / Remaining / Margin) for drill-down. Build to this.

Q5. Import Template on CO blocks — same templates, or CO-specific templates?

Emma's leaning: keep the global template library as-is (customers can name templates "CO …" if they want), and add an additional "Import from CO" entry on the CO block's import affordance that lets you pull the cost-code layout from another CO (on this job, or another job). The "Import from Template" button on the CO block continues to use the same global template list.

Still flagged as a business question — Brad/Kate to confirm. Implementation impact is minimal: same flow as the existing Import Template, but with a second source ("from CO") behind a small picker.

Why ask: scope hint. If global templates are sufficient + "import from CO" is added, no template-library work needed. If true CO-specific templates are required, we need a scope toggle on the template list itself.

Q6. Does the Job Value pill in the header continue to reflect base + COs (current behavior)? ANSWERED · Emma

Yes — unchanged. The page header pill remains the canonical Job Value = base + COs flagged into job value (includeInJobValue). Under Option A, the new "Contract Value" summary card derives from the same source — no divergence.

Recommended path forward

  1. Approve the Top Option direction — single CostCode.changeOrderId column + reuse of CostCodeAddEditForm per CO block.
  2. Phase 1 in v1.33: schema migration, model + resolver updates, refactor CostCodeAddEditForm to accept changeOrderId, render the Change Orders section on Planning & Tracking. Most existing CO data continues to behave the same (no changeOrderId on existing rows).
  3. Phase 2 in v1.33 or v1.34: Progress Report + Progress Bill grouping by CO via the already-present changeOrderId on line items. UI-only change once Phase 1 lands.
  4. Q1–Q6 above get a 15-minute conversation with Brad / Kate / Corey before Phase 1 starts. They're cheap to answer and they shape implementation choices.
  5. Pair with CO-2 (Q21030-11812) — the field-worker filtering. CO-2 is what makes the CO SOVs actually useful at time-entry time; without it, the field still doesn't know which SOV their hours are coding to.
Bottom line: One nullable FK on CostCode, reuse of the existing SOV editor scoped per CO, and a collapsible section beneath the base SOV. The schema change is tiny because JobBillLineItem and ProgressReportLineItem already carry changeOrderId — adding it to CostCode simply completes the chain so the line items can inherit instead of being re-tagged manually.
