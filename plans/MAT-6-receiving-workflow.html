MAT-6: Receiving + Two-Way Match (Implementation Plan)

Self-contained execution plan. Another agent should be able to pick this up cold, run the steps in order, and ship a PR. Paths are relative to the monorepo root (apps/api, apps/frontend). Read Pre-flight first. Companion spec: uis-MAT-6-receiving-workflow.html (that is the spec + decision log; this is the plan). Code blocks are drop-in starting points grounded in the named precedents on repo-2 (~6351-line schema) — match surrounding style, don’t reformat neighbours.

Overview & Outcome

Receiving records what physically arrived against a Supplier PO. It draws down the PurchaseOrderLineItem quantities MAT-5 created, auto-advances the PO through two new customizable statuses, and gives the PO detail page a two-way match (Ordered vs Received) + back-order view. After this lands:

  • Two new tables — PurchaseOrderReceipt (header: who/when/packing slip/notes + a global RCV-####) and ReceiptLineItem (per-line received + damaged qty). Both extend BaseModel.
  • A receivePurchaseOrder mutation validates each line (received ≤ remaining), writes the receipt + lines through the models (perm checks / hooks / audit), and recomputes the PO status.
  • Two new PropertyValues — Partially Received + Received — are added to the existing purchase-order-status group MAT-5 created, with two new Instance anchors driving the transition (never matched by label).
  • PurchaseOrderLineItem gains computed receivedQty / backOrderQty GraphQL fields (summed from receipts at query time — no stored columns).
  • Receiving is gated by MAT-5’s dedicated supplierPurchaseOrder permission (resolver-enforced) behind the RESTRICT_MATERIAL env gate.
Decisions baked into this plan (settled with the user this session — see the spec’s reconciliation callout).
  • Two-way match only (Ordered vs Received). No supplier-invoice / AP entity exists in the schema (only customer JobBill), so the “Invoiced” leg — the true three-way match — is its own slice, MAT-11.
  • Committed-cost roll-up is OUT → MAT-12. JobFinancialSummaryService has no “committed” concept today (forecast + actuals only; material actuals come from expense line items). Do not touch it here.
  • Status is a customizable PropertyValue, not an enum — MAT-6 adds two values to MAT-5’s purchase-order-status group + two Instance anchors. Reuses the RFI precedent.
  • Reuse MAT-5’s supplierPurchaseOrder permission (resolver-enforced). Do NOT use materialorder.edit and do NOT add anything to permissionsByReferenceModel.
  • Receipt totals are computed, not stored — no receivedQty/backOrderQty columns on PurchaseOrderLineItem.
  • Damaged semantics: good qty = receivedQty − damagedQty counts toward fulfilment; damaged keeps the line on back-order and feeds Vendor Credits (MAT-8).
  • No instanceId (single-instance app). No MAT-x identifiers in migration names or code comments.

5.1 RCV numbering (global, RFI precedent)

public async getNextReceiptNumber(): Promise<string> {
    const result = await prisma.$queryRaw<[{ maxNum: bigint | null }]>`
        SELECT MAX(CAST(SUBSTRING(receiptNumber, 5) AS UNSIGNED)) as maxNum
        FROM PurchaseOrderReceipt
        WHERE isDeleted = false
        AND receiptNumber REGEXP '^RCV-[0-9]+$'
    `;
    const next = Number(result[0]?.maxNum ?? 0) + 1;
    return `RCV-${String(next).padStart(4, "0")}`;
}

Global (no parent in the WHERE). Wrap the create in the same collision-retry RFI uses (RequestForInformation.ts:272–288): on a receiptNumber unique violation, recompute and retry.

5.2 Received totals (good qty per line)

// good received per line = Σ(receivedQty − damagedQty) across non-deleted receipt lines
public async getReceivedTotals(purchaseOrderId: string): Promise<Map<string, number>> {
    const lines = await prisma.purchaseOrderLineItem.findMany({
        where: { purchaseOrderId, isDeleted: false }, select: { id: true }
    });
    const rows = await prisma.receiptLineItem.groupBy({
        by: ["purchaseOrderLineItemId"],
        where: { isDeleted: false, purchaseOrderLineItemId: { in: lines.map(l => l.id) } },
        _sum: { receivedQty: true, damagedQty: true }
    });
    const map = new Map<string, number>();
    for (const r of rows) {
        map.set(r.purchaseOrderLineItemId, Number(r._sum.receivedQty ?? 0) - Number(r._sum.damagedQty ?? 0));
    }
    return map;
}

5.3 Receive (validate → atomic write → status)

public async receiveAgainstPO(input: IReceivePurchaseOrderInput, userId: string): Promise<IPurchaseOrderReceipt> {
    // 1) load PO + its lines + prior good-received totals (reads)
    const po = await prisma.purchaseOrder.findFirst({
        where: { id: input.purchaseOrderId, isDeleted: false },
        include: { PurchaseOrderLineItems: { where: { isDeleted: false } } }
    });
    if (!po) throw new NotFoundError("Purchase order not found");           // match repo error class
    const prior = await this.getReceivedTotals(po.id);

    // 2) validate each submitted line
    if (!input.lineItems.length) throw new ValidationError("No line items to receive");
    for (const l of input.lineItems) {
        const line = po.PurchaseOrderLineItems.find((x) => x.id === l.purchaseOrderLineItemId);
        if (!line) throw new ValidationError("Line item not on this PO");
        const good = l.receivedQty - (l.damagedQty ?? 0);
        if (l.receivedQty <= 0 || good < 0) throw new ValidationError("Invalid received/damaged quantity");
        const remaining = Number(line.quantity ?? 0) - Number(prior.get(line.id) ?? 0);
        if (good > remaining) throw new ValidationError(`Receiving ${good} exceeds remaining ${remaining}`);
    }

    // 3) create the receipt header + its lines THROUGH THE MODELS — always prefer model.createItem
    //    over raw prisma: it runs permission checks, afterCreate hooks, and audit, and generates the id.
    //    Sequential writes, matching upsertWorkOrderLineItems (WorkOrderLineItems.ts:23-98).
    const receipt = await this.createItem(
        {
            receiptNumber: await this.getNextReceiptNumber(),
            purchaseOrderId: po.id,
            receivedByUserId: userId,
            receivedDate: input.receivedDate ?? new Date(),
            packingSlipNumber: input.packingSlipNumber ?? null,
            notes: input.notes ?? null
        },
        userId
    );

    const lineModel = new ReceiptLineItemModel();
    for (const l of input.lineItems) {
        await lineModel.createItem(
            {
                receiptId: receipt.id,
                purchaseOrderLineItemId: l.purchaseOrderLineItemId,
                receivedQty: l.receivedQty,
                damagedQty: l.damagedQty ?? null,
                notes: l.notes ?? null
            },
            userId
        );
    }

    // 4) recompute PO status via the model edit (perm checks + audit), resolving the target via Instance anchors
    const nextStatusId = await this.resolveStatusAfterReceipt(po.id);
    if (nextStatusId) await new PurchaseOrderModel().editItem(po.id, { statusId: nextStatusId }, userId);

    return receipt;
}
Model methods, not raw prisma — always. The receipt header and every line are written through createItem (and the status flip through editItem) so each write runs its permission checks, afterCreate hooks, and audit, and gets a model-generated id. BaseModel methods can’t enlist in a prisma.$transaction, so the writes are sequential, not atomic — the same trade-off upsertWorkOrderLineItems already lives with. Guard the order so a failure can’t leave a header without lines (create the receipt first; if a line throws, the partial receipt is visible and re-runnable). The PO status is fully derivable from the receipt rows, so it’s recomputed last via the model edit. Wrap the createItem in the RFI-style retry (5.1) so an RCV-#### unique collision regenerates and retries.

5.4 Resolve status via the Instance anchors

private async resolveStatusAfterReceipt(purchaseOrderId: string): Promise<string | null> {
    const lines = await prisma.purchaseOrderLineItem.findMany({
        where: { purchaseOrderId, isDeleted: false }, select: { id: true, quantity: true }
    });
    if (!lines.length) return null;
    const totals = await this.getReceivedTotals(purchaseOrderId);
    const anyReceived = lines.some((l) => Number(totals.get(l.id) ?? 0) > 0);
    const allComplete = lines.every((l) => Number(totals.get(l.id) ?? 0) >= Number(l.quantity ?? 0));

    const instance = await prisma.instance.findFirst({
        select: { purchaseOrderReceivedStatusId: true, purchaseOrderPartiallyReceivedStatusId: true }
    });
    if (allComplete) return instance?.purchaseOrderReceivedStatusId ?? null;
    if (anyReceived) return instance?.purchaseOrderPartiallyReceivedStatusId ?? null;
    return null; // nothing received yet → leave status unchanged
}

Target states are read from the per-semantic Instance anchor, never matched by label — a renamed/recolored “Received” still works. MAT-6 only ever advances forward from Issued; it does not move a PO that is already past Received.

receivedQty: async ({ id }) => {

        where: { purchaseOrderLineItemId: id, isDeleted: false }, _sum: { receivedQty: true }
    });
    return Number(s._sum.receivedQty ?? 0);

backOrderQty: async ({ id, quantity }) => {
    const s = await prisma.receiptLineItem.aggregate({
        where: { purchaseOrderLineItemId: id, isDeleted: false }, _sum: { receivedQty: true, damagedQty: true }

    const good = Number(s._sum.receivedQty ?? 0) - Number(s._sum.damagedQty ?? 0);
    return Math.max(0, Number(quantity ?? 0) - good);
