Options + Plan Schema + Migration Q21030-11814 Refactor

MAT-10 · Material → Company FK Refactor

Manufacturer and Distributor on a Material today live as MaterialAttributeValue rows pointing at a per-attribute pick list (MaterialAttributeListValue rows where the parent attribute's slug is "manufacturer" or "distributor"). They look like Companies, walk like Companies, but they're not — they're string labels in a parallel universe with no link to the real Company table. POs, AP, expenses, and the planned MAT-0 supply chain layer can't connect material → supplier. This doc proposes a MaterialCompany M:N join with a role discriminator, a data migration that resolves the existing pick-list names against real Companies, and the form / list / MCP changes that ride along.

Jira: Q21030-11814 Related: MAT-0 (ManufacturerProduct + DistributorPrice three-level model) Related: Q21030-11797 (validation of existing string fields — partial overlap) Status: Pre-decision / pre-build Target: v1.33+

The scenario

Source — Q21030-11814 Jira + Thermogenix import findings

The Thermogenix material import created ~141 Materials with empty manufacturer/distributor and an unknown number with manufacturer/distributor names that don't match any existing Company. The Jira ticket frames the fix: drop the free-form attribute and make this a real foreign-key relationship to Company — and because the same pipe is bought from two distributors and sometimes made by two manufacturers, model it as M:N rather than 1:N (the ticket title says 1:N but the body recommends M:N — this doc commits to M:N).

Three concrete pains today:

  1. POs and AP can't link a line back to the material's supplier. Even though both Material and Company exist in the same database, a purchase order line carrying material X has no way to say "this came from Company Y" via the material itself — the supplier on the PO is independent of the material's known distributors.
  2. The MAT-0 supply chain model is blocked from doing what it advertises. MAT-0 plans ManufacturerProduct (a Company-keyed manufacturer's catalog) and DistributorPrice (a Company-keyed distributor's price for that product). Both assume Material → Company is a real link. Today it isn't.
  3. Dirty data risk between the pick list and the Company table. Within the attribute itself names are deduplicated (the pick list is one row per name) — but "Grainger" in the manufacturer pick list and "Grainger Industrial Supply" in the Company table are two different things with no link, and nothing prevents either side from drifting.

This refactor is also the structural answer to part of Q21030-11797's validation question: once Manufacturer / Distributor are FKs to Company, "validation" is just "did the user pick a valid company" — which the FK enforces for free.

What's already true (load-bearing givens)

1. Manufacturer and Distributor are already structured picks — not raw strings

Where: apps/api/prisma/schema.prisma:2875 · MaterialAttributeValue with materialAttributeId pointing at the MaterialAttribute row whose slug = "manufacturer" or "distributor". The actual selected value is a MaterialAttributeListValue.id stored in MaterialAttributeValue.value.
Why it matters: dedup within the attribute is already done — there's exactly one MALV row per manufacturer name within the manufacturer attribute. The Jira description's "same supplier spelled three different ways" risk is actually between this pick list and the Company table, not within the pick list. That simplifies the migration: we resolve N MALV rows to Companies, then rewrite each Material's MAV to a MaterialCompany row.

2. MaterialListFeed view already returns single manufacturerId / distributorId per material

Where: apps/api/prisma/views/MaterialListFeed.sql:28-31, 42-73. The view LEFT JOINs the MALV table once per attribute, exposing manufacturerName / manufacturerId / distributorName / distributorId per material. The "Id" here is a MaterialAttributeListValue.id, not a Company.id — anywhere downstream that treats it like a company ID is structurally wrong.
Today the view returns at most one of each. If a Material has multiple MAV rows pointing at the manufacturer attribute, the LEFT JOIN multiplies rows — undefined behavior. Going to M:N means committing the list view to either (a) the primary, (b) a comma-joined string, or (c) a row-multiplied result. We pick one in the open questions.

3. Company already has a companyTypeId property

Where: apps/api/prisma/schema.prisma:807 · Company.companyTypeId → PropertyValue (via CompanyPayableType for AP/AR semantics).
Why it matters: "Manufacturer" / "Distributor" / "Supplier" can be represented as company-type property values rather than as a hardcoded enum on the join. That keeps the source of truth on Company (where customers already maintain it) and lets the same Company carry both roles when they really do both (e.g., a manufacturer that also sells direct). The role discriminator on the join then just records how this Company relates to this Material, independent of the Company's own type tag.

4. MAT-0's ManufacturerProduct + DistributorPrice are the next layer up

Where: plans/MAT-0-supply-chain-model.html (release 1.32 supply chain effort). MAT-0 introduces ManufacturerProduct (Company + Material + manufacturer's SKU) and DistributorPrice (Company + ManufacturerProduct + effective price).
Why it matters: the question "who can make this material" and "who sells this material" is fundamentally what MAT-0 answers, in more detail (per-SKU, per-price). MAT-10's simple "this material has these companies as manufacturers" is a strict subset. The two CAN coexist (MAT-10 is the lightweight relationship, MAT-0 the priced/SKU'd one) but we need to decide whether MAT-10 becomes redundant once MAT-0 ships, or whether it remains the canonical "primary supplier" signal. See Alternative D.

5. MaterialOrderRecordValue reads the existing attribute slugs by name

Where: apps/api/src/models/MaterialOrderRecordValue.ts:184, 412-440. The model explicitly filters MaterialAttributes notIn: ["distributor", "manufacturer"], then separately pulls those two slugs and folds them into a distributorAndManufacture payload for material-order line item display.
Why it matters: this is the read path for the PDF material-order document and the order-item form. After migration it needs to read from MaterialCompany + Company instead. The "two-roles" handling already exists structurally; the data source just changes.

6. The frontend list page has facets and filters keyed to the same IDs

Where: apps/frontend/src/pages/materials/index.tsx:113-130, 198-211, 300-349 · useGetMaterialListManufacturerFacetsLazyQuery / useGetMaterialListDistributorFacetsLazyQuery, "Manufacturer" / "Distributor" columns, and where filter mapping from column name to manufacturerId[] / distributorId[].
Why it matters: the facet queries today pull distinct MALV names. After the migration they need to pull distinct Companies. Filter values change from MALV.id to Company.id. The column labels stay; the source moves.

Top option (recommendation)

Option A · MaterialCompany join with role enum + Company-type seed
Recommended Lift: M

One join table — MaterialCompany(materialId, companyId, role, isPrimary, …) — with role values MANUFACTURER / DISTRIBUTOR (and reserve a third SUPPLIER value for later, see Q1). The same Company can appear under multiple roles on the same Material when it genuinely plays both parts. isPrimary per (material, role) makes the existing "single manufacturer / single distributor" displays well-defined under M:N without forcing one-and-only-one. Soft-delete via isDeleted, audit fields, standard BaseModel CRUD.

Why this over separate join tables: the role enum keeps one query path for "which companies relate to this material in what way" and one set of indexes. Adding a future role (SUPPLIER, MANUFACTURER_REP, PRIVATE_LABEL) is one row, not one table. Symmetry with EstimateChangeOrderRecord's type enum and other existing role-discriminated joins in this codebase.

Why this over the polymorphic / property-tag approach: a real FK lets the query planner reason about it, lets Prisma generate the relation getter, and lets the frontend resolve to a real Company detail page. Tags are a worse approximation of what's already a real relationship.

Invariants:

  • I1. (materialId, companyId, role) is unique — same company can't appear twice under the same role on the same material. Different roles allowed.
  • I2. At most one row per (materialId, role) has isPrimary = true. Enforced in the model layer, not at the DB level (multi-column conditional uniques are awkward in MySQL).
  • I3. Setting a new row to isPrimary = true unsets the previous primary in the same (materialId, role). Done in MaterialCompany.editItem / createItem, in a transaction with the upsert.
  • I4. When the last row in a (materialId, role) group is removed, no implicit promotion happens. The next add gets primary by default.
  • I5. Company.companyTypeId is not enforced against MaterialCompany.role at the DB level (one company can carry "Manufacturer" type and still be assigned as distributor on a material that buys direct). UI surfaces a soft warning when role and company type disagree. See Q2.

Schema change

// New model
model MaterialCompany {
    id          String           @id @db.VarChar(21)
    isArchived  Boolean          @default(false)
    isDeleted   Boolean          @default(false)
    createdAt   DateTime         @default(now())
    updatedAt   DateTime         @default(now()) @updatedAt

    materialId  String           @db.VarChar(21)
    companyId   String           @db.VarChar(21)
    role        MaterialCompanyRole
    isPrimary   Boolean          @default(false)
    note        String?          @db.VarChar(400)

    Material    Material         @relation(fields: [materialId], references: [id])
    Company     Company          @relation(fields: [companyId], references: [id])

    @@unique([materialId, companyId, role], map: "MaterialCompany_unique_key")
    @@index([materialId])
    @@index([companyId])
}

enum MaterialCompanyRole {
    MANUFACTURER
    DISTRIBUTOR
    // SUPPLIER  — reserved, see Q1
}

// Material gets the relation
model Material {
    // ...existing fields
    MaterialCompanies MaterialCompany[]
}

// Company gets the relation
model Company {
    // ...existing fields
    MaterialCompanies MaterialCompany[]
}
Migration combines these into one file — table create + relation on Material + relation on Company, then the data backfill (see next section). Per project convention, one migration per related change. Name suggestion: add-material-company-join-and-migrate-attributes.

Data migration — three-pass strategy

The existing structure gives us a clean migration path: the unique input to resolve is the set of MALV names per attribute (not per material), because every material that says "Grainger" already points at the same MALV row. Resolve once, fan out per Material.

Pass 1 · Build name → company map For each MALV under the manufacturer and distributor attributes: try exact (case-insensitive, trim) match against existing Company.name. Record match / no-match.
→
Pass 2 · Optional fuzzy review For non-matches above a similarity threshold (e.g., Levenshtein, 0.85), produce a side-by-side dry-run CSV: MALV name | best Company match | similarity. Human reviews before commit. See Q4.
→
Pass 3 · Create + rewrite Create new Company rows for confirmed no-match names (typed as the corresponding role). For each MAV row pointing at a manufacturer/distributor MALV, insert a MaterialCompany row with the resolved companyId + role. Materials with no MAV row stay empty.

Reviewer in the loop. The migration is split into a dry-run mode (generates the CSV, makes no DB changes) and a commit mode (reads a confirmed CSV, makes changes). Customers with strong opinions on supplier naming (Thermogenix is the obvious example after the recent import) need to sign off on the fuzzy matches before commit. The default is conservative: anything below the threshold becomes a Create — we'd rather create a duplicate Company that can be merged later than incorrectly fold supplier A's materials into supplier B.

What happens to the old data

  • The MaterialAttribute rows for slugs "manufacturer" and "distributor" are not dropped in this migration. They get isArchived = true after backfill so they stop appearing in the attribute editor. Removing the rows entirely is a follow-up after we're confident no reporting depends on them. See Q6.
  • The corresponding MALV rows under those attributes stay around (archived) — they don't carry data the Company doesn't, but they're cheap to keep and they preserve the audit trail of "the old pick-list value for this material was X" if anyone needs to reconcile during the transition.
  • Existing MaterialAttributeValue rows under those two attributes are flagged isArchived after migration; reads stop using them via the new view.

Material list + facets after migration

The MaterialListFeed view becomes the most-impacted read path. M:N means we can't keep a single manufacturerId column the way the view does today. Three viable post-migration shapes:

ShapeBehaviorTrade-off
(a) Primary-only columns View exposes primaryManufacturerId / Name and primaryDistributorId / Name — pulled from the isPrimary = true row per (material, role). Cleanest replacement. List columns + filters keep working. Hides additional companies — but those are shown on the detail page anyway. Recommended.
(b) Concatenated View exposes manufacturerNames = GROUP_CONCAT(name), same for distributors. No single ID — facet filters work on join-existence not on the concatenated string. Less surprising for users who expect to see all suppliers in the list. Loses filter-by-id ergonomics unless the facet query is rewritten. Awkward sort.
(c) Row-multiplied (denormalized) Drop list-view manufacturer/distributor columns entirely. Live filtering goes through a separate facet endpoint over MaterialCompany. Cleanest semantically. Highest UI lift (changes the column model of the list). Probably wrong for a refactor of this size.
Pick (a). Primary-only columns + facet queries pulling distinct Companies (rather than distinct MALVs) gives the smallest delta. The list looks the same to a user; the IDs underneath swap from MALV.id to Company.id; multi-supplier materials show their primary in the list and the full set on the detail page.

MCP tools

The Jira ticket calls out create_material and bulk_upsert_materials by name (these are the MCP tools backing imports + agent workflows). Today they accept manufacturer and distributor as string inputs that get resolved/created as MALV. After this refactor:

  • Accept manufacturerCompanyIds: ID[] and distributorCompanyIds: ID[] as the canonical inputs. First in array is treated as primary unless an explicit primaryManufacturerCompanyId is provided.
  • Keep accepting manufacturer: string / distributor: string for one release as a backwards-compat shim — the model resolves the string to a Company by exact name and warns when no match exists (see Q8 on whether to auto-create or fail).
  • Tool description gets a short note that the string form is legacy and IDs are preferred, with a pointer to the Company lookup tool.
Don't import string + create silent duplicates. The previous Thermogenix import created the dirty state this whole refactor is meant to remove. Any "accept string, no-match found" path on the MCP side should default to fail loudly until the importer explicitly opts into auto-create-Company semantics. Otherwise the migration we just ran starts re-accumulating dirt the next time the tool runs.

Alternatives considered

Alternative B · Two separate join tables (MaterialManufacturer, MaterialDistributor)
Lift: L

One table per role, no enum. Simpler schema per-table; clearer FK arrows in a schema diagram.

  • Pro: table name self-describes; no enum gymnastics; per-role columns can diverge later (e.g., distributor-specific fields).
  • Con: two of every query path (read, create, update, delete). Adding "Supplier" or "Manufacturer Rep" later is a new table per role rather than a row. Resolvers double in count.
  • Verdict: rejected. The roles are structurally identical right now and any divergence would be small enough to fit as nullable columns on the unified join. M:N with a discriminator is the more compact model.
Alternative C · Add columns directly to Material
Lift: L

Add manufacturerId + distributorId as nullable FKs on the Material table itself. Single FK per role per material. The ticket title's literal "1:N" reading.

  • Pro: dead-simple. No join, no enum, no UI for adding multiples.
  • Con: hard-codes single-supplier per role. Customers with two distributors for the same pipe have to pick one and remember the rest manually. The ticket body explicitly calls this out as a real pattern that should be modeled.
  • Verdict: rejected. We'd ship and immediately need to walk it back.
Alternative D · Defer to MAT-0's ManufacturerProduct + DistributorPrice
Lift: M (later)

Skip MAT-10. Use MAT-0's ManufacturerProduct as the canonical "this material has these manufacturers" link, and DistributorPrice as the "this material is sold by these distributors" link.

  • Pro: no new model. MAT-0 ships and the relationship is implicit. Each "manufacturer of this material" carries an SKU; each "distributor" carries a price — strictly more information.
  • Con: blocked until MAT-0 lands (release 1.32 work, in flight but not done). Forces a manufacturer-of-this-material to have a SKU and a distributor to have a priced product, neither of which we have at migration time. Inflates the migration: 412 simple "Acme Plumbing distributes this material" rows become 412 priced ManufacturerProduct/DistributorPrice triples with placeholder prices.
  • Verdict: we still want MAT-10. MAT-10's MaterialCompany is the lightweight "this Company is involved with this Material somehow" signal. MAT-0's tables are the priced/SKU'd detail. The relationship in MAT-10 can be derivable from MAT-0 rows where they exist (a Material with a ManufacturerProduct has that Company as a manufacturer) but the inverse isn't true — and migrating today's pick-list data into priced product/distribution rows would be lossy.
Alternative E · Validate the existing strings (Q21030-11797 path)
Lift: L

Keep the MaterialAttributeValue strings. Add a validation rule that the chosen MALV's name must exactly match a Company.name. Treat it like an unenforced FK.

  • Pro: tiny change. Zero migration.
  • Con: brittle. Renaming a Company silently breaks every Material pointing at it. No real relation to query through. PO / AP linkage still impossible.
  • Verdict: rejected. This is essentially what Q21030-11797 Option A proposes, and this refactor (MAT-10) is the better answer to Q21030-11797 as well. Recommend resolving Q21030-11797 as "wait for MAT-10, then drop the validation requirement."

Phasing

Phase 1 Schema, model, dry-run migration tooling. Add the MaterialCompany table + relations behind a feature flag. Build the dry-run CSV generator (no writes). Ship the model + GraphQL resolvers + MCP shim accepting both ID and string. Nothing renders the new data yet.

Phase 2 UI + read paths + view swap. Update the material add / edit form. Update the list page facets + filters. Swap the MaterialListFeed view. Update MaterialOrderRecordValue and the PDF. Run the migration in dry-run mode against staging, review with stakeholders, commit on production after sign-off.

Phase 3 Decommission the old attribute. After a release of stability, archive the MaterialAttribute rows with slugs "manufacturer" and "distributor", drop the string-input shim from MCP tools, drop the MALV-backed legacy reads. (See Q6 — this might never fully happen if reporting depends on the old shape.)

Open questions

Q1. Is "Supplier" a real third role today, or reserved for later?

The Jira recommendation lists Manufacturer / Distributor / Supplier. The codebase today only models the first two. "Supplier" could either mean a generic catch-all when neither manufacturer nor distributor is the right label, or it could mean the entity that issues the PO (the "vendor" in AP terms).

Recommendation: reserve the value in the enum (commented out at first) and ship Manufacturer/Distributor only. Promote Supplier when we have a concrete UI need driven by MAT-5 (Supplier POs) or AP work — at that point the meaning is decided by the surface that introduces it.

Q2. Should Company.companyTypeId restrict which companies can be picked for each role?

Two flavors: (a) hard restriction — only Companies with companyType = "Manufacturer" appear in the Manufacturer picker; only "Distributor" in the Distributor picker. (b) soft warning — any Company is pickable, but the picker surfaces the matching-type ones first and shows an inline warning when the picked company's type doesn't match the role. (c) ignored — pickers don't read companyType at all.

(b) is the recommendation in this doc (see Invariant I5). The Thermogenix case is real: a Company tagged "Manufacturer" sometimes plays distributor (selling direct) and customers shouldn't have to re-tag the Company to record that. But surfacing the matching type first keeps the everyday flow fast.

Q3. Is "primary" manufacturer / distributor a real product concept, or just a display convenience?

The schema in this doc includes isPrimary so the list view and exports can show one of each cleanly. If primary has business meaning (e.g., it's the default supplier for material requests, the one quoted on estimates, the one printed on a PO header), that flag drives behavior. If it's just for display, the alternative is to drop the flag, render the full list everywhere, and live with "first by some sort order" in the list view.

Lean: primary has business meaning. Material requests and POs default to the primary distributor; the estimate-line manufacturer is the primary manufacturer. But this is a customer-facing decision — Brad / Kate to confirm.

Q4. Fuzzy-match threshold + review workflow.

Two parts. (a) What similarity score is the cut-off between "auto-match" and "needs review" and "create new"? (b) How does review happen — a CSV that gets edited and committed back, an admin screen, or a Slack message with thumbs-up reactions?

Lean: conservative defaults — auto-match only at 1.00, flag 0.85-0.99 for review, create new below 0.85. Review via CSV (engineer + customer rep review together) for the first run; if this becomes a recurring data-hygiene task, build a small admin screen later.

Q5. Does this work block on MAT-0, or run in parallel?

MAT-0 is release 1.32 supply chain work (ManufacturerProduct + DistributorPrice). MAT-10 doesn't strictly need MAT-0, but the two overlap: a Material with a row in ManufacturerProduct for a given Company arguably already has a manufacturer relationship. If we ship MAT-10 first, MAT-0 needs to keep MaterialCompany rows in sync (creating/updating one creates the other). If we ship MAT-0 first, MAT-10 is potentially redundant for the manufacturer side (DistributorPrice still doesn't fully replace MaterialCompany on the distributor side because it requires a priced product).

Lean: ship MAT-10 first. It's smaller, it's a strict prerequisite for MCP cleanliness (fixes part of Q21030-11797), and MAT-0 can layer on top without retro-fitting the lightweight relationship.

Q6. Drop the old MaterialAttribute rows for manufacturer / distributor — when?

Phase 3 above proposes dropping the legacy attribute rows after a release of stability. But Material List Templates, saved-table views, and exports may have references to those attribute IDs that are hard to detect statically. The conservative path is to never drop them — leave them archived forever and treat the new MaterialCompany as the source of truth going forward.

Lean: archive on migration, never drop. The two MA rows costing one byte each is not worth a forensic audit of saved templates.

Q7. List-view column behavior post-migration — primary-only, or comma-joined?

Shape (a) in the list section was recommended (primary-only). The alternative is comma-joined "JM Eagle, Charlotte Pipe" in the cell.

Lean: primary-only for the list view, with a tooltip / detail page showing the full list. Filters keep working the same way (filter by primary). Sort works on a single deterministic value.

Q8. MCP backwards-compat — accept string and silently create the Company, or fail loudly?

If bulk_upsert_materials is called with manufacturer: "Some New Brand" after the refactor: (a) auto-create a new Company typed Manufacturer and link it, (b) attempt exact-name match against Company and fail (clear error) on no-match, (c) drop the string input entirely after the migration.

Lean: (b). Auto-create is what got us into this mess. The agent or import should be forced to either pass a Company ID or get a clear error directing it to the company-lookup tool. (c) is the long-game position but (b) is friendlier mid-migration.

Bottom line

Ship the MaterialCompany M:N join with a role enum, plus a dry-run-first migration that resolves the existing pick-list names against the real Company table. The data is already structured enough that this is a clean lift — every Material's manufacturer/distributor today is a MALV id, and every MALV name resolves to either an existing Company or a new one we create. M:N solves the "two distributors for the same pipe" case the Jira ticket calls out; an isPrimary flag keeps single-value displays well-defined. MCP tools accept Company IDs going forward; the string-input shim fails loudly so we don't re-accumulate dirt. This work also closes the structural half of Q21030-11797 (validation becomes "FK exists" for free) and unblocks MAT-0's priced supply-chain layer to land on top.
