Inventory Management

Stock tracking by location with receiving intake, job checkout, inter-location transfer, physical count adjustments, movement ledger, and min/max alerts. The operational backbone for material visibility — built polymorphically so it tracks materials today and equipment next.

Parent: Release 1.33 Slice: MAT-7 Est: 8–10 days
Reconciled to live schema (repo-2) + aligned to Shopify's inventory model (for the future PR #7394 integration). Shopify's shape: a catalog thing (their InventoryItem) × a Location = an InventoryLevel row holding per-location quantities, with adjustments carrying a referenceDocumentUri audit pointer. MAT-7 mirrors this 1:1: (1) InventoryLocation → required Location FK (inventoryLocationId is reserved for the FK to InventoryLocation); (2) typeId is a PropertyValue category (the jobType/companyType precedent); (3) notes use polymorphic Note + NoteReferences (threaded comments + assets); (4) InventoryLevel (renamed from the draft’s “InventoryItem”) is the per-location balance — polymorphic referenceModel+referenceId = the stocked thing (Material now, Equipment later), with quantityOnHand + computed quantityAvailable; (5) InventoryMovement moves a thing between fromInventoryLocationId and toInventoryLocationId (explicit point A→point B), and the engine updates the two InventoryLevel balances; (6) referenceModel/referenceId on a movement = the thing moved (same meaning as on the level); the originating-document backlink (Shopify’s referenceDocumentUri) is left out of v1; (7) performedByUserId FKs User.

1 · Business Case & Customer Evidence ▼

Mid-market contractors carry inventory across warehouses, staging areas, and job trailers. Without tracking, they over-order (wasted capital), under-order (delayed jobs), or make truck rolls just to check stock.

2 · Scope ▼

In Scope

  • IN InventoryLocation, InventoryLevel, InventoryMovement Prisma models (Shopify-aligned shape)
  • IN InventoryLocation → required Location FK (geocoded address) + typeId PropertyValue category
  • IN Polymorphic InventoryLevel (referenceModel+referenceId) per location per thing — Material wired now, Equipment shape-ready
  • IN quantityOnHand (stored, from the ledger) + computed quantityAvailable (on-hand − open MAT-4 reservations)
  • IN Note + NoteReferences on locations and movements (threaded comments + assets)
  • IN ReferenceModel seed rows for the three new models (enables notes/tags/audit)
  • IN Receiving auto-creates inventory (from MAT-6 Supplier PO Receiving)
  • IN Job checkout with cost code assignment
  • IN Transfer between locations
  • IN Physical count adjustment
  • IN Min/max alert thresholds per item per location
  • IN Stock levels dashboard page
  • IN Location detail page
  • IN Movement history ledger
  • IN Mobile QR stock check (using UIS-15E QR pattern)

Out of Scope

  • OUT Barcode label printing
  • OUT Multi-unit-of-measure conversions
  • OUT Lot/serial number tracking
  • OUT Automated reorder PO generation
  • OUT Bin/shelf sub-locations
  • OUT Equipment stocking UI — the polymorphic shape is built now; wiring Equipment as a stocked item is a follow-up. Anticipates the coming bulk-equipment requirement (a single “angle bracket” record + a count, vs today’s one-record-per-asset): the per-location count is exactly InventoryLevel(referenceModel = "Equipment").
  • OUT Shopify’s full state set (committed/reserved/damaged/safety_stock/quality_control) — only on_hand+available in v1; the level row is structured to add the rest

4 · Data Model ▼

Shopify mapping

The shape mirrors Shopify’s inventory objects so the future PR #7394 integration is a near-direct field map:

ShopifyMAT-7Role
InventoryItem (per variant)Material / EquipmentThe catalog thing — already exists, referenced polymorphically
LocationInventoryLocation → LocationPhysical place that holds stock
InventoryLevelInventoryLevelPer-location balance (thing × location) with quantities
quantity states (on_hand/available)quantityOnHand / quantityAvailablev1 carries two of Shopify’s eight states
inventoryAdjust mutationsInventoryMovementThe change ledger (Shopify’s referenceDocumentUri audit backlink is a future add)

InventoryLocation

Its own model (not folded into Location) — Location is a shared address-book entity (Jobs, Companies, Contacts point at it) and an inventory location carries its own concerns (type, the levels relation, QR identity). It references a required Location for the address: stock is always stored somewhere, even a van has a home base. typeId is a PropertyValue category (Warehouse / Staging / Job Trailer / Vehicle) — the jobType/companyType precedent, a plain category with no Instance anchors. Notes attach via NoteReferences (no freetext column).

model InventoryLocation {
  id            String    @id @db.VarChar(21)
  isDeleted     Boolean   @default(false)
  isArchived    Boolean   @default(false)
  createdAt     DateTime  @default(now())
  updatedAt     DateTime  @default(now()) @updatedAt
  name          String    @db.VarChar(255)
  typeId        String?   @db.VarChar(21)
  Type          PropertyValue? @relation("inventoryLocationType", fields: [typeId], references: [id])
  locationId    String    @db.VarChar(21)        // required — the geocoded address
  Location      Location  @relation(fields: [locationId], references: [id])
  InventoryLevels InventoryLevel[]
  FromMovements InventoryMovement[] @relation("InventoryMovementFromLocation")
  ToMovements   InventoryMovement[] @relation("InventoryMovementToLocation")
  @@index([isDeleted])
  @@index([typeId])
  @@index([locationId])
}

InventoryLevel

The per-location balance — Shopify’s InventoryLevel. One row per (inventoryLocation, thing); the @@unique enforces it. This is how per-location stock is tracked: 2000 brackets at A, 1000 at B, 2000 at C = three rows, company total = their sum. referenceModel (FK → ReferenceModel.model) + referenceId = the stocked thing (Material now, Equipment later), mirroring the NoteReferences/TagReferences polymorphic convention. quantityOnHand is the stored running balance the InventoryMovement ledger keeps in sync; quantityAvailable is computed (= on-hand − open MAT-4 reservations against this level; equals on-hand until that link lands).

model InventoryLevel {
  id                 String    @id @db.VarChar(21)
  isDeleted          Boolean   @default(false)
  isArchived         Boolean   @default(false)
  createdAt          DateTime  @default(now())
  updatedAt          DateTime  @default(now()) @updatedAt
  inventoryLocationId String   @db.VarChar(21)
  InventoryLocation  InventoryLocation @relation(fields: [inventoryLocationId], references: [id])
  referenceModel     String        // "Material" now; "Equipment" later
  referenceId        String    @db.VarChar(21)
  ReferenceModel     ReferenceModel @relation(fields: [referenceModel], references: [model])
  quantityOnHand     Decimal   @db.Decimal(10, 2) @default(0)
  minQuantity        Decimal?  @db.Decimal(10, 2)
  maxQuantity        Decimal?  @db.Decimal(10, 2)
  unitCost           Decimal?  @db.Decimal(10, 2)   // weighted average cost at this location
  // quantityAvailable is computed at query time; sell price resolves via the LEM-3 cascade
  @@unique([inventoryLocationId, referenceModel, referenceId])
  @@index([inventoryLocationId, isDeleted])
  @@index([referenceModel, referenceId])
}

InventoryMovement

Append-only ledger line: “move quantity of thing from point A to point B.” It references the two locations directly (fromInventoryLocationId/toInventoryLocationId) and the thing (referenceModel/referenceId, same meaning as on the level); the engine updates the matching InventoryLevel balances. Receive = to only; Checkout = from only; Transfer = both (and from ≠ to); Adjustment = one (to to increase, from to decrease). Both columns are nullable — every type nulls at least one side — so the per-type requiredness, the “at least one set” guard, and quantity > 0 (direction is encoded by which side is populated, not a signed number) are enforced at the model layer, not as DB constraints. jobId/costCodeId are the checkout cost target (read by JobFinancialSummaryService). Notes attach via NoteReferences. (An optional originating-document backlink — which receipt/credit/count session produced the movement, Shopify’s referenceDocumentUri — can be added later; left out of v1.)

model InventoryMovement {
  id                   String    @id @db.VarChar(21)
  isDeleted            Boolean   @default(false)
  isArchived           Boolean   @default(false)
  createdAt            DateTime  @default(now())
  updatedAt            DateTime  @default(now()) @updatedAt
  type                 String    @db.VarChar(50)
  referenceModel       String        // the thing moved: "Material" | "Equipment"
  referenceId          String    @db.VarChar(21)
  ReferenceModel       ReferenceModel @relation(fields: [referenceModel], references: [model])
  quantity             Decimal   @db.Decimal(10, 2)
  fromInventoryLocationId String? @db.VarChar(21)
  toInventoryLocationId  String? @db.VarChar(21)
  FromLocation         InventoryLocation? @relation("InventoryMovementFromLocation", fields: [fromInventoryLocationId], references: [id])
  ToLocation           InventoryLocation? @relation("InventoryMovementToLocation", fields: [toInventoryLocationId], references: [id])
  jobId                String?   @db.VarChar(21)
  costCodeId           String?   @db.VarChar(21)
  performedByUserId    String    @db.VarChar(21)
  PerformedBy          User      @relation("InventoryMovementPerformedBy", fields: [performedByUserId], references: [id])
  @@index([referenceModel, referenceId])
  @@index([fromInventoryLocationId, isDeleted])
  @@index([toInventoryLocationId, isDeleted])
  @@index([jobId])
}

ReferenceModel + Note wiring

The migration seeds three ReferenceModel rows (InventoryLocation, InventoryLevel, InventoryMovement) so NoteReferences, TagReferences, and Audit FKs resolve. Notes are created through the existing notes system and linked via NoteReferences (referenceModel + referenceId) — giving threaded comments, assets, and subscriptions on both locations and movements for free.

Movement Type Constants

ConstantDescription
ReceiveInbound from supplier PO receiving (auto-created by MAT-6)
CheckoutOutbound to a job with cost code assignment
TransferMovement between two inventory locations
AdjustmentPhysical count correction (positive or negative)
ReturnInbound from a vendor credit return (MAT-8)

Reconciliation view

An InventoryLevelReconciliation SQL view sums InventoryMovement per (inventoryLocation, thing) — +quantity where toInventoryLocationId matches, −quantity where fromInventoryLocationId matches — and compares it to the stored InventoryLevel.quantityOnHand. The stored balance is the fast read; the ledger is the audit source of truth; the view flags any drift between them.

7 · Acceptance Criteria ▼

  • Receiving a supplier PO (MAT-6) auto-creates an InventoryMovement of type Receive and updates stock at the destination location
  • Checkout deducts quantity from the source location and creates a Checkout movement linked to a job and cost code
  • Transfer creates one movement with both fromInventoryLocationId and toInventoryLocationId set, decrementing the source InventoryLevel and incrementing the destination
  • Physical count adjustment creates an Adjustment movement (positive quantity; to set to increase, from set to decrease) and updates the level’s quantityOnHand
  • Model-layer validation enforces per-type from/to requiredness: at least one side set, both set & distinct for transfers, quantity > 0
  • Per-location stock is one InventoryLevel row per (location, thing); company-wide on-hand is the sum across rows
  • quantityAvailable resolves as on-hand minus open MAT-4 reservations (equals on-hand until that link lands)
  • Min/max alerts trigger when quantityOnHand falls below minQuantity on any InventoryLevel
  • The lowStockLevels query returns all levels below their minimum threshold with computed deficit
  • Movement ledger is append-only — movements are never edited or hard-deleted, only soft-deleted
  • Stock levels dashboard shows all locations with item counts and below-min counts
  • Location detail page shows all levels at that location with on-hand, available, min, max, and status
  • Checkout assigns cost code to the movement and is reflected in JobFinancialSummaryService
  • Mobile QR stock check allows scanning a location QR code to view stock levels (UIS-15E pattern)
  • Checkout quantity cannot exceed quantityOnHand at the source location (server-side validation)
  • Transfer quantity cannot exceed quantityOnHand at the source location (server-side validation)
  • Permission checks enforced: inventory.view, inventory.create, inventory.edit, inventory.delete
  • All movements record performedByUserId (FK → User) from the authenticated user context
  • InventoryLevel is polymorphic (referenceModel+referenceId); Material resolves today and the same shape accepts Equipment
  • Notes on locations and movements persist through Note + NoteReferences (threaded comments + assets), not a freetext column; the three models are seeded into ReferenceModel
  • InventoryLocation.typeId resolves to a PropertyValue category and locationId resolves a required Location address
  • The reconciliation view flags any drift between summed movements and the stored quantityOnHand
