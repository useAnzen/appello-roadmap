MAT-5: Supplier Purchase Orders (Implementation Plan)

Self-contained execution plan. Another agent should be able to pick this up cold, run the steps in order, and ship a PR. Paths are relative to the monorepo root (apps/api, apps/frontend). Read Pre-flight first. Companion spec: uis-MAT-5-supplier-po.html (that is the spec + decision log; this is the plan). Code blocks are drop-in starting points grounded in the named precedents on repo-2 (Release-v1.33.0 line); match surrounding style, don’t reformat neighbours.

Overview & Outcome

A “Supplier PO” is an outbound purchase order to a vendor — the inverse of today’s customer PO. MAT-5 builds it on the same PurchaseOrder table that MAT-1 converted to BaseAuditableModel, using a type discriminator. After this lands:

  • PurchaseOrder carries type (enum CustomerPO | SupplierPO, existing rows backfilled to CustomerPO), a customizable statusId → PropertyValue (per-instance, seeded Draft/Issued/Closed/Cancelled — like jobStatus/rfiStatus), and deliveryLocationId (FK→Location) / shippingMethod / expectedDeliveryDate. The supplier reuses MAT-1’s companyId / contactId columns.
  • A new PurchaseOrderLineItem child table holds catalog-or-free-text lines with a locked cost snapshot (a near-clone of WorkOrderMaterialItem).
  • One combined upsert (upsertSupplierPurchaseOrder) saves the header + syncs line items; new supplier POs get an auto SPO-####.
  • The PO renders to an HTML/Tailwind PDF through the existing pdf-export → PSPDFKit pipeline (download button), and can be sent to the supplier as a JWT download link (no attachment).
  • A dedicated supplierPurchaseOrder permission gates the new surfaces at the resolver; everything is behind the RESTRICT_MATERIAL env gate.
Decisions baked into this plan (settled with the user — see spec reconciliation note).
  • Extend MAT-1’s shared model, do not build a new one. type/status/PurchaseOrderLineItem/SPO-#### were explicitly deferred from MAT-1 to here.
  • Status is a customizable PropertyValue, not an enum (only type is an enum). Per-instance values + Instance anchor FKs drive lifecycle transitions — the rfiStatus precedent. (User decision this session.)
  • Collapsed FK: the line item references one materialAttributePriceId (the MAT-0 source row), not the deleted manufacturerProductId/distributorPriceId.
  • No emailed PDF attachments (anti-spam). Download + JWT link-to-download only, reusing the emailAction pipeline (PR #7385).
  • Dedicated supplierPurchaseOrder permission, resolver-enforced. Do NOT add PurchaseOrder to permissionsByReferenceModel (it would regress customer-PO parent-authorization).
  • Committed-cost roll-up is OUT — a separate follow-up MAT task. Received statuses are MAT-6.
  • No instanceId (single-instance app). No MAT-x identifiers in migration names or code comments.

Why Instance anchors and not workflowState. Labels are user-editable, so issueSupplier can’t look up “Issued” by name. PropertyValue.workflowState is only a coarse bucket (todo|inprogress|done|default) — too lossy to distinguish Issued from Closed. RFI solves this with per-semantic Instance FKs (rfiSentStatusId, …); we mirror it. Closed needs no anchor for MAT-5 (user-selected, or set by MAT-6 on full receipt); add one only if a code path sets it automatically.
Why mirror WorkOrderMaterialItem and not the richer MaterialOrderRecord tree. A PO line is flat (one material/variant + qty + price), exactly like WorkOrderMaterialItem — which already has the recalculateTotal hook and the proven combined-upsert sync. The 3-level MaterialOrder/Record/RecordValue tree models spec-area breakdowns we don’t need here. One difference from WorkOrderMaterialItem: no costPrice/unitPrice split — a PO line price is the buy cost, so one unitPrice.

import { IPurchaseOrderLineItem, IField } from "../types";
import prisma from "./_prismaClient";

class PurchaseOrderLineItemModel extends BaseModel<IPurchaseOrderLineItem> {
    public name = "PurchaseOrderLineItem";
    name_plural = "PurchaseOrderLineItems";
    protected prisma = prisma.purchaseOrderLineItem;

    protected modelFields: IField<IPurchaseOrderLineItem>[] = [
        { name: "purchaseOrderId", type: "string", options: { isRequiredOnCreate: true, canCreate: true } },
        { name: "materialId", type: "string", options: { canCreate: true, canEdit: true } },
        { name: "materialAttributePriceId", type: "string", options: { canCreate: true, canEdit: true } },
        { name: "description", type: "string", options: { canCreate: true, canEdit: true } },
        { name: "quantity", type: "float", options: { canCreate: true, canEdit: true } },
        { name: "unitPrice", type: "float", options: { canCreate: true, canEdit: true } },
        { name: "orderNo", type: "int", options: { canCreate: true, canEdit: true } }
        // `total` is derived — not user-writable
    ];

    protected async afterCreate(record: IPurchaseOrderLineItem) { await this.recalculateTotal(record.id); }
    protected async afterEdit(record: IPurchaseOrderLineItem) { await this.recalculateTotal(record.id); }

    public async recalculateTotal(id: string): Promise<void> {
        const item = await prisma.purchaseOrderLineItem.findUnique({ where: { id } });
        if (!item) return;
        const qty = Number(item.quantity ?? 0);
        const unit = Number(item.unitPrice ?? 0);
        await prisma.purchaseOrderLineItem.update({ where: { id }, data: { total: qty * unit } });
    }
}

export { PurchaseOrderLineItemModel };

5.2 SPO numbering (global, RFI precedent)

public async getNextSpoNumber(): Promise<string> {
    const result = await prisma.$queryRaw<[{ maxNum: bigint | null }]>`
        SELECT MAX(CAST(SUBSTRING(poNumber, 5) AS UNSIGNED)) as maxNum
        FROM PurchaseOrder
        WHERE type = 'SupplierPO'
        AND isDeleted = false
        AND poNumber REGEXP '^SPO-[0-9]+$'
    `;
    const next = Number(result[0]?.maxNum ?? 0) + 1;
    return `SPO-${String(next).padStart(4, "0")}`;
}

Global (no jobId filter) because supplier POs are company-wide procurement docs. Customer-PO numbering is untouched.

5.3 Combined upsert (header + line-item sync)

Model the sync on upsertWorkOrderLineItems (graphql/models/WorkOrderLineItems.ts:23–98): create-or-edit the header, then for line items — load existing for this PO, delete those not in the payload, create the id-less ones, edit the rest. Pre-fill unitPrice from bestAvailableCost when omitted on a catalog line. Recompute the header amount from the line totals at the end.

public async upsertSupplier(input: IUpsertSupplierPOInput, userId: string): Promise<IPurchaseOrder> {
    const { id, lineItems, jobId, ...header } = input;

    // 1) header
    const po = id
        ? await this.editItem(id, { ...header, type: "SupplierPO" }, userId)
        : await this.createItem(
              { ...header, type: "SupplierPO", statusId: header.statusId ?? await this.getDefaultPoStatusId(), poNumber: await this.getNextSpoNumber() },
              userId
          );

    // 2) optional job linkage via the existing assignment path (create only)
    if (!id && jobId) await this.assignToEntity(po.id, "Job", jobId);

    // 3) line-item sync
    const lineModel = new PurchaseOrderLineItemModel();
    const existing = await prisma.purchaseOrderLineItem.findMany({ where: { purchaseOrderId: po.id, isDeleted: false } });
    const submittedIds = new Set(lineItems.filter(l => l.id).map(l => l.id));
    for (const ex of existing) if (!submittedIds.has(ex.id)) await lineModel.deleteItem(ex.id, userId);

    for (const line of lineItems) {
        const unitPrice = line.unitPrice ?? (line.materialId ? Number(await bestAvailableCost(line.materialId) ?? 0) : 0);
        const data = { ...line, unitPrice, purchaseOrderId: po.id };
        if (line.id) await lineModel.editItem(line.id, data, userId);
        else await lineModel.createItem(data, userId);   // afterCreate → recalculateTotal
    }

    // 4) roll the line totals into the header amount
    const agg = await prisma.purchaseOrderLineItem.aggregate({
        where: { purchaseOrderId: po.id, isDeleted: false }, _sum: { total: true }
    });
    return this.editItem(po.id, { amount: Number(agg._sum.total ?? 0) }, userId);
}
MAT-9 discount on the buy side. When MAT-9 has landed, the pre-fill should be the discounted distributor cost, not the raw cost. Resolve it through the same bestAvailableCost hook (MAT-0 wires the cheapest/preferred discounted source into it — signature unchanged), so this call site does not change. Until then, bestAvailableCost returns the house cost and the user adjusts manually.

public async issueSupplier(id: string, userId: string) {

public async cancelSupplier(id: string, userId: string) {
