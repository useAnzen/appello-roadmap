Customer PO Entity

Enrich the customer purchase order — already a first-class, multi-PO, polymorphically-linked entity in the live schema — with company / contact / amount / terms metadata, a detail page that surfaces every record the PO ties to, and file attachments. Purely additive on the shipped PO system.

Parent: Release 1.33 — Material Supply Chain Slice: MAT-1 Est: 2–3 days (backend + UI)

⚠ Hardened against the live schema — read first

The original draft of this spec assumed the customer PO was still a free-text string on the Job and proposed building PurchaseOrder + PurchaseOrderLineItem from scratch. That refactor already shipped. The live schema has a working PurchaseOrder + polymorphic PurchaseOrderAssignment system that already delivers the three headline asks: first-class entity (not a string), multiple POs per job, and PO-aware invoicing.

So MAT-1 has been re-scoped from “build it” to “enrich it”: add metadata columns, a detail page, and file attachments — nothing more. Supplier-PO concepts that had leaked into the draft (a type discriminator, a status lifecycle, line items, and CPO-#### auto-numbering) are deferred to MAT-5, where they actually gain meaning. See §4 and the deferral box in §2.

1 · Business Case & Customer Evidence ▼

A customer PO is the customer’s authorization to bill: they issue you a PO number, you reference it on the estimate / change order / invoice it covers. A single job often accumulates several — one per change order. Appello already tracks these as real records, deduplicated per job and rolled up from won estimates / COs; what’s missing is a place to see a PO and the few facts that travel with it (who issued it, for how much, on what terms) plus the signed PO document itself.

“Some jobs have three POs — it’s O-1, O-2, O-3 … we can absolutely pull that into the invoice.” — Stacey Needham / Corey Shelson, Sage50 Q&A (May 2024) — action item: “add customer PO number field to invoices”
“Jobs should derive their P.O. number from the Won Estimates and Change Orders … a list of won PO Numbers that can be utilized on List Tables and Detail Pages, linking to their respective Estimate / Change Order. In invoices, include the Job PO# by default if there is only one; if more than one, ask the user to select.” — Q21030-6953, “Add PO# as a Default Property for Jobs”

All of the above already ships via PurchaseOrderModel.getAllForJob() (direct + child ECO/Bill roll-up) and the PO sync wired into estimates, change orders, and invoices. MAT-1 does not rebuild any of it.

2 · Scope ▼

IN SCOPE

  • Additive columns on the existing PurchaseOrder model: companyId, contactId, issuedDate, amount, terms, description (+ Company / Contact relations)
  • Customer PO detail page at /purchase-orders/[id] — tabs: Overview, Linked Records, Files
  • Linked Records tab reads the existing PurchaseOrderAssignment rows (Job, Estimate / CO, Invoice) — reuses the resolver’s displayLabel / referenceType
  • Files tab via Asset / AssetReference with referenceTable = "PurchaseOrder" (no schema change to attach)
  • PO tab on the Company detail page (filtered by companyId)
  • GraphQL: extend the existing PurchaseOrder type with the new fields + Files resolver; add purchaseOrder(id) and purchaseOrdersForCompany(companyId) queries; add metadata create/edit + attach/detach-file mutations
  • Model-layer methods on PurchaseOrderModel for metadata create/edit and file attach/detach (existing CRUD/sync methods untouched)
  • Route configuration for /purchase-orders/[id]

OUT OF SCOPE

  • Already shipped — not touched: the Job.purchaseOrder string → entity migration, multi-PO-per-job roll-up, the invoice / estimate / CO PO dropdowns and auto-populate behavior
  • A standalone global /purchase-orders index list (no customer demand; reach a PO via its job, the company tab, or a linked record)
  • Custom / configurable fields on POs (the DocumentAttribute system) — PO fields are few and stable; fixed columns are the right call
  • PO approval workflow, PO-to-PO linking, mobile PO management

➝ Deferred to MAT-5 (Supplier PO) — not customer-PO concepts

These appeared in the original draft but belong to the supplier PO, where you issue the document and receive against it:

  • type discriminator (CustomerPO / SupplierPO) — every PO today is implicitly a customer PO; the column does nothing until MAT-5 adds the second value (it will default existing rows → CustomerPO then).
  • Status lifecycle (Draft / Issued / Sent / PartiallyReceived / FullyReceived / Closed) — you don’t receive against a customer PO, you invoice against it. A lifecycle only matters supplier-side.
  • PurchaseOrderLineItem — a customer PO is the customer’s number; you don’t re-key their items. Line items are the things you order on a supplier PO (Ace Insulation onboarding, Jun 2025: “hit new PO and enter your own line items”).
  • Auto-numbering — a customer PO number comes from the customer (entered, as today). Minting (SPO-####) is supplier-side; MAT-5 will follow the existing RFI-## / PR-## max-plus-one precedent.

4 · Data Model ▼

Foundation — what already exists (live schema, unchanged)

The customer PO is already a first-class, polymorphically-linked entity. MAT-1 adds columns to PurchaseOrder and touches nothing else here.

model PurchaseOrder {
    id         String   @id @db.VarChar(21)
    isDeleted  Boolean  @default(false)
    isArchived Boolean  @default(false)
    createdAt  DateTime @default(now())
    updatedAt  DateTime @default(now()) @updatedAt
    poNumber   String   @db.VarChar(191)          // user-entered (the customer's number)
    PurchaseOrderAssignments PurchaseOrderAssignment[]
    @@index([poNumber])
}

// Polymorphic link: one PO → many Jobs / EstimateChangeOrderRecords / JobBills (invoices)
model PurchaseOrderAssignment {
    id              String        @id @db.VarChar(21)
    referenceModel  String        @db.VarChar(191)   // "Job" | "EstimateChangeOrderRecord" | "JobBill"
    referenceId     String        @db.VarChar(21)
    purchaseOrderId String        @db.VarChar(21)
    PurchaseOrder   PurchaseOrder @relation(fields: [purchaseOrderId], references: [id])
    @@unique([referenceModel, referenceId, purchaseOrderId])
    @@index([referenceModel, referenceId])
    @@index([purchaseOrderId])
}

The MAT-1 change — additive columns on PurchaseOrder

model PurchaseOrder {
    // ...existing fields unchanged...

    companyId   String?   @db.VarChar(21)     // NEW — the customer who issued the PO
    contactId   String?   @db.VarChar(21)     // NEW
    issuedDate  DateTime?                      // NEW
    amount      Decimal?  @db.Decimal(10, 2)   // NEW
    terms       String?   @db.Text             // NEW
    description String?   @db.Text             // NEW

    Company     Company?  @relation(fields: [companyId], references: [id])   // NEW
    Contact     Contact?  @relation(fields: [contactId], references: [id])   // NEW

    @@index([companyId])                       // NEW
}

No instanceId (Appello is single-instance). No type / status / line items / auto-numbering — all deferred to MAT-5. The reciprocal PurchaseOrders relation arrays are added to Company and Contact.

Files — reuse Asset / AssetReference (no schema change)

The existing polymorphic file join attaches any asset to any record via a plain string table name — the same shape as PurchaseOrderAssignment. Attaching the signed PO PDF is one AssetReference row:

// existing model — no change needed
model AssetReference {
    id             String @id @db.VarChar(21)
    assetId        String @db.VarChar(21)
    referenceTable String @db.VarChar(255)   // = "PurchaseOrder"
    referenceId    String @db.VarChar(21)    // = purchaseOrder.id
    // ...
    @@unique([assetId, referenceTable, referenceId])
    @@index([referenceTable, referenceId])
}

Migration

Additive columns only — CreateTable is not needed (the tables exist), and the Job.purchaseOrder string → entity data migration already shipped. No data backfill. (When MAT-5 adds type, that migration will default existing rows to CustomerPO.)

5 · API Surface ▼

GraphQL SDL — extends the existing PurchaseOrder type

type PurchaseOrder {
    id: ID!
    poNumber: String!
    isArchived: Boolean
    createdAt: DateTime
    updatedAt: DateTime
    # --- NEW (MAT-1) ---
    companyId: String
    Company: Company
    contactId: String
    Contact: Contact
    issuedDate: DateTime
    amount: Float
    terms: String
    description: String
    Files: [Asset!]                          # resolved from AssetReference
    PurchaseOrderAssignments: [PurchaseOrderAssignment]   # Linked Records (existing)
}

# PurchaseOrderAssignment already exposes displayLabel + referenceType
# (used directly by the Linked Records tab — no new type needed)

input CustomerPurchaseOrderInput {
    poNumber: String!
    companyId: String
    contactId: String
    jobId: String            # optional — assigns the PO to a Job on create
    issuedDate: DateTime
    amount: Float
    terms: String
    description: String
}

extend type Query {
    purchaseOrder(id: ID!): PurchaseOrder
    purchaseOrdersForCompany(companyId: ID!): [PurchaseOrder]
    # existing, unchanged: purchaseOrdersForJob(jobId), checkForPoForEntity(...)
}

extend type Mutation {
    createCustomerPurchaseOrder(input: CustomerPurchaseOrderInput!): PurchaseOrder!
    editCustomerPurchaseOrder(id: ID!, input: CustomerPurchaseOrderInput!): PurchaseOrder!
    attachFileToPurchaseOrder(purchaseOrderId: ID!, assetId: ID!): Asset!
    detachFileFromPurchaseOrder(purchaseOrderId: ID!, assetId: ID!): Boolean!
}

Model layer — additions to PurchaseOrderModel

Existing methods (getAllForJob, findOrCreateForJob, assignExistingPOToEntity, handleCreatePOSync / handleEditPOSync, …) are untouched. New methods:

MethodPurpose
getById(id)PO + assignments + attached assets for the detail page
createWithMetadata(input)Create PO with metadata; if jobId given, assign to the Job via the existing assignment path
editMetadata(id, input)Update the new metadata columns + poNumber
getForCompany(companyId)POs filtered by companyId for the Company PO tab
attachFile / detachFile(id, assetId)Manage AssetReference rows (referenceTable = "PurchaseOrder")

Computed / resolved fields

PurchaseOrder.Files resolves AssetReference rows where referenceTable = "PurchaseOrder" and referenceId = po.id. The Linked Records tab reuses PurchaseOrderAssignments with its existing displayLabel / referenceType resolvers — no new query.

7 · Acceptance Criteria ▼

  • PurchaseOrder gains companyId, contactId, issuedDate, amount, terms, description + Company / Contact relations — additive migration, no data backfill
  • PO detail page at /purchase-orders/[id] with Overview, Linked Records, and Files tabs
  • Linked Records tab lists every Job / Estimate / CO / Invoice the PO is assigned to, read from PurchaseOrderAssignment
  • Files tab uploads / lists / removes attachments via Asset / AssetReference (referenceTable = "PurchaseOrder")
  • Company detail page shows a Purchase Orders tab filtered by companyId
  • poNumber remains user-entered (no auto-numbering); poNumber required on create
  • No regression: existing multi-PO roll-up, invoice / estimate / CO PO dropdowns, and auto-populate behavior are unchanged
  • Permission: users need appropriate permission to view / create / edit POs and attach files
  • No type, status, line items, or auto-numbering introduced (all deferred to MAT-5)
