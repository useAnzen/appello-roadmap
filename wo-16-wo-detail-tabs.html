WO-16 Work Orders P1 - 1.33 Draft

WO Detail Tabs · Schedule + Equipment Assignment

Two new tabs on the WO detail page, both port-existing-Jobs-UI registrations (same pattern as WO-13). The Schedule tab mounts the existing Calendar Schedule scoped to this Job. The Equipment Assignment surface ports the existing Job-side UI 1:1. Pure tab port — no new components. The Planned Crew advisory sidebar that originally lived in this spec has moved to WO-15c, since it's template-driven and naturally pairs with the apply UI.

Estimate: 1-2 days Sequence: 1.33, independent Requires: WO-1 Enables: WO-15c (which mounts the advisory into this Schedule tab)

1. Business Case

Two pieces of UI that already work on regular Jobs need to be enabled on Work Orders. Same architectural shape as WO-13 for forms — the data layer already supports it (a WO is a Job), the components already exist, what's missing is the gate that hides them when jobClassification = WorkOrder.

Equipment Assignment on WOs unblocks WO-15c: the template apply step creates EquipmentAssignment rows from user-resolved equipment plans, and users need somewhere to view + manage those rows after the WO is saved. Without this surface, applied equipment is invisible on the WO.

The Schedule tab is more than a port — it adds a small advisory sidebar that consumes WorkOrderTemplateLaborPlan rows from the WO's applied template (when one exists) so the dispatcher sees "you need 2 × Apprentice × 4hrs" alongside the calendar where they actually drag users to schedule them. This closes the loop on WO-15c's create-form Planned Crew callout, which explicitly points users here.

2. Scope

Already Built

  • DONE Existing Job-side Schedule tab + Calendar Schedule UI — components, queries, mutations, drag-to-schedule
  • DONE Existing Job-side Equipment Assignment UI — list, create, edit, check-in / check-out (EquipmentAssignment already supports checkoutJobId per schema.prisma:1947)
  • DONE WO-1 classification routing — gate logic already discriminates WO from project job
  • DONE WO-3 detail page scaffolding — host for the new tabs

In Scope (WO-16)

  • IN Register the existing Schedule tab on the WO detail page (desktop) — same component, same data, no new code
  • IN Register the existing Equipment Assignment surface on the WO detail page (desktop) — same component, same data, no new code
  • IN Register the existing Equipment surface on the mobile WO detail page (WODetail.tsx) using the existing JobEquipment component (jobId prop already supported)
  • IN Identical behavior to Jobs for all three surfaces — same permissions, same workflows

Out of Scope

  • OUT Schema changes — none required
  • OUT Planned Crew advisory sidebar — moved to WO-15c. The advisory is template-driven, so it ships in the same spec as the apply UI; this spec just stands up the host Schedule tab.
  • OUT Mobile Schedule tab — desktop-only in V1 (matches existing Job-side scope)
  • OUT Mobile Equipment Assignment edit/check-in/check-out flows — V1 mobile is read-list only via JobEquipment
  • FUTURE Schedule tab redesign / optimization — V1 reuses the existing component as-is

3. UI Concepts

Interfaces being added to WOs

  • Desktop WO Detail · Schedule tab (existing Calendar Schedule, full-width)
  • Desktop WO Detail · Equipment Assignment surface (existing Job-side UI, no changes)
  • Mobile WO Detail · Equipment tab (existing JobEquipment component)
Pure tab port — no new components. Each surface is registered on the WO detail page using the same component already used on the Job detail page. The Planned Crew advisory sidebar that previously belonged to this spec has moved to WO-15c; it remains a 2-column variant of the Schedule tab that mounts only when a template is applied, but it ships with the apply UI rather than with the host tab.

4. Data Model

No schema changes. EquipmentAssignment.checkoutJobId already supports linking to any Job (a WO is a Job). JobSchedule already keys off jobId.

5. API Surface

No new GraphQL types, queries, or mutations. Both surfaces consume existing API:
  • Equipment Assignment — same queries / mutations the Job-side UI uses today
  • Schedule tab calendar — same as Job's Schedule page
  • Mobile Equipment tab — existing JobEquipment defaultWhere keys off the jobId prop

7. Acceptance Criteria

  1. Opening a WO on desktop shows a Schedule tab and an Equipment Assignment surface in the same positions and styling as their Job detail equivalents.
  2. The Schedule tab loads the existing Calendar Schedule scoped to this Job (same component, same data path).
  3. The Equipment Assignment surface lists existing EquipmentAssignment rows on this Job using the same component as the Job-side surface.
  4. Creating, editing, and checking equipment in/out from the WO Equipment Assignment surface uses existing mutations; no WO-specific code path.
  5. Opening a WO on mobile shows an Equipment tab using JobEquipment, scoped to assignedToJob = woId.
  6. Existing Job-side Schedule and Equipment Assignment surfaces remain unchanged — same component code path, no regressions.
  7. Mobile job-sites Equipment tab remains unchanged (no edits to the donor component).
