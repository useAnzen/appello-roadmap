Forms on Work Orders

Surface the existing job-forms UI on Work Orders. Pure UI work — no schema changes, no new GraphQL surface. Reuse the same components and screens that jobs already use; remove the gate that hides forms on WOs.

Estimate: 0.5-1 day Sequence: 1.33 — independent, can ship anytime Requires: WO-1 Enables: Template form-defaults (lives with WO-14)

1. Business Case

From the May 5, 2026 product calls (Emma + Corey): forms are currently hidden on Work Orders. Service workflows expect forms to surface on each WO — generator inspections, equipment checklists, refrigerant logs, customer sign-offs. The platform already supports assigning FormWrappers to a Job (JobSafetyFormWrapper) and capturing submissions (JobSafetyForm); a WO is a Job (WO-1), so the data layer already works.

This spec is the smallest possible step: turn the existing job-forms UI on for WOs, on both desktop and mobile, with zero behavior changes. Per-WO defaults driven by WO Templates are explicitly out of scope here and live with the Templates spec (WO-14).

Direct quote from the call: "Open forms up on work orders, possibly with a different UI where you don't have like the whole library and stuff. It's like these are things that are assigned to it." Translation in this spec: same UI as jobs, no special trimming yet. If a trimmed surface is needed we'll add it as a follow-up after real users react.
Clarification vs Corey's WOX-06: "Assigned-only UI" in this spec means only the forms attached to this WO are shown, not the entire form library — i.e., the WO surface is scoped to its own form attachments. It does not mean "filter by the user assigned to the visit on mobile" (which is the additional feature WOX-06 proposed: a per-user-assignment filter so each tech only sees their forms in the mobile inbox). That filter is out of scope here and would ship as a future spec if/when techs report mobile inbox clutter as a pain point. Our V1 = WO surface shows all forms attached to the WO, identical to how jobs show all forms attached to the job.

2. Scope

Already Built

  • DONE JobSafetyFormWrapper — assignment record linking a FormWrapper to a Job (schema.prisma:2355)
  • DONE JobSafetyForm — submission record per assigned form (schema.prisma:2333)
  • DONE Job detail Forms tab (desktop) — assignment picker, list of assigned forms, status, submission history
  • DONE Job detail Forms surface (mobile) — list of assigned forms, fill flow, submission UI
  • DONE All GraphQL queries / mutations for assigning, removing, and submitting forms against a Job
  • DONE WO-as-Job classification routing (WO-1) — feature gating already discriminates classification

In Scope (WO-13)

  • IN Render the existing Forms tab on the WO detail page (desktop) — same component, same data, gated open for jobClassification = WorkOrder
  • IN Render the existing Forms surface on the WO detail page (mobile) — same component, same data, gated open
  • IN Identical behavior to jobs: assign FormWrapper, fill form, view submissions, remove assignment

Out of Scope

  • OUT Any new schema changes — none required
  • OUT Any new GraphQL queries / mutations — existing job-form surface covers this
  • OUT Trimmed / WO-specific forms UI — V1 reuses the job UI as-is
  • FUTURE Default forms per WO template — lives with the WO Templates spec (WO-14)
  • FUTURE Conditional / role-gated form assignment
  • FUTURE WO-specific Forms list UI redesign (driven by user feedback once V1 ships)

3. UI Concepts

No new components or layouts. Each surface below already exists on the Job side and will function and look identical on the WO — only the gate that currently hides them when jobClassification = WorkOrder is removed.

Interfaces being added to WOs

  • Desktop WO Form Submissions
  • Desktop WO Settings with Form Settings
  • Mobile Forms tab
  • Mobile Form Submission History tab

4. Data Model

No schema changes. JobSafetyFormWrapper and JobSafetyForm already key off jobId. A WO is a Job (WO-1), so all existing form data flows work unchanged.

5. API Surface

No new queries or mutations. The existing job-form GraphQL surface (connect_form_to_jobs, disconnect_form_from_jobs, form-submission mutations, job-forms query) operates on Jobs and works for WOs without changes. Frontend uses the same hooks.

6. Change Surface

7. Acceptance Criteria

  1. Opening a WO on desktop shows a Forms tab in the same position and styling as the Job Forms tab.
  2. Opening a WO on mobile shows a Forms surface identical to the Job Forms surface.
  3. Adding a form to a WO writes a JobSafetyFormWrapper row using the existing mutation; no WO-specific code path.
  4. Filling out a form on a WO writes a JobSafetyForm submission using the existing mutation.
  5. Removing an assigned form from a WO soft-deletes the JobSafetyFormWrapper using the existing mutation.
  6. Submission history, attachments, signatures, and PDF rendering on a WO behave identically to a Job.
  7. No regressions on the Job Forms tab — same component code path.
  8. Existing form permissions (view, fill, sign) apply on WOs without modification.
