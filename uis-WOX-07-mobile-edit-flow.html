Mobile EDIT Flow — Step-by-Step Reuse

Today the mobile WO EDIT flow is one giant scrolling form. Restructure it to use the same step-by-step wizard pattern as the CREATE flow (uis-20h-1) so a tech editing on-site doesn't lose context. Same 5 steps, pre-populated with the existing WO's values, identical save behaviour.

Status: Concept Effort: +2d on WO-8 Extends: uis-20h-1 · WO-8 Master ref: #23

1. Where this lives in the app

Page / route: apps/mobile/src/pages/work-orders/[id]/edit.tsx (path TBD — to be created during WO-8 mobile build; mirrors the CREATE flow location)

API surface: GraphQL — workOrder(id) query for prefill, editWorkOrder(id, input) partial-save mutation per step

The CREATE wizard introduced in uis-20h-1-stepped-form-wizard.html already exists in spec. This UIS reuses the same shell components (StepHeader, StepBody, StepFooterNav, ProgressDots) and only changes the data plumbing: pre-populate from the existing WO, and route saves through editWorkOrder instead of createWorkOrder. No new design language, no new patterns — purely an information-architecture fix.

3. Key decisions for Emma + Corey to discuss

D1 Should EDIT skip steps where nothing changed?
Recommended: No — explicit confirm-and-continue per step preserves the wizard mental model. Skipping breaks parity with CREATE and creates inconsistent muscle memory. The Review step (5) carries the diff burden, so the cost of paging through unchanged steps is one tap per step.
D2 Destructive edits (e.g. removing a line item with logged time) — block or warn?
Recommended: Warn with audit trail; allow only for users with workOrder.editLineItems permission. Hard-blocking in the field creates support tickets; a yellow inline warning ("Sarah K logged 4 hrs against this line — removing will detach those entries") plus a confirm chip is the right balance.
D3 Keep the "Save & exit" button on every step or only at the end?
Recommended: Every step — partial saves are OK. Field connectivity is unreliable; persisting per-step state lets a tech bail out of step 3 with a saved PO# from step 1 already committed. Implementation: each step's "Next" call doubles as a save.
D4 Mirror desktop EDIT to use the same wizard?
Recommended: Yes — post-V1, file as a separate UIS. The mental-model parity argument applies equally to dispatchers. But desktop has more screen real estate, so a "tab-style" wizard (steps shown as tabs) may be preferable to mobile's "page-style" wizard. Defer to 1.34.
D5 Do we show the Review step's diff against the last-saved WO or against the original WO version?
Recommended: Last-saved. The diff serves as a "what am I about to commit" sanity check, not a full version history. Full version history belongs on the WO Audit tab (separate UIS).
