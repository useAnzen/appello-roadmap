WO-14 Work Orders P1 - 1.33 Draft

Simple Checklist on Work Orders

A first-class procedural checklist on every Work Order — items + a done checkbox + an optional rich description, with who-checked-it and when. Configuration lives on the WO Settings tab; ticking and quick-add are surfaced everywhere the user works (Overview, Create/Edit form, Mobile detail). Templates that pre-populate items will ship with WO-15.

Estimate: 3-4 days Sequence: 1.33, before WO-15 (Templates) Requires: WO-1, WO-3, WO-3d Enables: WO-15 (Templates pre-fill checklist items)

1. Business Case

Service work orders are repeatable, procedural work — show up, do these eight things, get a sign-off. From the May 5, 2026 product calls: techs and dispatchers want a simple list of steps on every WO they can tick through. Forms (WO-13) handle structured data capture, but they are heavyweight for "did you do step 3 yet?" — a checkbox is the right primitive.

Real-world checklist items are bimodal: most are short ("Go to location"), some need context ("Replace VC-7 valve — torque spec 45 ft-lbs, see manual §4.2"). Each item carries an optional rich-text description, collapsed by default in lists, that pays for itself the first time a tech avoids calling the office. Tracking who ticked an item and when is included from day one because audit is cheap to add now and expensive to retrofit. Per-template default items (so an HVAC inspection always seeds the same 12 steps) ship with the Templates spec (WO-15).

"What if a work order checklist is basic? It's just got a name and it's got a done. Just a checkbox to do or done. That's all we give them. We restrict it. The work order checklist is just a list of things in an order and a to-do and done." — Corey Shelson, 2026-05-05 product call

2. Scope

Already Built

  • DONE WO-as-Job classification routing (WO-1) — feature gating discriminates classification
  • DONE WO create / edit / detail page scaffolding (WO-3, WO-4)
  • DONE WO Property Settings tab on the WO detail page (WO-3d) — host for the configuration surface
  • DONE Existing TipTap-based WYSIWYG editor — reused for rich descriptions

In Scope (WO-14)

  • IN New WorkOrderChecklistItem model with jobId, label, description (sanitized HTML, optional), orderNo, createdByUserId, isDone, completedByUserId, completedAt, photoRequired (Boolean), completionPhotoAssetId (FK to Asset, optional)
  • IN When photoRequired = true, ticking the item requires capturing a photo; the resolver rejects the tick if no photoAssetId is supplied. Untick clears the photo reference along with the audit fields. Locked-down minimum behavior — no captions, no multiple photos, no annotations.
  • IN Computed % complete on the WO — derived field (count of isDone=true non-archived items) / (count of all non-archived items). Surfaced on the WO detail page header (desktop) as a small progress indicator (e.g., "4 of 12 complete · 33%"). Not stored; recomputed on read.
  • IN Direct CRUD GraphQL mutations for the Settings + Overview surfaces
  • IN Atomic embed of checklist diff (upsert, archive) in createJob / editJob payloads — quick-add on the Create/Edit form persists with the form save, not as a separate request
  • IN Tick / untick mutation that auto-records the acting user + timestamp from auth context — always live, regardless of which surface the user is on
  • IN Desktop · WO Settings tab — full management: add, edit, drag-and-drop reorder, rich description editor (TipTap), archive (only when not ticked), restore archived
  • IN Desktop · WO Overview / detail surface — read, tick, quick-add (label only), archive (only when not ticked), expand/collapse description
  • IN Desktop · WO Create / Edit form — read, tick (live), quick-add (label only) and archive participate in the form save
  • IN Mobile · WO Detail — read, tick, expand/collapse description (read-only)
  • IN Mobile · WO Create / Edit form — read, tick. No add or archive on mobile in V1
  • IN Permissions: any user with WO edit access can add/check items (V1 — no fine-grained checklist permissions)

Out of Scope

  • OUT Deletion / archive of ticked items on any surface — audit invariant. To remove a ticked item the user must first untick it (which clears the audit fields), then archive.
  • OUT Items pre-populated from a template — lives with WO-15; this spec keeps the data model open to it (template-load resolver writes WorkOrderChecklistItem rows on WO creation)
  • OUT Add / archive of items on mobile — read-and-tick only in V1; revisit if field demand surfaces
  • OUT Rich description editing on mobile — view (expand/collapse) only; rich editing requires desktop
  • OUT Assigning checklist items to specific users / groups / roles
  • OUT Multi-day re-runs (one-and-done per WO, confirmed in product call)
  • OUT Checklist items with sub-fields, captions, multiple photos, annotations, or numeric values. The single-photo photoRequired flag (see In Scope) is intentionally minimal; richer workflows belong in Forms (WO-13).
  • OUT Checklist as a gating mechanism for WO status transitions
  • OUT Checklist propagation on WO → Invoice / CO conversion — checklist stays attached to the originating WO only
  • FUTURE Reporting on checklist completion rates per WO type

3. UI Concepts

Placement model

The checklist is exposed on five surfaces, each with a deliberate operation set. Configuration (heavy editing, rich descriptions, restore) lives on the WO Settings tab; ticking and lightweight add/archive are surfaced wherever the user is already working.

Surface Read Tick Quick-add (label) Edit / rich desc / reorder Archive (unticked) Restore
Desktop · Settings tab

Desktop · Overview tab ✓ ✓ (live) ✓ (live) — (Settings) ✓ (live) —
Desktop · Create / Edit form ✓ ✓ (live) ✓ (form save) — (Settings) ✓ (form save) —
Mobile · WO Detail ✓ ✓ (live) — — — —
Mobile · Create / Edit form ✓ ✓ (live) — — — —
Why ticking is always live — the audit invariant requires that "checked by Bob at 2:47 PM" is the wall-clock truth, not a timestamp from a later form save. Tick/untick fires setWorkOrderChecklistItemDone immediately on every surface, including from inside the Create/Edit form.
Why quick-add on Create/Edit form is part of the form save — on Create there is no jobId yet, so items must be drafted client-side and submitted with the job. On Edit, batching item add/archive into the same save keeps the transaction atomic with the rest of the form's edits and avoids partial-failure states.

4. Data Model

4.1 New model: WorkOrderChecklistItem

model WorkOrderChecklistItem {
  id          String   @id @db.VarChar(21)
  isDeleted   Boolean  @default(false)
  isArchived  Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @default(now()) @updatedAt

  jobId       String   @db.VarChar(21)
  Job         Job      @relation(fields: [jobId], references: [id], onDelete: Cascade)

  label       String   @db.VarChar(500)
  description String?  @db.Text                  // sanitized HTML from TipTap; null when no rich body
  orderNo     Int      @default(0)

  createdByUserId    String?   @db.VarChar(21)
  CreatedByUser      User?     @relation("WorkOrderChecklistItemsCreated",
                                          fields: [createdByUserId],
                                          references: [id],
                                          onDelete: SetNull)

  isDone             Boolean   @default(false)
  completedByUserId  String?   @db.VarChar(21)
  CompletedByUser    User?     @relation("WorkOrderChecklistItemsCompleted",
                                          fields: [completedByUserId],
                                          references: [id],
                                          onDelete: SetNull)
  completedAt        DateTime?

  // When true, ticking this item requires at least one photo. The resolver
  // rejects setWorkOrderChecklistItemDone(isDone: true) unless at least
  // one photoAssetId is supplied. Photos themselves are joined via the
  // existing polymorphic AssetReference table (referenceTable =
  // "WorkOrderChecklistItem", referenceId = this item's id) — no FK
  // column on this model.
  photoRequired      Boolean   @default(false)

  @@index([jobId, isDeleted, isArchived, orderNo], map: "WOChecklistItem_job_order_idx")
  @@index([createdByUserId], map: "WOChecklistItem_createdBy_idx")
  @@index([completedByUserId], map: "WOChecklistItem_completedBy_idx")
}

CREATE TABLE `WorkOrderChecklistItem` (
    `id`                 VARCHAR(21)   NOT NULL,
    `isDeleted`          BOOLEAN       NOT NULL DEFAULT FALSE,
    `isArchived`         BOOLEAN       NOT NULL DEFAULT FALSE,
    `createdAt`          DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    `updatedAt`          DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    `jobId`              VARCHAR(21)   NOT NULL,
    `label`              VARCHAR(500)  NOT NULL,
    `description`        TEXT          NULL,
    `orderNo`            INT           NOT NULL DEFAULT 0,
    `createdByUserId`        VARCHAR(21)   NULL,
    `isDone`                 BOOLEAN       NOT NULL DEFAULT FALSE,
    `completedByUserId`      VARCHAR(21)   NULL,
    `completedAt`            DATETIME(3)   NULL,
    `photoRequired`          BOOLEAN       NOT NULL DEFAULT FALSE,
    PRIMARY KEY (`id`),
    INDEX `WOChecklistItem_job_order_idx` (`jobId`, `isDeleted`, `isArchived`, `orderNo`),
    INDEX `WOChecklistItem_createdBy_idx` (`createdByUserId`),
    INDEX `WOChecklistItem_completedBy_idx` (`completedByUserId`),
    CONSTRAINT `WOChecklistItem_jobId_fkey`
        FOREIGN KEY (`jobId`) REFERENCES `Job`(`id`) ON DELETE CASCADE,
    CONSTRAINT `WOChecklistItem_createdBy_fkey`
        FOREIGN KEY (`createdByUserId`) REFERENCES `User`(`id`) ON DELETE SET NULL,
    CONSTRAINT `WOChecklistItem_completedBy_fkey`
        FOREIGN KEY (`completedByUserId`) REFERENCES `User`(`id`) ON DELETE SET NULL
);

-- Photos are joined via the existing AssetReference table:
-- AssetReference (assetId, referenceTable = 'WorkOrderChecklistItem',
--                 referenceId = checklistItem.id)
-- No new tables, no schema changes for the photo relationship.
Description storage: sanitized HTML in TEXT, written by the existing TipTap editor on save. Sanitization (allow links, basic formatting; strip scripts and embedded media) runs server-side in the model's beforeEdit / beforeCreate hooks.
Why model is named WorkOrderChecklistItem not JobChecklistItem: the feature is intentionally WO-specific — checklists are not surfaced on project jobs (per Out of Scope). Naming after the conceptual home keeps the codebase honest. The FK is to Job only because WO is a Job; the model is filtered to WO classification at the GraphQL layer.

  orderNo: Int!
  createdByUserId: String

  # referenceId = this item's id). Empty array when the item is unticked

  completionPhotos: [Asset!]!

extend type Job {
  workOrderChecklistItems(includeArchived: Boolean = false): [WorkOrderChecklistItem!]!
  # Computed % complete — count of (isDone=true AND isArchived=false) divided
  # by count of all non-archived items. 0–100 integer; null when no items
  # exist. Not stored; recomputed on read. Surfaced on the WO detail page
  # header on desktop.
  workOrderChecklistProgress: WorkOrderChecklistProgress
}

type WorkOrderChecklistProgress {
  doneCount: Int!
  totalCount: Int!
  percentComplete: Int           # null when totalCount = 0; otherwise 0..100
}

5.2 Live mutations (Settings + Overview surfaces, and ticks everywhere)

# Records createdByUserId from auth context server-side — not client-supplied.
createWorkOrderChecklistItem(
  jobId: String!,
  label: String!,
  description: String,
  orderNo: Int,              # optional — defaults to (max + 1) if omitted
  photoRequired: Boolean     # optional — defaults to false

editWorkOrderChecklistItem(
  id: String!,
  label: String,
  description: String,
  orderNo: Int,
  photoRequired: Boolean

# Always live, on every surface, including from inside the Create/Edit form.
# Records completedByUserId from auth context and completedAt = now() server-side.
# When the target item has photoRequired=true and isDone=true is requested,
# photoAssetIds must be a non-empty array; the resolver rejects ticks
# without at least one photo. The resolver creates AssetReference rows

  jobId: String!,
  orderedIds: [String!]!

# Archive is rejected by the resolver if the target item has isDone = true.
archiveWorkOrderChecklistItem(id: String!): WorkOrderChecklistItem!
restoreWorkOrderChecklistItem(id: String!): WorkOrderChecklistItem!

5.3 Form-save embed (Create/Edit form on desktop, no separate request)

# createJob and editJob accept an optional checklist diff. The resolver
# applies upserts and archives in the same transaction as the rest of the
# job edits. Ticks are NOT included here — they always go through
# setWorkOrderChecklistItemDone live.

input WorkOrderChecklistItemDraftInput {
  id: String                  # null = create new; present = update existing
  label: String!
  description: String
  orderNo: Int
}

input WorkOrderChecklistDiffInput {
  upsert: [WorkOrderChecklistItemDraftInput!]
  archiveIds: [String!]       # rejected per-id if item.isDone = true
}

extend input CreateJobInput {
  checklistItems: WorkOrderChecklistDiffInput
}

extend input EditJobInput {
  checklistItems: WorkOrderChecklistDiffInput
}
Why a dedicated setWorkOrderChecklistItemDone mutation: server-side recording of completedByUserId and completedAt from auth context — not client-supplied — is a correctness invariant. Ticks fire live regardless of which surface the user is on, so the audit timestamp is the moment of the tick, never the moment of an unrelated form save.
Why the form-save embed is upsert-based, not full replace: a full-replace payload would race with live ticks happening in another tab or on mobile. Upserting by ID with explicit archive IDs is conflict-free with concurrent setWorkOrderChecklistItemDone calls.

7. Acceptance Criteria

  1. A user can add a checklist item to a WO from Settings (live), Overview (live), and the Create/Edit form (commits with the form save).
  2. A user can edit an existing item's label and rich description from the Settings tab; description editing is unavailable on Overview, Create/Edit form, and any mobile surface.
  3. A user can drag-and-drop reorder items from the Settings tab; the new order persists via orderNo.
  4. Ticking an item — from any surface, including the Create/Edit form — fires setWorkOrderChecklistItemDone immediately and records the current user and timestamp.
  5. Unticking an item clears completedByUserId and completedAt.
  6. Ticked items cannot be archived from any surface — the archive control is hidden or visibly disabled, and the API rejects the call with a clear error.
  7. Quick-add and archive on the Create/Edit form are queued in form state and persist in the same transaction as the rest of the form's save; cancelling the form discards them.
  8. Description content is sanitized server-side (links, basic formatting allowed; scripts and embedded media stripped).
  9. The checklist UI displays "Checked by <User> · <Date>" beneath any ticked item; if the user is later deleted the caption shows the date only.
  10. Restoring an archived item is available only on the Settings tab.
  11. Deleting a WO cascade-deletes its checklist items.
  12. The Checklist surface is gated to jobClassification = WorkOrder — it does not appear on project jobs or any non-WO classification.
  13. Description rendering in lists is collapsed by default; expanding one item does not affect others.
  14. photoRequired is settable on every item from the Settings tab; defaults to false. Items not marked photo-required can be ticked normally.
  15. Ticking a photoRequired item without supplying at least one photoAssetId is rejected by the resolver. The mobile UX prompts the camera on tick; the desktop UX prompts a file picker. Both allow attaching multiple photos in a single tick.
  16. Photos attach via the existing AssetReference polymorphic join (referenceTable = "WorkOrderChecklistItem", referenceId = checklistItem.id) — no FK column on WorkOrderChecklistItem; no new tables.
  17. Unticking a photoRequired item deletes all AssetReference rows for this checklistItem alongside clearing completedByUserId and completedAt.
  18. Photo-required behavior is intentionally locked down on metadata: no captions, no annotations, no per-photo descriptions. Multiple photos per item are allowed (the AssetReference pattern naturally supports it). Richer photo workflows belong in Forms (WO-13).
  19. A ticked photoRequired item displays inline thumbnails of all captured photos on every read surface (Settings, Overview, Create/Edit form, Mobile detail, Mobile create/edit). Tapping a thumbnail opens a lightbox with prev/next when multiple photos exist.
  20. Items with photoRequired = true but isDone = false show a small camera glyph next to the checkbox so the user knows a photo will be required at tick time.
  21. The WO detail page header (desktop) displays a computed % complete derived from workOrderChecklistProgress: "X of Y complete · Z%". Hidden when the WO has zero non-archived checklist items.
  22. The data model accepts items written by an external caller (the future template-load resolver in WO-15) without modification.
