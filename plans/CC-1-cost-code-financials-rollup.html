CC-1 · Cost-Code Financials Rollup + Financial Summary Breakdown

Rival is the first cost-code pilot. Brad and Kate spotted the gap mid-setup: CostCode rolls up to an AccountItem, and TradeLevel also rolls up to an AccountItem. If both fire on the same timesheet entry, the same labour cost lands in the Financial Summary twice. The Financial Summary also has no cost-code-level breakdown — once you turn cost codes on, the granularity disappears at the financial roll-up. This doc lays out what to do about both, with concrete file paths and a phased plan.

Jira: Q21030-11808 Driver: Rival (Brad Viers, Kate Hallett, Josh Jankowiak) Related: Rival cost-codes pilot, Foundation payroll import Status: Pre-decision / pre-build Target: v1.33

The scenario

Rival is the first customer wiring up cost codes. Brad built the schedule of values for two pilot jobs manually so he could see how the codes flow. Kate walked through how it'd land in Foundation. Mid-conversation Corey caught what was hiding under it.

Two things came out of that conversation that this doc is answering:

  1. The rollup question. Both CostCode and TradeLevel have an accountItemId. Do they both feed the Financial Summary actuals, and if so does that double-count? (Investigation + guardrail.)
  2. The breakdown question. Once cost codes are in use, customers want to see cost-code-level totals nested under each AccountItem row in the Financial Summary — same numbers, finer slice. (UI work.)

Brad's framing later in the same call:

Brad · May 27 · 20:48 I would, if we're always going to put in labor, if I haven't done a setup in two months, I'm going to go in there and form and bam, bam, right? That's the whole spirit of Phase 1: don't give the form the opportunity to produce data that double-counts. The breakdown UI (Phase 2) only works if Phase 1's guardrail is in place — otherwise the cost-code subtotals under an AccountItem row will not reconcile with the AccountItem total.

What's already true (load-bearing givens)

1. The Financial Summary feed is a SQL view, not a service

Where: apps/api/prisma/views/Z_FinancialSummaryFeed.sql — the FinancialSummaryFeed MySQL view is the single source of truth for everything you see in the per-AccountItem Financial Summary grid (estimate, actual, expenses, wages, hours, equipment cost). The GraphQL resolver (financialSummaryFeed) is a thin SELECT * FROM FinancialSummaryFeed WHERE ….
Implication: changes to how labour rolls up to AccountItem happen in this SQL file. There is no application-layer transform to hook into. Update the view, run pnpm run prisma:updateViews — no migration needed.

2. Labour wages today roll up via TradeLevel → AccountItem — that's the only path

The TimesheetHoursAndWages CTE inside Z_FinancialSummaryFeed.sql:

TimesheetHoursAndWages AS (
    SELECT tsdr.jobId, ai.id AS accountItemId,
           SUM(tsdrv.approvedDuration) AS hoursAsSeconds,
           CAST(SUM((tsdrv.approvedDuration / 3600) * tlr.baseValue) AS DECIMAL(10,2)) AS wages
    FROM TimeSheetDetailRecordValue tsdrv
    LEFT JOIN TimeSheetDetailRecord tsdr ON tsdr.id = tsdrv.timeSheetDetailRecordId
    LEFT JOIN TimeSheetRecord tsr ON tsr.id = tsdr.timeSheetRecordId
    LEFT JOIN TradeLevelRate tlr ON tlr.id = tsdrv.tradeLevelRateId
    LEFT JOIN TradeLevel tl ON tl.id = tlr.tradeLevelId
    LEFT JOIN AccountItem ai ON ai.id = tl.accountItemId
    WHERE tsr.status = 'Approved' AND tsdr.isDeleted = false
    GROUP BY tsdr.jobId, ai.id
)

So today, a Foreman's 8 hrs hit one row: AccountItem = Foreman.accountItem, wages = 8 × baseValue. Nothing about cost codes is in this rollup. If you toggle cost codes on and code that same 8 hrs to 2105 Pipe Direct Labor, the Financial Summary view sees no change at all — TDRVCC is not joined.

3. Cost codes already map to an AccountItem

Where: apps/api/prisma/schema.prisma — CostCode.accountItemId (line 4393).
CostCode is also tied to an AccountCategory (e.g. "Direct Labour"). The cost-code template UI already enforces an AccountItem mapping per code.

4. Cost codes attach to TDRV via the TimeSheetDetailRecordCostCode junction

Where: apps/api/prisma/schema.prisma — TimeSheetDetailRecordCostCode (line 4098).
A single TDRV can have multiple cost codes, each with its own approvedDuration. The split is enforced to sum to the parent TDRV's duration. The job-level summary service (JobFinancialSummaryService) already aggregates labour cost via this junction — but only for its own consumer (the monthly forecast vs actual dashboard), not for the per-AccountItem feed.

5. The mobile form has a "require cost codes" instance setting

Where: apps/mobile/src/components/Forms/TimesheetAddEditForm/TimesheetCostCodeStep.tsx · requireCostCodeOnMobileTimesheet.
When the instance setting is on and the job has direct-labour cost codes, a user can't submit time without allocating every hour to a cost code. Emma confirmed this in the May 27 meeting at the 50:00 mark. Desktop has no such gate yet.

6. The current cost-code picker is filtered only by job + AccountCategory

Where: apps/frontend/src/graphql/queries/costCodes.query.graphql · GetLabourCostCodesByJob.
Filter is jobId = $jobId AND AccountCategory.slug = "direct-labour". Nothing restricts to the user's trade level. A Foreman sees every direct-labour cost code on the job — including ones that map to an AccountItem the Foreman's trade level doesn't map to.

The double-count risk — worked example

Take Rival's pilot job. Foreman trade level maps to AccountItem = Labour — Direct. Cost code 2105 Pipe Direct Labor also maps to AccountItem = Labour — Direct (per the meeting decision: "all labor into this 106 bucket").

Brad's foreman logs 8 hours at $52/hr, allocating all 8 hours to cost code 2105:

Today
FinancialSummaryFeed labour rollup: TimesheetHoursAndWages CTE only.
Labour — Direct row: $416 wages, 8 hrs. Correct.
Cost code is invisible to the Financial Summary.
⚠ Naïve add
If we add a parallel CostCode → AccountItem rollup CTE (via TDRVCC) alongside the existing TradeLevel → AccountItem one, both feed the same AccountItem row.
Labour — Direct row: $832 wages, 16 hrs. Double-counted.
Goal
Labour — Direct row: $416 wages, 8 hrs, broken down as: ↳ 2105 Pipe Direct Labor — $416, 8 hrs. AccountItem total = sum of cost-code rows under it. Numbers reconcile.

The ticket's investigation question — does it double-count today? No. The Financial Summary view currently has only the TradeLevel path. The double-count is a latent risk that becomes real the moment Phase 2 is added without Phase 1 in place. But there's a related current problem worth knowing about:

The cross-AccountItem drift problem (already possible today). Nothing stops Brad's foreman from coding their 8 hours to a cost code that maps to AccountItem = Subcontractor Labour. The view still uses the Foreman trade level for the rollup, so the wages still land in Labour — Direct. But when we add the cost-code breakdown, that Subcontractor Labour AccountItem will have zero wages on it and a ghost cost-code line showing 8 hrs — because the AccountItem total comes from one source and the breakdown from another. The reconciliation contract is broken before we even ship. This is the actual reason Phase 1's filter matters — not "today's double-count," but "guarantee the two rollup paths always pick the same AccountItem so they can be unified into one source."

★ Top Option — One CTE, two grouping keys

Don't run two rollups and dedupe. Run a single TDRV aggregation that emits one row per (jobId, accountItemId, costCodeId) with the cost code allowed to be NULL (for un-coded hours). The Financial Summary feed sums it to AccountItem; the breakdown reads the same rows grouped by cost code under each AccountItem. Same query, same numbers, no reconciliation step.

How the data flows under this model

  • AccountItem comes from the cost code if there is one, otherwise from the trade level. Picking AccountItem off the cost code (when present) means cost-coded time always lands under the AccountItem its cost code maps to — even if it differs from the trade level's. Un-coded time still rolls into the trade-level's AccountItem like it does today, preserving the existing flow for non-cost-coded customers.
  • Phase 1's guardrail eliminates the divergence at the source. The cost-code picker on timesheet entry forms filters to codes whose accountItemId matches the user's trade level's accountItemId. So cost-code.accountItem and tradeLevel.accountItem always agree — the "AccountItem comes from the cost code" rule is just a tiebreaker that already aligns.
  • The breakdown is a free output of the same query. The CTE groups by (jobId, accountItemId, costCodeId). The existing Financial Summary feed groups it up to (jobId, accountItemId) — sums match by construction. A new jobCostCodeBreakdown query reads the same rows pre-rollup.
  • Un-coded hours show up as an "Unallocated" line. Under each AccountItem row, in addition to the cost-code subtotals, there's a row for costCodeId IS NULL. This is the "didn't bother / cost codes not required on this job" bucket. It is a normal expected line, not an error state.

Why this beats run-two-paths-and-dedupe

  • There is no possible reconciliation drift: the total and the breakdown come from the same SELECT.
  • No "subtract path B from path A" code anywhere — that kind of dedupe always rots when one consumer changes.
  • Future cost-code-aware reports (Brad's "monthly cost report" pivot) read the same rows pre-rollup. One source, many views — the rule the meeting already settled on.

Invariants the system enforces

  • I1. Cost-code AccountItem must match trade-level AccountItem at time of TDRV save (enforced on the form + backend validation).
  • I2. The Financial Summary feed labour rollup reads from one CTE only. No new CTE that joins via the cost-code path independently.
  • I3. Existing flow (no cost codes anywhere on the job) continues to produce identical numbers — the new CTE collapses to the current behaviour when tsdrvcc rows don't exist.

Cons / tradeoffs

  • If a customer changes a cost code's accountItemId mapping later, historical Financial Summary numbers shift — same as today for any rollup-mapping change.
  • Phase 1's filter is a small extra step in the timesheet picker (cost codes narrow as the user's trade level is known). Trade-off: the picker is shorter, so for some scenarios it's actually faster.
  • Adds an additional LEFT JOIN on TimeSheetDetailRecordCostCode in the FS view; existing perf budget should absorb it (the view is rebuilt on the same nightly cadence as today).

Phase 1Investigation + guardrail: filter cost codes by AccountItem

What changes

  1. Backend filter on the cost-code picker query. GetLabourCostCodesByJob currently filters by jobId + AccountCategory.slug = "direct-labour". Add a third filter: CostCode.accountItemId = userTradeLevel.accountItemId. Resolve the user's trade level on the API side from the user's active TradeLevelRate + the date of the timesheet entry, so this works for users with multiple trade levels.
  2. Backend validation on save. When a TDRV with a cost code is created/updated, validate that costCode.accountItemId === tradeLevelRate.tradeLevel.accountItemId. Reject with a clear error otherwise. This is the actual integrity gate — the form-level filter is UX, the validation is the contract.
  3. Desktop bulk-entry picker already at apps/frontend/src/components/BulkEntry/BulkEntryCostCodeSelect.tsx — same filter applied.
  4. Mobile picker at apps/mobile/src/components/Forms/TimesheetAddEditForm/TimesheetCostCodeStep.tsx — same filter applied. Already permission-gated by requireCostCodeOnMobileTimesheet; just need the narrower list.

Resolving the user's trade level for the picker

A user has exactly one active trade level on any given date — no union, no disambiguation step needed. The TSDR record itself, however, can carry an overrideTradeLevelId (already on the model, wired on desktop, surfaced on mobile separately under the Q21030-11722 work). The filter uses that override when present, otherwise falls back to the user's default trade level for the date:

effectiveTradeLevelId =
    TSDR.overrideTradeLevelId
    ?? user.activeTradeLevelOn(TSDR.workDate)

allowedAccountItemId = TradeLevel[effectiveTradeLevelId].accountItemId

// Picker shows: cost codes WHERE accountItemId = allowedAccountItemId

Cost-code allocations within a TSDR all share the same effective trade level — there's no way to split a single TSDR across two trade levels — so a single AccountItem-scoped picker is correct for the whole TSDR's worth of allocations.

Edge cases the design must handle

  • Trade level has no accountItemId set. Treat as "show all direct-labour cost codes." Log a warning; the customer needs to fix the mapping. Don't block the user.
  • Cost code has no accountItemId set. Hide from the picker. (Same logic — incomplete config; flag in setup.)
  • Customer doesn't use cost codes at all. Picker is not shown — current behaviour unchanged.
  • TSDR's overrideTradeLevelId changes after cost codes are already allocated. Existing allocations may now violate the filter. Re-validate on save: surface the conflict so the user can clear and re-allocate, rather than silently dropping rows.

Migration / backfill

No data migration. The filter is read-side only. Existing TDRVCC rows with mismatched AccountItems remain (we don't fix history); the Phase 2 view query handles them by treating the cost-code's AccountItem as the source of truth — anything historical that drifted gets resolved into its own breakdown row.

Phase 2Financial Summary cost-code breakdown

SQL view change

Replace TimesheetHoursAndWages with a new TimesheetHoursAndWagesWithCostCode CTE that joins through TimeSheetDetailRecordCostCode with a LEFT JOIN (so un-coded hours still appear, with costCodeId = NULL). It emits:

TimesheetHoursAndWagesWithCostCode AS (
    SELECT tsdr.jobId,
           COALESCE(cc.accountItemId, tl.accountItemId) AS accountItemId,
           tsdrvcc.costCodeId AS costCodeId,         -- NULL for un-coded
           SUM(COALESCE(tsdrvcc.approvedDuration, tsdrv.approvedDuration)) AS hoursAsSeconds,
           CAST(SUM(
               (COALESCE(tsdrvcc.approvedDuration, tsdrv.approvedDuration) / 3600)
               * tlr.baseValue
           ) AS DECIMAL(10,2)) AS wages
    FROM TimeSheetDetailRecordValue tsdrv
    LEFT JOIN TimeSheetDetailRecord tsdr ON tsdr.id = tsdrv.timeSheetDetailRecordId
    LEFT JOIN TimeSheetRecord tsr ON tsr.id = tsdr.timeSheetRecordId
    LEFT JOIN TradeLevelRate tlr ON tlr.id = tsdrv.tradeLevelRateId
    LEFT JOIN TradeLevel tl ON tl.id = tlr.tradeLevelId
    LEFT JOIN TimeSheetDetailRecordCostCode tsdrvcc
        ON tsdrvcc.timeSheetDetailRecordValueId = tsdrv.id
        AND tsdrvcc.isDeleted = false
        AND tsdrvcc.approvedDuration > 0
    LEFT JOIN CostCode cc ON cc.id = tsdrvcc.costCodeId
    WHERE tsr.status = 'Approved' AND tsdr.isDeleted = false
    GROUP BY tsdr.jobId, COALESCE(cc.accountItemId, tl.accountItemId), tsdrvcc.costCodeId
)

The existing Financial Summary feed view aggregates this further to (jobId, accountItemId) — that's the rollup. A new query reads it grouped by (jobId, accountItemId, costCodeId) — that's the breakdown. Same rows.

New GraphQL query for the breakdown

Where: add jobCostCodeLabourBreakdown(jobId: ID!): [CostCodeLabourBreakdownRow] to apps/api/src/graphql/models/FinancialSummary.ts (or a new resolver file JobCostCodeBreakdown.ts). Model method on apps/api/src/models/FinancialSummary.ts.
Returns one row per (accountItemId, costCodeId | null) with the same hoursAsSeconds / wages shape the FS feed uses, so the frontend can sum-check trivially.

The main Financial Summary table renders one row per AccountItem. Under that row, when the job has cost codes, the row is expandable — opening it reveals one row per cost code that contributed, plus an "Unallocated" row for un-coded time. The same "AccountItem total = sum of cost-code rows" contract holds — but for expenses, an "Unallocated" row covers expenses coded only to the Job (referenceModel = 'Job') and not to a cost code.

Alternatives considered

A · Two parallel rollups + subtraction dedupe
Med lift High risk

Keep the existing TradeLevel → AccountItem rollup. Add a new CostCode → AccountItem rollup. On the final SELECT, subtract cost-coded hours from the trade-level path so each row's hours are only counted once.

Why we didn't pick it: the subtraction is brittle. If anything ever creates TDRVCC rows that don't sum to the parent TDRV's approvedDuration (partial allocation), the subtraction produces nonsense. Also: two SELECTs is two places to update when anything changes. The Top Option's single-CTE approach makes the math impossible to get wrong.

B · CostCode is the only source; drop TradeLevel→AccountItem rollup entirely
High lift Breaks non-cost-code customers

Strip the TradeLevel.accountItemId link entirely. Every TDRV must have a cost code; Financial Summary actuals come from CostCode.accountItemId only.

Why we didn't pick it: most existing customers don't use cost codes. Removing the trade-level rollup breaks their Financial Summary. Even Rival's pilot has the option of un-cost-coded time during transition. The Top Option preserves the trade-level fallback for the no-cost-code case via COALESCE.

C · Don't add the breakdown — surface cost codes only in the Monthly Cost Report
Low lift Punts

Leave Financial Summary alone. Direct customers wanting cost-code-level analysis to the Monthly Cost Report (which already aggregates by cost code via JobFinancialSummaryService).

Why we didn't pick it: Brad and Kate were already in the Financial Summary asking this question during setup. The Monthly Cost Report is a separate report; users analyzing a job's actuals expect to see them in one place. Also doesn't address the latent double-count risk if anyone does wire up a cost-code CTE later — the structural problem remains.

D · Validate-only Phase 1; ship breakdown later
Low lift Leaves UI gap

Implement the cost-code AccountItem filter + save-time validation now, without the Financial Summary breakdown UI. Brad and Kate's Rival pilot can then run safely; the breakdown is a follow-up release.

Why this is a viable fallback: if the breakdown UI work doesn't fit the release window, Phase 1 alone is independently useful — it stops the cross-AccountItem drift problem and is the prerequisite for Phase 2. Brad already gets the data integrity guarantee; the visualization comes later. This is essentially "ship Phase 1 in v1.33, Phase 2 in v1.34."

Open questions for business review

Q1. Cross-AccountItem cost-coding — strict block or warning?

If Brad's foreman tries to code their time to 3005 Subcontractor (which maps to a different AccountItem), should we block it or warn? Strict block keeps Financial Summary clean; warning gives the field user a way out.

Why ask: blocks force users to ask their PM for a code that exists. Warnings get ignored. Either is defensible — but it has to be one or the other consistently across desktop + mobile.

Q2. Should "Unallocated (no cost code)" show on jobs that require cost codes?

On a job where the instance setting + cost codes are both on, every hour must be allocated — so the row would be 0. Still render the row for visual consistency, or hide it?

Why ask: cosmetics matter when this is for business review. Showing a constant zero row clutters the UI; hiding it makes the table shape depend on data. Default proposal: hide when zero.

Q3. Change orders — do change-order cost codes get their own grouping in the breakdown?

The May 27 meeting flagged this separately: change-order cost codes (3xxx series at Rival) need to be visually distinguishable from base-contract codes. Do we group them as a sub-section under each AccountItem? Or just sort with a label?

Why ask: the change-order schedule-of-values is its own design (see related Jira). For now this doc treats CO cost codes as ordinary cost codes; we can layer the CO grouping in once that design lands.

Q4. Historical TDRVCC rows that violate the new constraint

Pre-fix, nothing stopped a foreman from coding time to a cost code whose AccountItem differs from their trade level's. There may be a handful of these on Rival's pilot already. Do we backfill / fix them, leave them as drift, or surface them in a separate "needs review" lane?

Why ask: the Top Option's COALESCE(cc.accountItemId, tl.accountItemId) makes the cost-code's AccountItem win — historical drift gets resolved silently. That's probably fine for Rival's small pilot but worth confirming before we ship to other customers.

Q5. Should the desktop timesheet also enforce cost codes (like the mobile setting)?

From Emma in the May 27 meeting: "I believe on desktop, it's still like you can submit time how you submit time normally." Most data entry happens on mobile, but office staff editing timesheets desktop-side currently bypass the requirement. Do we extend requireCostCodeOnMobileTimesheet to desktop?

Why ask: not strictly part of this ticket, but Brad's "don't give me the opportunity to screw up" framing makes it relevant. Easy follow-up.

Q6. Phasing decision — ship Phase 1 alone in v1.33, Phase 2 in v1.34?

Phase 1 is the integrity gate; Phase 2 is the UI. Phase 1 has no user-visible UI change other than a shorter picker list and a save-time error. Phase 2 is mostly frontend work + one SQL view change. Could be a clean two-release split.

Why ask: lets Rival pilot run safely on v1.33 with no double-count risk while the breakdown UI is iterated on. Corey already mentioned the Rival rollout target is v1.33 in the meeting.

Recommended path forward

  1. Approve the Top Option direction — single CTE keyed by (jobId, accountItemId, costCodeId) with COALESCE(cc.accountItemId, tl.accountItemId) as the AccountItem source. This is the architectural commitment.
  2. Phase 1 in v1.33: picker filter + save-time validation, on both desktop and mobile. Rival pilot ships on this. No FS view change yet.
  3. Phase 2 in v1.34: swap the TimesheetHoursAndWages CTE for the cost-code-aware version + add the breakdown UI to the Financial Summary report. Same swap for expenses.
  4. Q1–Q6 above get answered by Corey / Brad / Kate before Phase 1 starts. They're cheap to resolve and the answers shape implementation choices.
Bottom line: Brad and Corey were right that "this entire system needs to continue running, even if you don't use cost codes." The Top Option preserves that: with no cost codes, the new CTE collapses to the old one. With cost codes, you get a richer breakdown for free, with no double-count possible by construction.
