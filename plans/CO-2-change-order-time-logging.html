CO-2 · Schedule users to a Change Order + filter mobile cost codes

Once a job has won change orders with their own cost-code SOVs (CO-1), field workers logging time on mobile need to know which SOV their hours roll into. Today the mobile cost-code picker shows every direct-labour code on the job — no separation between base and CO. This doc proposes a small modal that fires when scheduling a user to a job with cost-coded COs ("base, or which CO?"), persists the choice on the schedule record, and uses it to filter the mobile picker. The actual logged-against value lands on a new nullable changeOrderId on TimeSheetDetailRecord (the job-scoped record — alongside its existing jobId), so the field can still override case-by-case.

Jira: Q21030-11812 Depends on: CO-1 · Q21030-11809 Related: CC-1 · Q21030-11808 Status: Pre-decision / pre-build Target: v1.33+ (after CO-1)

The scenario

Source — Q21030-11812 Jira + Rival cost-codes pilot (May 27)

With cost codes on change orders (CO-1), field workers logging time on mobile need to know which cost codes belong to the main contract versus a specific change order. The cleanest way to handle this is at scheduling time: a project manager or scheduler indicates on the desktop that a user is working the base contract or a specific change order, and the mobile cost-code dropdown filters accordingly.

Without this gating, two things go wrong:

  1. Field workers see CO codes they shouldn't. A foreman assigned to base-contract work for the day sees the entire 60-line cost-code list (base + every CO) and has to know which 5 codes are theirs. Brad's framing from the May 27 meeting: "don't give me the opportunity to screw up because I'm going to screw up."
  2. CO-coded hours land on the wrong SOV's actuals. Once CO-1 ships, hours coded to a CO's 3001 code roll up into that CO's progress. Mis-coded hours show up in the wrong invoice. The data-model fix is good; the UX gating prevents the mistake.

What's already true (load-bearing givens)

1. Cost codes will carry changeOrderId after CO-1 ships

Where: CO-1 Phase 1 adds CostCode.changeOrderId (nullable). NULL = base contract; a value points at a won EstimateChangeOrderRecord. This doc depends on that field existing.
Implication: CO-2 cannot ship without CO-1. Plan accordingly.

2. Today's cost-code picker filters on jobId + AccountCategory only

Where: apps/frontend/src/graphql/queries/costCodes.query.graphql · GetLabourCostCodesByJob (line 131).
Filter: jobId = $jobId AND AccountCategory.slug = "direct-labour". Adding a changeOrderId filter is straightforward — same query, one more clause.

3. JobSchedule exists but doesn't carry per-user assignments today

Where: apps/api/prisma/schema.prisma:4116 — JobSchedule has jobId, supervisorId, date/time, calendarViewId, workerCount, title/description — but no user FK. Users are scheduled onto jobs through an adjacent layer (the calendar UI in JobScheduleCalendarAddEditForm.tsx calls assignWorker(jobIds, userId, ...)).
Implication: there isn't a clean per-user-per-job-per-date record to hang the CO assignment on. We need either (a) a new model or (b) to extend whatever layer wires users to schedules. See "Where the assignment lives" below.

4. TimeSheetDetailRecord is the job-scoped record; TSDRV is the rate/hours leaf

Where: apps/api/prisma/schema.prisma:4039 — TimeSheetDetailRecord (TSDR). Has jobId + optional overrideTradeLevelId; unique on (timeSheetRecordId, jobId, overrideTradeLevelId).
apps/api/prisma/schema.prisma:4075 — TimeSheetDetailRecordValue (TSDRV). Sits beneath TSDR; one TSDRV per tradeLevelRateId, holds approvedDuration + the rate link. Cost codes attach via TSDRVCC under each TSDRV.
Implication: "this time is on a change order" is a TSDR-level fact — it scopes the whole job assignment for that work-day. The new nullable changeOrderId lives on TSDR, alongside jobId. All TSDRVs (and their TSDRVCCs) under that TSDR inherit the scope.

5. Mobile cost-code step already exists and is permission-gated

Where: apps/mobile/src/components/Forms/TimesheetAddEditForm/TimesheetCostCodeStep.tsx. Step in the timesheet add/edit wizard. Already conditionally rendered based on requireCostCodeOnMobileTimesheet + presence of direct-labour cost codes on the job.
Implication: the place to apply the CO filter is here. No new step needed; just narrow the existing list.

6. EstimateChangeOrderRecord already has the "won" status

Same as CO-1: only Won + includeInJobValue = true COs are eligible. COs in Pending / Lost / Draft are not surfaced in the scheduling modal — they're not active work.

★ Top Option — Schedule-time modal + TSDR.changeOrderId + mobile filter

Three small changes, one cohesive flow.

  1. Schema: add nullable changeOrderId to TimeSheetDetailRecord (the job-scoped record, alongside jobId). Also add it to whichever layer carries the per-user schedule assignment (see "Where the assignment lives" — proposed: extend the existing user-schedule join with a nullable changeOrderId).
  2. Desktop modal at scheduling time: when a user is being scheduled to a job that has at least one won CO with cost-code lines, pop a small modal: "Base contract or which CO?" The selection persists on the schedule assignment.
  3. Mobile picker: when the user opens their timesheet for that job-date, the cost-code step reads the assignment's changeOrderId and filters the picker to that scope. The user can switch (out-of-band) if needed, but the default is locked to the scheduled scope.

How the data flows

Scheduler
PM schedules Bob to Job 01-02 for Tuesday. Job has CO-001 (Won) with cost-code SOV → modal fires. PM picks "CO-001". Choice saved on the user's schedule assignment.
Bob's phone
Tuesday morning, Bob opens the job on mobile to log time. Cost-code step queries with changeOrderId = co-001-id → picker shows only the 2 codes under CO-001's SOV.
TSDR save
When Bob's TSDR is created/saved for the day, changeOrderId on the TSDR is set from the schedule assignment by default. All TSDRVs under it inherit the scope; TSDRVCC rows reference the (now filtered-to-CO) cost codes.
Rollup
CO-1's SOV actuals see Bob's 8 hrs land under 3002 CO-001 Direct Labor. Base contract is undisturbed. Progress invoice for CO-001 picks up the new actuals next time it runs.
Why TSDR (not TSDRV). TimeSheetDetailRecord is the job-scoped record (carries jobId) — one TSDR per (timesheet, job, optional trade-level override). TimeSheetDetailRecordValue sits beneath the TSDR and holds the rate × hours for a given TradeLevelRate. "Which CO is this work on?" is a property of the user's job assignment for the day, not of the rate line — so it belongs on TSDR alongside jobId and overrideTradeLevelId. Every TSDRV under the TSDR shares the same CO scope.

Tap context pill to switch to base contract codes

Context pill at the top shows the active scope. Tap to open a chooser identical to the desktop modal — lets the field worker override the scheduled scope when a day actually does straddle base + CO work (e.g. they were on base in the morning, did a CO punch-list item after lunch).

Invariants the system enforces

  • I1. A TSDR's changeOrderId, when set, must reference a CO on the same jobId as the TSDR. Validated on save.
  • I2. Every TSDRVCC (cost-code allocation) reachable through TSDRVs under a TSDR must reference a cost code whose changeOrderId matches the parent TSDR's changeOrderId (both NULL = base contract is also valid). Validated on save.
  • I3. The schedule-time modal only fires when the target job has ≥ 1 Won CO with at least one cost code attached. Plain old jobs with no cost-coded COs see no behavior change.
  • I4. The mobile context pill is always present whenever the user has a schedule assignment with a CO scope — even when the user is logging time outside the wizard (e.g. quick-log).

Cons / tradeoffs

  • One more modal at scheduling time on jobs with cost-coded COs. For schedulers running bulk operations across many users, this adds a few clicks. Mitigation: the modal supports a "Apply to all selected users" checkbox.
  • If a field worker actually does split a day between base and CO work, they have to toggle the context pill mid-timesheet. Acceptable: it's still 1-tap, and the data model (per-TSDRV changeOrderId) supports it cleanly.
  • Mobile cost-code list shortens — which is a feature, but feels like "missing options" to users not yet familiar with the new flow. Mitigate with the visible context pill that explains why.

Where the assignment lives — open architectural question

Today, JobSchedule is a job-date-level record (one per job per day, with a supervisor and a workerCount). The actual per-user assignment to a scheduled day appears to flow through the calendar UI's assignWorker(jobIds, userId, ...) function, which likely writes to either an undiscovered model or a join that we haven't located in this exploration.

Action required before implementation: trace the assignWorker path in JobScheduleCalendarAddEditForm.tsx + SelectedUsersToSchedule.tsx to identify the model that records "User X is scheduled to Job Y on Date Z." That model gets the new nullable changeOrderId. If no such model exists yet, this work has a small data-modeling dependency that should be resolved up-front.

Three possible homes for the per-user CO assignment

Home A · On the existing user-schedule join (whichever it is) Likely best

Add a nullable changeOrderId column to the join record. The schedule modal writes the value when the user is assigned. The mobile picker reads it via a query keyed on (userId, jobId, workDate).

Why: the assignment is intrinsically per (user, job, date); the join is the natural carrier. No new table.

Home B · A new JobScheduleUserCOAssignment model
More plumbing

Separate model keyed by (userId, jobId, workDate, changeOrderId). Survives JobSchedule deletes; can carry future per-assignment metadata.

Why not (default): over-engineered if Home A is viable. Worth it only if the user-schedule join is too rigid to extend.

Home C · On TimeSheetRecord itself (per-day per-user)
Wrong layer

Add changeOrderId directly to TimeSheetRecord as the per-user-per-day source. The schedule modal writes it on TSR create.

Why not: couples scheduling intent to a record that may not exist yet (TSRs are created when the user opens the timesheet, not when they're scheduled). The schedule's "intent" needs to exist before the TSR. Also, TSR is already busy with status / approval workflow concerns — keep scheduling intent separate.

Recommendation: proceed with Home A once we've identified the user-schedule join. If for some reason it doesn't exist (and assignment is purely transient on the calendar), use Home B. Skip Home C.

Phase 1Schema + mobile picker filter (no scheduling UI yet)

Schema migration

model TimeSheetDetailRecord {
    // ... existing fields (jobId, overrideTradeLevelId, etc.)
    changeOrderId String?                    @db.VarChar(21)
    ChangeOrder   EstimateChangeOrderRecord? @relation(fields: [changeOrderId], references: [id])
}

Sits naturally alongside jobId and overrideTradeLevelId — all three are facts about this user's work on this job for this timesheet. Plus the per-user-schedule join model (Home A above) gets a matching nullable changeOrderId once that model is identified.

Mobile picker filter

Extend GetLabourCostCodesByJob (or add a sibling query) to accept an optional changeOrderId filter argument. The mobile cost-code step reads the user's schedule assignment for the (jobId, workDate) — if a CO scope is set, pass it through; otherwise pass NULL (base contract).

query GetLabourCostCodesByJob($jobId: String!, $changeOrderId: String) {
    costCodes(options: {
        where: {
            filter: {
                logic: "AND"
                filters: [
                    { fieldName: "jobId", fieldOperation: "equals", value: $jobId }
                    {
                        tableName: "AccountCategory"
                        fieldName: "slug"
                        fieldOperation: "equals"
                        value: "direct-labour"
                    }
                    # NEW:
                    { fieldName: "changeOrderId", fieldOperation: "equals", value: $changeOrderId }
                ]
            }
        }
    }) { ... }
}

Save-time validation

When a TSDR (or any of its children) is created or updated:

  • If TSDR has changeOrderId set, every TSDRVCC under the TSDR's TSDRVs must reference a cost code whose changeOrderId matches.
  • If TSDR has changeOrderId = NULL, every TSDRVCC must reference a cost code with changeOrderId = NULL.
  • Reject with a clear error otherwise. (Same shape as CC-1's save-time validation pattern.)

Mobile context pill

Always render a small context pill at the top of the mobile cost-code step (and on the timesheet summary screen) showing the current scope. Tapping it opens a bottom-sheet identical to the desktop scheduling modal — lets the field worker switch scope for the current TSDR if they actually did mixed work that day.

Phase 1 ships functionality for jobs that already have CO assignments coming through some other means (initial pilot can use admin direct-write to set them). Phase 2 ships the desktop scheduling modal so the assignments get set in the normal flow.

Phase 2Desktop scheduling modal

Where it fires

In apps/frontend/src/components/Forms/JobScheduleCalendarAddEditForm/JobScheduleCalendarAddEditForm.tsx at the point where users are assigned (the assignWorker call path). Before assignWorker fires for a job that has won cost-coded COs, present the modal.

Modal behavior

  • Trigger condition: target job has ≥ 1 won CO with at least one cost code (changeOrderId on a cost code). Otherwise skip the modal entirely.
  • Default selection: "Base contract" pre-selected.
  • "Apply to all" support: when scheduling multiple users in a batch, the modal supports an "Apply to all selected users" checkbox so the PM doesn't have to click through each one.
  • Edit later: existing scheduled users on a job get an edit affordance — clicking a user's name on the calendar shows their current CO scope and lets the PM switch it.
  • COs without SOV set up: a "Needs setup" pill renders next to the CO label. Selecting that CO is allowed but warns the PM that the cost-code picker will be empty until the SOV is configured.

Alternatives considered

A · No modal; mobile picker shows all codes, field worker chooses scope
Low lift Defeats the purpose

Skip the scheduling modal entirely. Mobile picker shows everything, organized by base/CO group. Field worker picks the right group themselves.

Why we didn't pick it: Brad's "don't give me the opportunity to screw up" comment is the entire reason this ticket exists. Forcing the field to pick the scope reintroduces the mistake we're trying to prevent.

B · Put changeOrderId on TSDRV instead of TSDR
Same lift Wrong granularity

Add the field one layer down — on each TSDRV (rate × hours leaf) rather than on the TSDR (job-scoped parent).

Why we didn't pick it: TSDR is the layer that already carries jobId + overrideTradeLevelId for the same user-day-job context. CO scope is the same kind of fact — it scopes the whole assignment for that day's work on that job, not per rate line. Putting it on TSDRV would allow different TSDRVs under one TSDR to have different CO scopes, which is incoherent (the user can't be on base contract for some rate lines and on a CO for other rate lines within a single job-day). TSDR-level matches the actual semantics.

B′ · Put changeOrderId on TSDRVCC (per cost-code allocation)
Redundant

Instead of a single CO scope on TSDR, mark each cost-code allocation under each TSDRV with its own changeOrderId.

Why we didn't pick it: TSDRVCC's costCode already carries changeOrderId via CO-1. Adding a redundant field on TSDRVCC creates two sources of truth and offers no granularity gain. The TSDR-level field is the picker-scope default; the cost code is the actual integrity bearer via I2.

C · Scope per work-order (use the WO subsystem instead of scheduling)
Cross-cutting Not all customers use WOs

Pair each CO with a work order; assign users to WOs; mobile picker filters via the WO.

Why we didn't pick it: requires the customer to use Work Orders, which not everyone does. The Rival pilot is direct-job-coding; making WOs a prerequisite would block them. Schedule-time assignment is the lowest common denominator.

Open questions for business review

Q1. Field worker override — soft (one TSDR) or sticky (rest of the day)?

If a field worker switches scope mid-day via the context pill, does the switch apply only to the current TSDR being edited, or does it stick for the rest of the timesheet entries that day?

Why ask: sticky reduces taps but might surprise the worker if they go back to base in the afternoon. Default proposal: per-TSDR (not sticky) — they tap the pill each time they switch, which is rare in practice.

Q2. PM permission to set CO scope — anyone who can schedule, or a narrower role?

Anyone who can assign a user to a job can pick the CO scope today (by default). Is that the right gating, or should it be restricted to a more specific permission (e.g. "manage cost code allocation")?

Why ask: scheduling and cost-coding are sometimes done by different people in larger orgs. A narrower permission gate would prevent a scheduler from inadvertently mis-categorizing CO hours.

Q3. What happens if a CO scope is set, then the CO is reverted from Won → Pending?

Existing TSDRV / TSDRVCC rows referencing the CO are still valid (audit trail). But the schedule modal would no longer list that CO in fresh assignments. Show a warning when this happens, or silently re-default to base?

Why ask: status changes on COs are rare but non-zero. Need to make sure the design doesn't strand assignments.

Q4. Multi-day scheduling — one modal, or per-day?

If a PM schedules a user across a week to the same job, does the modal fire once (and apply to all days) or once per day?

Why ask: once-and-done is cleaner UX but locks the user into one scope for the whole stretch. Most jobs don't switch scope mid-week, so this is probably the right default.

Q5. Should the desktop timesheet also enforce the CO scope?

Same flavour as CC-1's Q5. When office staff edit timesheets desktop-side, today they can pick any cost code on the job. Should the desktop picker also apply the CO filter when a schedule assignment exists?

Why ask: consistency with mobile. If yes, the desktop timesheet editor needs the same filter logic. If no, the mobile gate is the only one and office overrides are the escape hatch — that's defensible too.

Q6. Where the assignment lives (Home A vs Home B) — confirm during implementation kickoff

See the "Where the assignment lives" section. The data model dependency is small but real; need to trace assignWorker in the calendar form before sizing Phase 1 confidently.

Why ask: 2-hour spike to confirm, but it shifts the scope of the migration.

Recommended path forward

  1. Ship CO-1 first. This doc depends on CostCode.changeOrderId existing.
  2. Resolve Q6 up-front (where the per-user-per-day CO assignment lives). 2-hour spike traces assignWorker in the calendar form.
  3. Phase 1 (schema + mobile filter + validation): ship the data field on TSDRV and the user-schedule join, the mobile picker filter, the context pill, and save-time validation. Pilot customers (Rival) can set assignments via admin direct-write while Phase 2 is being built.
  4. Phase 2 (desktop scheduling modal): ship the modal so assignments flow naturally through the calendar UI. "Apply to all selected users" + inline-edit on already-scheduled users.
  5. Q1–Q5 get answered in the same review session as CO-1's Q1–Q6.
Bottom line: Schedule-time modal sets the default; nullable changeOrderId on TSDR (the job-scoped record) is the source of truth at log time; mobile picker filters by it. Field worker keeps a one-tap escape hatch via the context pill. Save-time validation (TSDR's CO matches every TSDRVCC cost code's CO) is the integrity contract that ties it all back to CO-1's data model.
