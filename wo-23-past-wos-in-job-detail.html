1. Business Case

In the existing forms-based "WO" workflow, every form submission is attached to a Job via JobSafetyForm.jobId — so when a customer (Thermogenics, etc.) opens a Job they see all the form-submission-style WOs that have ever been done on it. When 1.33 ships real WOs, that visibility breaks unless WOs can declare a parent Job.

Per Corey's framing of the hierarchy on the demo call: "the order of hierarchy is project, job, work order, and then soon will be task." A WO can stand alone (no parent Job, no project), but it can also nest inside a Job. This spec adds the smallest piece needed to make that nesting visible: a self-FK on Job (parentJobId) and a Work Orders tab on the Job detail page that lists child WOs. Full sub-relationship handling (Project → Job → WO → Task with rollups) is the post-V1 WOX-23 work.

"If you ever look at the job, so right now how it is is that whatever job that we go to and you go to form submission, you can see all the work orders associated with that job." — Kris Grant (Thermogenics), 2026-05-07 demo call

2. Scope

Already Built

  • DONE WO classification routing (WO-1) — distinguishes WO-classified Jobs from Project Jobs
  • DONE Job detail page (desktop + mobile) — host for the new Work Orders tab
  • DONE WO list / detail pages (WO-4, WO-5) — child rows link to these

In Scope (WO-23)

  • IN New self-FK on Job: parentJobId (nullable; SetNull on parent archive)
  • IN Set parentJobId at WO creation when the WO is created from a Job's context (e.g., "+ New work order" button on the Job detail page passes the parent's id)
  • IN "+ New work order" button on Job detail page (desktop + mobile) for Project-Job-classified Jobs — opens the WO create form pre-wired with this Job as parent
  • IN Work Orders tab on the Job detail page (desktop + mobile) — lists Jobs where parentJobId = this job's id AND jobClassification = WorkOrder. Reuses the existing WO list row component (same as WO-5 portfolio list).
  • IN Tab visible only on Project-Job-classified Jobs (it's meaningless on a WO Job; WOs don't nest under WOs in V1)
  • IN Reverse pointer on the WO detail page header: when a WO has a parentJobId, render a small chip linking back to the parent Job ("Part of: Cedar Ridge HVAC Retrofit")

Out of Scope

  • OUT Multi-level nesting (WO under WO, Task under WO) — that's WOX-23 post-V1
  • OUT Rollup financials from child WOs to parent Job — financial summary continues to compute from the Job's own line items in V1
  • OUT Bulk-reparent UI (move N WOs to a different Job) — no demand in V1; can be done one-at-a-time via the WO edit form
  • OUT Cascading rules on parent Job archive — SetNull only; child WOs survive the parent's archive intact
  • FUTURE Parent breadcrumbs / hierarchy navigation — folds into WOX-23 work

3. UI Concepts

Interfaces being added

  • Desktop Job detail · new "Work Orders" tab listing child WOs (with status, completion date, primary technician, link-through)
  • Desktop Job detail · "+ New work order" button at the top of the Work Orders tab, pre-wires the new WO with this Job as parent
  • Mobile Job detail · same Work Orders tab, mobile layout (compact list)
  • Desktop / Mobile WO detail header · "Part of: <parent Job name>" chip when parentJobId is set; tap to navigate to parent Job
Reuse: the WO list row component already exists for WO-5 (T&M Work Order Log, in QA). The Work Orders tab on Job detail uses the same component with a different filter (parentJobId = this.job.id instead of portfolio-wide). No new list UI to build — just a new mount point.

4. Data Model

4.1 Job — self-FK addition

// Added to existing Job model:
parentJobId String?  @db.VarChar(21)
ParentJob   Job?     @relation("JobChildJobs",
                                fields: [parentJobId],
                                references: [id],
                                onDelete: SetNull)
ChildJobs   Job[]    @relation("JobChildJobs")

@@index([parentJobId, isDeleted], map: "Job_parentJob_idx")

4.2 Migration

ALTER TABLE `Job`
    ADD COLUMN `parentJobId` VARCHAR(21) NULL,
    ADD INDEX `Job_parentJob_idx` (`parentJobId`, `isDeleted`),
    ADD CONSTRAINT `Job_parentJobId_fkey`
        FOREIGN KEY (`parentJobId`) REFERENCES `Job`(`id`)
        ON DELETE SET NULL ON UPDATE CASCADE;
Why a self-FK on Job and not a join table: WOs are Jobs (per WO-1). The hierarchy "Project Job has child WOs" is a parent-child relationship between Job rows. A self-FK is the natural shape — and matches what WOX-23 will extend (Project Job → WO → Task all on the same Job table). Self-FK now means WOX-23 just adds nesting depth, not a new model.

5. API Surface

5.1 Type extension

extend type Job {
  parentJobId: String
  parentJob: Job
  childWorkOrders(includeArchived: Boolean = false): [Job!]!
    # field resolver — filters this.children to jobClassification = WorkOrder
}

5.2 Mutation input extensions

extend input CreateJobInput {
  parentJobId: String     # set when creating a WO from a Job's "+ New work order" button
}

extend input EditJobInput {
  parentJobId: String     # allows reparenting a WO; null clears the link
}

No new mutations. The existing createJob / editJob mutations gain the optional parentJobId input.

5.3 Validation

  • The parentJobId target must be a Project-Job-classified Job (not another WO) — V1 doesn't allow WO under WO. Resolver enforces.
  • A Job cannot be its own parent (the resolver rejects parentJobId == id).
  • No cycle check needed in V1 since nesting is shallow (one level only).

7. Acceptance Criteria

  1. Job.parentJobId is added as a nullable self-FK with SetNull on parent archive.
  2. Creating a WO from a Project Job's "+ New work order" button sets the new WO's parentJobId to that Project Job's id.
  3. Project Job detail page (desktop + mobile) shows a Work Orders tab listing child Jobs where jobClassification = WorkOrder; uses the same WO list row component as WO-5.
  4. The Work Orders tab is hidden on WO-classified Jobs in V1 (WOs don't nest under WOs).
  5. WO detail header shows a "Part of: <parent Job name>" chip when parentJobId is set; tapping navigates to the parent Job.
  6. The resolver rejects setting parentJobId to a Job whose jobClassification = WorkOrder (V1 prevents WO-under-WO).
  7. The resolver rejects setting parentJobId == id (no self-parenting).
  8. Archiving a parent Job SetNulls the parentJobId on every child WO; child WOs survive intact.
  9. Existing Jobs with no parentJobId behave identically to before this spec — no regressions on standalone WOs or standalone Project Jobs.
