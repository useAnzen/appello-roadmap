LEM Combined Report

A single page that shows Labor / Equipment / Material side-by-side as cost vs. billable, with margin per row, drillable to source records. Built in two phases: Phase 1 (Labor + Equipment) ships standalone right after LEM-1 and LEM-2 clear QA. Phase 2 (Material) lights up automatically when MAT-2a lands. Replaces the spreadsheet that every owner builds by hand today.

Customer drivers: Thomas (canonical), Owens, Rival, Luse, Barnes Phase 1 effort: 4 days · 1 engineer (Labor + Equipment) Phase 2 effort: 2 days (after MAT-2a lands — adds Material columns)

1. Why this matters

Owners and PMs need to know, on any job, in any month: how much did it cost us, how much can we bill, what's our margin? Today, that answer requires merging at least three reports — labor from one screen, equipment from another, material from a third (or from raw AP) — and assembling the answer in Excel. Every customer past the 5-job mark eventually builds this spreadsheet; nobody builds it the same way; everyone builds it manually every month.

"This to me looks like a single report that includes all AP processed, plus all timesheets logged, broken down by cost code, broken down by wage rate in the most simple format." — Corey, on behalf of Thomas Kanata (Nov 2025) — the canonical LEM ask

Appello already has every input: Z_FinancialSummaryFeed (cost-side, in production), TimesheetReportView, JobActivityReportFeed, plus the new billableValue fields from LEM-1 and LEM-2 (both in QA). What's missing is one report that joins them on cost-code and emits cost-vs-billable side-by-side. Q21030-7740 (Job Labour Report) has been sitting in Tech Review with no assignee since 2024 — TTC-5 closes it and goes further by including equipment and (Phase 2) materials in the same report.

2. Who this is for

  • Owners / principals — they want to look at any job and see the margin in 5 seconds, not 30 minutes of spreadsheet building.
  • Project managers — they need cost-vs-billable per cost code mid-job to spot under-billed labor or runaway equipment hours.
  • Estimators / VPs — they want post-job actuals to feed back into the next bid.
  • Controllers — they reconcile the report against the GL and use it during month-end close.
  • Onboarding consultants — they show this report on day 1 of a customer pilot. It's the "wow" moment.

3. User stories

As an owner
I want to open one report and see Labor + Equipment + Material as cost vs. billable for any job, so I know my margin without building a spreadsheet.
As a PM
I want to group the report by cost code or by job, so I can see either "where on the job is bleeding" or "which jobs are bleeding."
As a PM
I want to filter by date range (this month, last month, custom), so the report matches a billing or accounting period.
As an owner
I want to drill down on any cell to see the underlying timesheets / equipment time entries / AP invoices, so I can investigate anomalies without leaving the report.
As a controller
I want to export the report to CSV/Excel, so I can reconcile against the GL during month-end.
As an estimator
I want to see margin % on every row, color-coded green/yellow/red, so I can spot under-priced trade-level rates feeding back into the next bid.
As an onboarding consultant
I want this report to work for a customer with only Labor + Equipment (Phase 1), so I can ship value before MAT-2a lands.

~2 min per ad-hoc question · authoritative, source-linked

7. Decisions needed

D1 · Default group-by (Cost Code or Job)?
Recommend Cost Code when a single Job is selected; Job when multiple jobs are in the filter. The grouping picker overrides this default.
D2 · Reuse Z_FinancialSummaryFeed or build a new view?
Recommend build a new view Z_LemCombinedReport.sql. The existing FinancialSummaryFeed is cost-only and entangled with the existing dashboards — modifying it risks regressions. Better to add a new view that joins the existing source views and adds billable columns. Per the workspace rules (.cursor/rules/general.mdc), updating a view file just needs pnpm run prisma:updateViews — no migration needed.
D3 · Phase 1 ships standalone or wait for Material?
Recommend ship Phase 1 standalone. Mak, Owens, Rival, and Luse all get value from Labor + Equipment alone. Material is additive and can light up later via the Include filter without changing the page layout.
D4 · Time period: bill-date, service-period, or transaction-date?
Recommend service / activity date — i.e. the date the work was performed (timesheet record date, equipment time entry date, AP invoice service date). This matches what owners actually want to know ("how did we do in April?"), not when the AP invoice happened to be entered.
D5 · Margin thresholds — instance-configurable or hardcoded?
Recommend instance-configurable with sane defaults (20% / 5% / negative). Some customers run on 10% net, others on 30% — one set of colors won't fit all.
D6 · Permission model
New permission report.lemCombined.view, default ON for Owner / Controller / PM roles, OFF for everyone else (since this exposes margin data).

Engineering notes

Architecture: a new SQL view, not a new model

This report is read-only and aggregates existing data — it should be a SQL view, not a Prisma model. Per .cursor/rules/general.mdc, view files in apps/api/prisma/views/*.sql don't need a migration; pnpm run prisma:updateViews applies them.

-- apps/api/prisma/views/Z_LemCombinedReport.sql

SELECT
  j.id  AS jobId,
  j.code AS jobCode,
  j.name AS jobName,
  cc.id AS costCodeId,
  cc.code AS costCodeCode,
  cc.name AS costCodeName,

  -- Labor
  COALESCE(labor.totalCost, 0)     AS laborCost,
  COALESCE(labor.totalBillable, 0) AS laborBillable,

  -- Equipment
  COALESCE(equip.totalCost, 0)     AS equipmentCost,
  COALESCE(equip.totalBillable, 0) AS equipmentBillable,

  -- Material (Phase 2 — left at 0 until MAT-2a)
  COALESCE(mat.totalCost, 0)       AS materialCost,
  COALESCE(mat.totalBillable, 0)   AS materialBillable

FROM Job j
LEFT JOIN CostCode cc ON cc.jobId = j.id  -- or whatever the relation is

LEFT JOIN (
  SELECT
    tsr.jobId,
    tsr.costCodeId,
    SUM(tsr.durationSeconds / 3600.0 * tlr.baseValue)        AS totalCost,
    SUM(tsr.durationSeconds / 3600.0 * COALESCE(tlr.billableValue, tlr.baseValue)) AS totalBillable
  FROM TimeSheetDetailRecord tsr
  JOIN TradeLevelRate tlr ON tlr.id = tsr.tradeLevelRateId
  WHERE tsr.approvedAt IS NOT NULL
    AND tsr.isDeleted = 0
  GROUP BY tsr.jobId, tsr.costCodeId
) labor ON labor.jobId = j.id AND labor.costCodeId = cc.id

LEFT JOIN (
  SELECT
    ete.jobId, ete.costCodeId,
    SUM(ete.durationSeconds / 3600.0 * erv.baseValue)        AS totalCost,
    SUM(ete.durationSeconds / 3600.0 * COALESCE(erv.billableValue, erv.baseValue)) AS totalBillable
  FROM EquipmentTimeEntry ete
  JOIN EquipmentRateValue erv ON erv.id = ete.equipmentRateValueId
  WHERE ete.isDeleted = 0
  GROUP BY ete.jobId, ete.costCodeId
) equip ON equip.jobId = j.id AND equip.costCodeId = cc.id

LEFT JOIN (
  -- Phase 2 join — populated once MAT-2a's MaterialConsumption + LEM-3 land
  SELECT jobId, costCodeId, 0 AS totalCost, 0 AS totalBillable
  FROM Job WHERE 1=0
) mat ON mat.jobId = j.id AND mat.costCodeId = cc.id

WHERE j.isDeleted = 0;

Date filtering

Date filtering happens in the GraphQL resolver, not the view — pass periodStart / periodEnd through and add the date predicate to the query against the view (or push the filter into the view via a parameterized table-valued function if MySQL allows). Easiest v1: keep the view broad and apply WHERE tsr.recordDate BETWEEN ? AND ? at query time in the model. The view can be rewritten to be parameterized later if performance demands it.

Model methods (in apps/api/src/models/LemCombinedReport.ts — new model)

  • getLaborDrillDown / getEquipmentDrillDown / getMaterialDrillDown — each one calls the existing BaseModel.getList on the source model with a where filter. Per CLAUDE.md's data-access rule: never raw Prisma in resolvers; always go through model methods.

Permissions

  • New permission key: report.lemCombined.view. Default ON for Owner / Controller / PM roles. OFF by default for crew/field roles.
  • Drill-down queries require the same permission plus existing timeSheetDetailRecord.view / equipmentTimeEntry.view for source data.

Performance

  • The view's three subqueries are independently indexable. Make sure the existing indexes on TimeSheetDetailRecord (jobId, costCodeId, approvedAt) and EquipmentTimeEntry (jobId, costCodeId) exist; add if missing.
  • For instances with very large datasets, the view query can be wrapped in a derived table with the date filter applied first — common SQL trick to keep the planner happy.
  • Target: ≤ 3 seconds on a 5K-timesheet job. Add a load-test script in apps/api/__tests__/performance/ following the existing pattern.

Testing surface

  • SQL: snapshot test of the view definition; integration test seeded with known timesheets, equipment entries, and rates verifying every cell.
  • Unit: model method permission checks, group-by aggregation, fallback rate when billableValue is null.
  • Integration: drill-down endpoints return the exact records that contributed to a parent cell (sum tie-out).
  • E2E: open report, filter to a known job, verify cell totals match a hand-built fixture.
  • Phase 2: re-run the same E2E with Material data added; numbers tie out and Material columns appear.
