MAT-2a: LEM Material Consumption — Desktop (Implementation Plan)

Self-contained execution plan. Another agent should be able to pick this up cold, run the steps in order, and ship a PR. File paths are relative to the monorepo root (apps/api, apps/frontend). Read Pre-flight first. Companion spec: uis-MAT-2a-lem-consumption-desktop.html (this is the plan; that is the spec + decision log). Code blocks are drop-in starting points — match surrounding style, don’t reformat neighbours.

Overview & Outcome

MAT-2a completes the “M” in LEM by promoting the existing WorkOrderMaterialItem from a bare line-item row into a structured, approvable pricing record — the material peer of Timesheet and Equipment Time. There is no new MaterialConsumptionEntry model. After this lands:

  • A user logs material consumed on a Job / Work Order day — one or many rows, each a catalog pick (materialId + axes → materialAttributePriceId, the MAT-0 source row) or free text (description) — with a work date, quantity, a stored cost snapshot, and a per-line cost-code split.
  • Each row carries its own ApprovalStatus (NotSubmitted→InReview→Approved/Rejected) with a full submit/approve audit trail, exactly like EquipmentTimeEntry.
  • A combined daily LEM report, keyed on (jobId, workDate), aggregates the three structured-tier records — Timesheet (labour), Equipment Time (equipment), and WorkOrderMaterialItem (material) — showing cost and billable, exportable to PDF.
  • Approved material consumption (stored cost snapshot + billable value) flows into the Job Financial Summary.
Most of the row already exists. WorkOrderMaterialItem ships today (migration 20260409200000_work_order_line_item_tables) with jobId/jobScheduleId, the catalog-XOR-free-text fields, quantity/unitPrice/costPrice/total, a recalculateTotal on create/edit, and a combined upsertWorkOrderLineItems mutation. The genuinely new work is: a handful of columns (workDate, status + audit, unitPropertyValueId), one child join table (WorkOrderMaterialItemCostCode), the approve flow + permission, the daily report view/resolver, the Financial-Summary hookup, and the desktop UI.
HARD PREREQ — the WorkOrder*Item tables must be on your branch. They exist on the WO/LEM integration branches (verified in repo-2 @ schema.prisma≈5959 and application-mono-repo) but not on Patch-v1.32.26. Confirm the line-item migration is merged into your 1.33 integration branch before starting; if it isn’t, this slice blocks on it. Likewise the daily report’s billable column depends on LEM-3a (resolveMaterialSellPrice) and catalog cost resolution depends on MAT-0 source rows — both should be merged first.

Conventions

  • Golden rule: logic in models/ + services/; resolvers stay thin.
  • No instanceId — single-instance app; the row carries none.
  • No slice identifiers (“MAT-2a”) in migration names or code comments.
  • Reuse the existing ApprovalStatus enum (already in the Prisma schema + the types/ const-array). Do not add new values; do not invent a Draft/Submitted/Approved string enum — that was the old draft.
  • gql definitions at the bottom of files; no triple-quote GraphQL descriptions; React components as FC arrow fns; boolean/shorthand JSX props last.

What you are NOT doing

  • No MaterialConsumptionEntry model — the draft’s parallel model is dropped; consumption is a WorkOrderMaterialItem.
  • Not touching the structured timesheet / equipment-time records — you only read them for the report.
  • Not folding the bare unstructured WorkOrderLaborItem / WorkOrderEquipmentItem quick rows into the LEM report (they carry no cost codes/billable/status; including them double-counts).
  • No inventory deduction (MAT-7), no mobile entry (MAT-2b), no offline support, no bulk import.
Decisions (defaults below; confirm with user if they object).
  • D1 — PERMISSION — RESOLVED (do NOT reuse materialorder). Material Consumption is a separate concern from MaterialOrder, so it gets its own permission key. Add WorkOrderMaterialItem to permissionsByReferenceModel with view / create / edit / delete / approve, mirroring EquipmentTimeEntry; approve is the net-new privileged gate. ⚠ Shared-model coupling (see Step 7): the Consumption tab and the Work Order line-item editor are the same model, and adding it to the map flips it from parent-passthrough to enforced — so create/edit/delete/view gate both surfaces. The parent authorization it passes through to today is Job:edit (a Work Order is a Job), so default those actions to match Job:edit (no regression) and label them in PermissionMap as also governing material lines on Work Orders. A future MaterialConsumption ↔ MaterialOrder link is parked — not this slice.
  • D2 — RESTRICT_MATERIAL: the consumption tab + report respect the existing material feature gate (publicRuntimeConfig.n) like the other material surfaces.
  • D3 — cost-code split unit: WorkOrderMaterialItemCostCode.quantity (Decimal), mirroring equipment’s approvedDuration split. No split entered → the whole line implicitly allocates to its single code (or none).
  • D4 — cost vs billable: material cost = the stored snapshot (total); material billable = resolveMaterialSellPrice (LEM-3a). The report shows both, matching labour/equipment.

Step 1 — Schema: extend WorkOrderMaterialItem + new WorkOrderMaterialItemCostCode

Action
MOD apps/api/prisma/schema.prisma
Risk
Low — additive columns + one new table; existing rows backfilled in Step 2.

Add the structured-pricing columns to WorkOrderMaterialItem and create the cost-code join. Add the back-relations on User, Application, PropertyValue, and CostCode.

model WorkOrderMaterialItem {
  // ... existing fields unchanged ...

  workDate DateTime                                  // daily LEM anchor (see Step 2 backfill)

  unitPropertyValueId String?        @db.VarChar(21) // free-text rows only; null = derive from Material
  UnitPropertyValue   PropertyValue? @relation("WorkOrderMaterialItemUnit", fields: [unitPropertyValueId], references: [id])

  status                   ApprovalStatus @default(NotSubmitted)
  submittedByUserId        String?        @db.VarChar(21)
  SubmittedByUser          User?          @relation("WorkOrderMaterialItemSubmitter", fields: [submittedByUserId], references: [id])
  submittedOnApplicationId String?        @db.VarChar(21)
  SubmittedOnApplication   Application?   @relation("WorkOrderMaterialItemSubmittedOnApp", fields: [submittedOnApplicationId], references: [id])
  approvedByUserId         String?        @db.VarChar(21)
  ApprovedByUser           User?          @relation("WorkOrderMaterialItemApprover", fields: [approvedByUserId], references: [id])
  approvedOnApplicationId  String?        @db.VarChar(21)
  ApprovedOnApplication    Application?   @relation("WorkOrderMaterialItemApprovedOnApp", fields: [approvedOnApplicationId], references: [id])

  WorkOrderMaterialItemCostCodes WorkOrderMaterialItemCostCode[]

  @@index([jobId, isDeleted])               // existing
  @@index([jobId, workDate, isDeleted])
  @@index([materialId])                     // existing
  @@index([status, isDeleted])
}

model WorkOrderMaterialItemCostCode {
  id         String   @id @db.VarChar(21)
  isDeleted  Boolean  @default(false)
  isArchived Boolean  @default(false)
  createdAt  DateTime @default(now())
  updatedAt  DateTime @default(now()) @updatedAt

  workOrderMaterialItemId String                @db.VarChar(21)
  WorkOrderMaterialItem   WorkOrderMaterialItem @relation(fields: [workOrderMaterialItemId], references: [id], onDelete: Cascade, onUpdate: Cascade)

  costCodeId String   @db.VarChar(21)
  CostCode   CostCode @relation(fields: [costCodeId], references: [id], onDelete: Restrict, onUpdate: Cascade)

  quantity Decimal? @db.Decimal(10, 2)

  @@index([workOrderMaterialItemId, costCodeId, isDeleted])
}

Back-relations to add: User → the four named relations; Application → SubmittedOnApplication/ApprovedOnApplication; PropertyValue → WorkOrderMaterialItemUnit; CostCode → WorkOrderMaterialItemCostCodes WorkOrderMaterialItemCostCode[]. (Match how EquipmentTimeEntry declares its equivalents.)

Step 6 — LEM report: view + resolver

Action
NEW apps/api/prisma/views/LEMReportView.sql · src/graphql/models/LEMReport.ts

A daily aggregation keyed on (jobId, workDate), built from the three structured-tier sources. The view aggregates cost + volume; compute billable in the resolver (or via the LEM-3a sell-price SQL mirror) so material billable runs through resolveMaterialSellPrice, matching how labour/equipment billable is derived.

-- LEMReportView.sql — three CTEs UNION'd, grouped by (jobId, workDate)
-- Labour    : TimeSheet / TimeSheetDetailRecord where status = Approved
-- Equipment : EquipmentTimeEntry where status = Approved (workDate)
-- Material  : WorkOrderMaterialItem where status = Approved (workDate)
--             materialQty = SUM(quantity), materialCost = SUM(total)
-- EXCLUDES WorkOrderLaborItem / WorkOrderEquipmentItem (unstructured quick rows)
  • lemReport(input: LEMReportFilterInput!): [LEMReportRow!]! — reads the view filtered by jobId + optional dateFrom/dateTo, enriches material rows with billable via resolveMaterialSellPrice, returns cost + billable per dimension + daily totals.
  • Register the resolver in src/graphql/schema.ts (import, typeDef, Query).
Depends on LEM-3a. If resolveMaterialSellPrice / the material billable view isn’t merged yet, ship the report with materialCost populated and materialBillableValue falling back to cost, then wire billable when LEM-3a lands. Flag this in the PR.

Step 10 — Smoke test & acceptance

  • Logging a catalog row resolves a materialAttributePriceId, derives UoM from the Material, and stores a total snapshot; a free-text row requires a unitPropertyValueId.
  • A row with neither material nor description, or with quantity ≤ 0 / no workDate, is rejected.
  • New rows default to NotSubmitted; setting Approved/Rejected requires the WorkOrderMaterialItem:approve permission and stamps the approve audit fields.
  • approveWorkOrderMaterialItems(ids) approves a batch in one call.
  • A row splits across multiple material-typed cost codes; a labour-typed code is rejected.
  • The LEM report aggregates daily by (job, workDate) from Timesheet + Equipment Time + WorkOrderMaterialItem, shows cost & billable, and does not double-count the unstructured WO quick rows.
  • The report exports to PDF; Approved material consumption appears in the Job Financial Summary.
  • With RESTRICT_MATERIAL on, the consumption tab + report are gated.
