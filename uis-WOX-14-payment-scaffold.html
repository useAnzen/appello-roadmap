Customer Payment Gateway — Scaffolding (V1)

Customers pay invoices today by check or e-transfer to an email — slow, manual, hard to reconcile. Long-term we want a "Pay now" button on emailed invoices. V1 scope is scaffold only: data models, permission, settings page stub, hidden feature flag. Live Stripe / Square integration deferred to a 1.34 activation sprint so it's a config drop-in, not a refactor.

Status: Concept · Scaffold Effort: ~2d (V1 scaffold) + ~8-10d (V2 activation) Extends: TTC-2 · WO-7 Master ref: #29 — Payment Gateway scaffold

1. Where this lives in the app

Page / route (V1 hidden): /settings/payments (path TBD — likely under existing Settings shell at apps/frontend/src/pages/settings/)
Backend models (NEW): PaymentGatewayConfig · CustomerPayment · PaymentMethod (Prisma schema in apps/api/prisma/schema.prisma)
Backend API: placeholder mutation payInvoice(invoiceId, provider) that returns NOT_IMPLEMENTED until activated
Future surface (V2): Pay button in TTC-2 send-invoice email · customer-facing receipt page · WO detail invoice flyout

V1 ships only the data spine and a hidden settings page guarded by a payments.enabled feature flag — no live UI exposed to customers. The mockup below sketches both the V1 admin stub and the future V2 customer-facing flow so Emma + Corey can confirm the shape we're scaffolding toward.

2. UI Concept

V1 (ships in 1.33): hidden settings page where an admin can pre-select a future provider. V2 (sketched, not built): the customer-facing pay flow we're aiming at — clearly marked "not yet implemented".

3. Key decisions for Emma + Corey to discuss

D1 Which gateway first when we activate?
Recommended: Stripe Connect Express. Broadest reach, best Canadian + US support, ~1-2 weeks to ship vs Square's in-person tap-to-pay focus. Helix is the Corey-research alternative — defer until the Helix link is reviewed.
D2 Fees pass-through to customer or absorbed?
Recommended: Configurable per instance, default off (absorbed). Pass-through is industry-acceptable but a poor first impression. Add the toggle now in the data model so customers can flip it without migration.
D3 Partial payments supported?
Recommended: Yes — but post-V1 with a full reconciliation workflow. Scaffold the model with amountPaid + amountDue fields now so we don't refactor when activated.
D4 What ships in V1 specifically?
Recommended: (a) Prisma models + migrations · (b) /settings/payments hidden behind payments.enabled feature flag · (c) JobBill.paymentLink nullable column · (d) GraphQL placeholder mutation that errors. NO live UI · NO gateway code · NO customer-facing button.
D5 Timeline for activation?
Recommended: Size in 1.34 planning once Helix vs Stripe is decided. Activation sprint is ~8-10d once provider chosen — config + webhooks + receipt page. The scaffold makes activation a config sprint, not a refactor.
