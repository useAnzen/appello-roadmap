Forms from Equipment — Options Brief

Inspection forms launched directly from a piece of equipment on mobile. Decision needed on how the equipment ↔ submission link is recorded.

Context

Field users want to open a piece of equipment on mobile, tap Start Inspection, and fill out a form that's automatically tied to that equipment — without first navigating to a Job. Today, a Feedback (form submission) requires a Job, and the only way a submission gets linked to a specific piece of equipment is via the user's answer to an Equipment-typed question on the form.

From Ian (2026-05-14): "the ability to pull up a piece of Equipment and start an inspection form against it is going to be key… ideally the forms are filtered to only those that should be available for equipment… if they are in that specific equipment it would already know that."

Shared piece — form-library filter

Both options below need the same eligibility rule for "which forms can be launched from this equipment":

A SafetyForm is eligible from equipment E (category C) if it has at least one Equipment-type question where either the question has zero _EquipmentCategoriesQuestions rows (open to any category), or it has a row for C.

Option 1 — Reuse the existing Equipment-question relationship

When the user starts an inspection from equipment E, the form's Equipment question answer is pre-seeded with E. The association lives where it already lives today — on the Answer row. No new columns.

Pros

  • Zero schema change.
  • One source of truth — no risk of equipment-on-feedback and equipment-on-answer disagreeing.
  • Existing "forms on this equipment" queries / reports keep working unchanged.
  • Clean filter rule — forms without an Equipment question simply aren't eligible.

Cons

  • Every eligible form must have an Equipment question. If a form author forgets to add one, the form is silently invisible from the equipment surface.
  • Forms with multiple Equipment questions — we have to pick one to pre-seed.
  • The "started from equipment X" intent is encoded as an editable answer unless we lock it.
  • Doesn't help with the optional "drop the Job requirement" follow-on.

Option 2 — Add Feedback.equipmentId (system-set only)

Add an optional equipmentId column on Feedback, populated only when the form is launched from the equipment surface. Never user-editable; not surfaced in the form builder or form UI. It records where the submission was initiated from.

"Forms on this equipment" list query becomes a union: rows where Feedback.equipmentId = E OR an answer on the feedback references E via the Equipment question.

Pros

  • Form library doesn't have to be equipment-aware. Any inspection form can be launched from equipment — no requirement to include an Equipment question.
  • Clean separation between user intent (Equipment question answer) and system context (where it was initiated). Both can coexist and even disagree without ambiguity.
  • Unlocks the optional follow-on: making Feedback.jobId nullable.
  • Indexable on a single column — cheaper "all submissions for this equipment" queries than joining through Answer → Question.

Cons

  • Schema change + migration on the (large) Feedback table. Additive nullable column, but still a review item.
  • Two places to look for the equipment link — reports / list queries must union both, or pick one canonical source. Risk of drift if not centralized.
  • Form-library filter rule on the equipment surface is still the same as Option 1 unless we relax it.
  • Need a decision on whether the link survives equipment archival / reassignment.

Filter twist for Option 2 — explicit "equipment form" classification

Because Option 2 doesn't require the form to have an Equipment question, the shared eligibility rule no longer protects us from launching an unrelated form (e.g. a daily timesheet form) against a piece of equipment. Two ways to keep the launch list focused:

  • Keep the shared rule — only forms with a matching Equipment question are launchable, even though Feedback.equipmentId would work for any form. Safer; mirrors Option 1 behaviour for the filter.
  • Add an explicit classification — e.g. a new SafetyForm.formType enum or boolean (EQUIPMENT_INSPECTION / isEquipmentForm) maintained by the form author. Lets us launch forms with no Equipment question at all, but makes form authors responsible for tagging. Could also drive other surface filters down the road (job-form pickers, library views).

A hybrid is possible — show forms matching either the shared eligibility rule or the explicit tag — but probably overkill until we see how form authors actually use it.

Optional follow-on for Option 2 — drop the Job requirement

If we go with Option 2, Feedback.equipmentId gives us a non-Job anchor for a submission. We could then make Feedback.jobId nullable so a true "equipment-only" inspection has no Job at all.

Much larger change than Option 2 alone. Feedback.jobId being NOT NULL is assumed by every downstream consumer — feedback lists, job detail, project rollups, exports, notifications, the idx_Feedback_ViewIndex composite, and the auto-clone / replacement workflow. Recommend treating this as a separate phase after Option 2 ships, not bundled.

Lighter alternative within Option 2: auto-create / reuse a per-tenant "Equipment Inspections" Job (Ian's "01-001 Mkwa Equipment Inspections" pattern) so Feedback.jobId stays NOT NULL and downstream code is unchanged. Cost is a synthetic Job that some queries / UIs may need to know to filter or label specially.

Recommendation

Option 2, without the drop-Job follow-on for now. The decoupling between user intent and system context is the right shape long-term and costs one additive nullable column. It also lets us launch inspection forms from equipment even when the form author forgot the Equipment question — the more forgiving failure mode for field users.

Column + index can land in 1.33; the Job-nullability conversation can continue separately.

Open questions

  1. Form-library eligibility rule — does the shared filter (Equipment question with no _EquipmentCategoriesQuestions rows OR a matching category row) match expected behaviour, or do we want a separate SafetyForm.isEquipmentForm flag for explicit opt-in?
  2. Option 1 vs Option 2 — does the decoupling argument for Option 2 outweigh the extra column / migration?
  3. If Option 2: do we pre-seed the form's Equipment question answer with the launch equipment (so it and Feedback.equipmentId agree), and do we lock that answer from edit?
  4. Drop the Job requirement — appetite to revisit Feedback.jobId nullability in 1.34, or commit to the synthetic "Equipment Inspections" Job pattern?
  5. Equipment archival — should Feedback.equipmentId survive equipment archival / category reassignment? (Default: yes.)
