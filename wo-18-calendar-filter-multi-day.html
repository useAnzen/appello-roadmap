WO-18 Work Orders P1 - 1.33 Draft

Schedule View Toggle + Status-Aware WO Filtering

Add a Calendar / Work Orders toggle to /scheduling. When flipped to Work Orders, the status filter swaps from jobStatus values to workOrderStatus values (which is what WOs actually use), and the schedule-entry form's job picker filters to WO-classified jobs only. Fixes the bug where WOs are invisible on the schedule today (filter mismatch). Path B build of WOX-01's V0 toggle pattern + the underlying status predicate fix; satisfies Emma's previously-skipped scope item #1 at V0 fidelity.

1. Business Case

Bug: WOs are invisible on the schedule. The Calendar Schedule pulls events from TimeSheetRecord (which works fine for WOs — they're Jobs), but pre-filters by jobStatus. WOs use a separate workOrderStatus property (per WO-1's split status systems), so a WO's status will never match a jobStatus "In Progress" predicate → WO time records are never returned to the calendar. Same root cause for the Job Schedule's pre-filter.

WOs are Jobs in the data model but split off their status into a separate workOrderStatus PropertyValue category (Draft / Submitted / Awaiting Signature / Signed / Approved / Invoiced / Void) seeded in WO-1. That split is correct — WO and project-job lifecycles are different — but it leaks into the schedule layer where the predicate looks for jobStatus only.

The fix is two-sided: (a) route the schedule's status predicate based on classification (project jobs use jobStatus, WOs use workOrderStatus), and (b) give the user a clean way to tell the schedule which classification they're working with — which is what WOX-01's V0 Calendar/Work Orders toggle is for. The toggle is also what unlocks WOs being visible on a "I want to schedule WO labor" workflow at all, so this fix subsumes Emma's previously-skipped scope item #1 at V0 fidelity. Full Kanban dispatch (WOX-16) stays post-V1.

Schedule-entry form behavior also flows from the active view: in Calendar mode the form's job picker shows project jobs; in Work Orders mode it shows WOs. Mixing the two would let users accidentally schedule a WO from Calendar mode despite being invisible there — friction without value.

Emma's scope #9 (multi-day labor date column) is not in this spec — it's already handled. WO labor entries flow through TimeSheetRecord (because WOs are Jobs), the same path Job labor uses. Date is already an attribute of every record. Adding a separate "date column" to the WO labor table would duplicate state that lives correctly in TimeSheetRecord. #9 is satisfied by existing infrastructure.

4. Data Model

No schema changes. WO-1 already seeded the workOrderStatus values; the bug is that schedule queries don't consult them. Fix is at the query / filter-predicate layer.

5. API Surface

One change to the existing schedule events query input: classification-aware filtering.

extend input ScheduledEventsFilter {
  # Active classification — drives which status property the predicate
  # matches against. Defaults to "ProjectJob" (preserves existing
  # behavior for clients that don't pass it).
  jobClassification: JobClassification

  # Status filter inputs become classification-aware.
  # ProjectJob events match jobStatusIds; WorkOrder events match
  # workOrderStatusIds. Server-side resolver picks the right one based
  # on jobClassification.
  jobStatusIds:       [String!]
  workOrderStatusIds: [String!]
}

The same pattern applies to any other schedule-feed queries with a status pre-filter (e.g., Job Schedule's "In Progress" predicate). No new types, no new mutations.

7. Acceptance Criteria

  1. The /scheduling page shows a Calendar / Work Orders toggle at the top, defaulted to Calendar.
  2. In Calendar mode, the schedule shows events from project-job-classified Jobs only; the Status filter exposes jobStatus values; behavior matches the current pre-this-spec experience.
  3. In Work Orders mode, the schedule shows events from WO-classified Jobs only; the Status filter exposes workOrderStatus values (Draft / Submitted / Awaiting Signature / Signed / Approved / Invoiced / Void).
  4. Toggle state persists per-user via localStorage; revisiting the page restores the last-used view.
  5. The schedule-entry form opened from Calendar mode lists only project jobs in its job picker.
  6. The schedule-entry form opened from Work Orders mode lists only WOs in its job picker.
  7. The Job Schedule's "In Progress" pre-filter matches WOs whose workOrderStatus maps to InProgress (Submitted / Awaiting Signature / Signed) — WOs are no longer invisible there.
  8. Existing project-job behavior on every schedule surface is unchanged.
  9. Two e2e tests pass: (1) WOs in active workOrderStatus appear in Work Orders mode; (2) schedule-entry form picker scoping respects the active toggle.
  10. No schema changes; only the ScheduledEventsFilter input gains jobClassification + workOrderStatusIds.
