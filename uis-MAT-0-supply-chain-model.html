Supply Chain Foundation — Per-Source Material Pricing

Give every material cost a source. Instead of one catalogue cost per size, the price grid (MaterialAttributePrice) gains a (distributor + manufacturer) dimension plus a SKU and procurement metadata — so “the 2″ elbow costs $Y from Crossroads (Owens-Corning) and $B from ABC (Johns-Manville)” is a row, not a new subtree. The cheapest/preferred source feeds the existing bestAvailableCost() hook LEM-3a left for MAT-0. Foundation for MAT-3 (price book), MAT-5 (supplier PO), MAT-9 (discounts).

1. Business Case

After MAT-10, a Material knows which Companies are its manufacturers / distributors (the MaterialCompany link). What it still can’t answer: what each source charges, and under what SKU. Today a material’s cost is a single value per size cell (MaterialAttributePrice.value) or, for single-SKU items, Material.unitCost — there is no per-supplier price, no cheapest-source, and nothing for procurement (PO sourcing, price-book import) to build on.

The real-world facts that shape the model:

  • A SKU is size-specific. “90° Elbow” is a product family; the 2″ and 3″ are different SKUs at different prices. In Appello terms the SKU-bearing, priced unit is a MaterialAttributePrice cell, not the Material.
  • Cost has a source. The same cell can be bought from several distributors, and one distributor can sell two manufacturers’ versions of the same material at different prices/SKUs. So the source is a (distributor, manufacturer) pair.
The pricing payoff is already wired for. LEM-3a’s MaterialPricingService.bestAvailableCost() carries the comment: “MAT-0 will upgrade this to prefer DistributorPrice.effectivePrice … before falling through to MaterialAttributePrice. Service signature must not change.” MAT-0 fulfils that hook — the cheapest/preferred source cost flows into every sell-price the app already computes, with no caller changes.

2. Design History & Rationale

MAT-0 went through three shapes in review. Recording why we landed where we did (the rejected drafts are preserved):

A — CEO three-level (superseded copy): Material → ManufacturerProduct → DistributorPrice, with manufacturerSku at the material level. Rejected: a single SKU/price per material is wrong — SKUs and prices are size-specific, so they belong on the per-cell grid. The layer also duplicated cost storage that MaterialAttributePrice already owns.
B — a Material per manufacturer/distributor combo: reuse Material, make one per source. Rejected: N×M catalogue explosion, contradicts MAT-10’s Material↔Company M:N (it’s exactly MAT-10’s rejected single-supplier alternative), kills cheapest-source comparison, and emits duplicate Shopify Products for one real product (Shopify wants one generic Material = one Product).
C — a separate MaterialSupplierPrice table: Rejected: it runs parallel to MaterialAttributePrice, which already stores per-size prices — two price stores to reconcile.
Chosen — D: add a source dimension to the existing cost grid. MaterialAttributePrice gains a nullable (distributor + manufacturer) source, a SKU, and procurement metadata; the source-less row is the “house” price (today’s behaviour). The generic Material stays the product (one Shopify Product), MaterialCompany (MAT-10) is the source link, and ManufacturerProduct / DistributorPrice are dropped entirely. Smallest model that does size-specific SKUs + multi-source cheapest cost, reusing the grid, its editor, and the LEM hook.

3. Scope

Extend the cost grid with a source + SKU + procurement metadata, and resolve cheapest/preferred cost into the LEM hook. No new top-level models. Company & Material UI to view/manage sources, GraphQL + MCP, and the Shopify catalogue-readiness fields.

In Scope

  • IN Extend MaterialAttributePrice: nullable distributorId + manufacturerId (source), sku (+ optional manufacturerSku/upc), and procurement metadata (listPrice, discountPercent, effectiveFrom/To, minQty, leadTimeDays, packageQty/packageUnit, isPreferred, isInStock); relaxed unique so a cell has many source rows + one house row
  • IN Migrate the 0-axis price from Material.unitCost into an all-null MAP row so 0-axis SKUs carry sources too (axes already nullable per PR #7211; see Q-a)
  • IN effectivePrice (computed) + cheapest/preferred source resolution per cell/material
  • IN Wiring the source cost tier into bestAvailableCost() (the MAT-0 hook) — signature unchanged; keep the resolvedSellPrice SQL mirror in sync
  • IN Gate a source's distributorId/manufacturerId against MaterialCompany (MAT-10) — role-aware membership validation (a manufacturer must be a declared role=Manufacturer of the material, likewise distributor); inline confirm-then-add for a supplier not yet linked
  • IN Company detail: Products / Products & Pricing tabs (by join-existence, not company type); Material detail: source pricing with a best-price marker
  • IN GraphQL + MCP (thin → model); per-variant catalogue fields (own sku, barcode, weight, weightUnit) on the MAP house row

Out of Scope

  • OUT Bulk price-book import — MAT-3 · Quantity/tier discount cascade — MAT-9 (MAT-0 has a single price + flat discountPercent) · Supplier POs — MAT-5
  • OUT isPublishedToShopify / Shopify sync (deferred); product images (already handled by AssetReference, referenceTable = "Material")
  • OUT ManufacturerProduct / DistributorPrice models — not built (design D)

4. Current State — Load-Bearing Givens

Grounded against Release-v1.33.0.

1. MaterialAttributePrice — the grid we’re extending

schema.prisma ~line 2906. Keyed (materialId, selectedXValueId, selectedYValueId, selectedZValueId) → value Decimal(10,2) (the cost). The three axis columns are already nullable (PR #7211, the 1-axis refactor) and the @@unique already spans all four columns — so the table is structurally ready to hold an all-axes-null row for a 0-axis material. It just doesn’t today: 0-axis price still lives in Material.unitCost, and bestAvailableCost deliberately routes 0-axis to unitCost and avoids MAP “so a stale row doesn’t shadow the canonical unitCost.” MAT-0 flips that: the 0-axis price becomes an all-null MAP row (migrated from unitCost), so it can carry sources like any cell. (Not a heavily-used surface — safe to extend.)

2. bestAvailableCost() is the named MAT-0 hook

apps/api/src/services/MaterialPricingService.ts. bestAvailableCost(materialId): axis materials → latest MaterialAttributePrice.value; 0-axis → Material.unitCost. Header comment reserves the upgrade for MAT-0 and says the signature must not change. It is the any-cell fallback — WO/IE structured lines resolve a specific cell and pass costPrice in. The no-job sell tiers are mirrored as SQL in graphql/models/TableFeed/ConfigureColumnsData/material.ts (resolvedSellPrice).

3. MAT-10 MaterialCompany is the membership gate — MAP draws from it

The source FKs point at Company (the durable identity — what the price is from, and what the Shopify vendor / cross-material queries key on), not at MaterialCompany. A single-column FK can’t express the gate anyway: it can’t constrain the target row’s role, and MAP already carries its own materialId that a FK wouldn’t force to match — so the gate is inherently a composite, model-layer rule regardless of FK target. Hanging pricing off MaterialCompany would also couple price-row lifecycle to a thin, revivable membership join. Keep the FK on Company; gate on membership.

Rule (model layer, authoritative): on write of a source row, manufacturerId must resolve to a live MaterialCompany(material, company, role=Manufacturer) and distributorId to a live MaterialCompany(material, company, role=Distributor) — reject otherwise (a company declared only as a distributor still can’t be used as manufacturerId). MCP/direct writes hit this same check, so the UI dropdown isn’t the only guard. MaterialCompany is the set of which companies may supply the material; MAP source rows are the priced (cell × distributor × manufacturer) tuples drawn from that set. Adding a supplier not yet linked uses MAT-10’s confirm-then-create flow (search Company → confirm → create the MaterialCompany link + the price row together) — not a silent upsert.

4. Company type is NOT load-bearing (from MAT-10 Q2)

Company type is a configurable PropertyValue (many tenants only have “Vendor”/“Customer”). MAT-0 does not gate behaviour on it — the Company Products tab shows because the company has source rows (join-existence), not because of a type tag.

5. Company detail is tabbed; Material lacks sku/barcode/weight

Company detail composes a flat allTabOptions array (apps/frontend/.../CompanyDetailsPage) — a tab is one entry + one component. Material has no sku/barcode/weight/weightUnit yet (greenfield).

5. Data Model Changes

One existing table extended; no new top-level models. New columns shown; existing columns elided.

model MaterialAttributePrice {
    // ...existing: id, isArchived, isDeleted, createdAt, updatedAt, materialId, Material...
    value             Decimal? @db.Decimal(10, 2)   // unit COST for this (cell, source)

    // axis cell — ALREADY nullable (PR #7211); MAT-0 does NOT change these.
    // All three null = the 0-axis material's price row (migrated from Material.unitCost).
    selectedXValueId  String?  @db.VarChar(21)
    selectedYValueId  String?  @db.VarChar(21)
    selectedZValueId  String?  @db.VarChar(21)

    // NEW — source dimension (both null = the "house" row = the variant itself)
    distributorId     String?  @db.VarChar(21)      // Company — the seller (null on house row)
    manufacturerId    String?  @db.VarChar(21)      // Company — whose version (a distributor may sell several)

    // SKU — meaning depends on the row: HOUSE row = your own (variant) SKU; SOURCE row = the distributor's SKU
    sku               String?  @db.VarChar(100)
    manufacturerSku   String?  @db.VarChar(100)     // per-source reference (maker's part #)

    // NEW — variant-intrinsic catalogue identity (set on the HOUSE row = the Shopify variant)
    barcode           String?  @db.VarChar(64)      // UPC/EAN/GTIN
    weight            Decimal? @db.Decimal(10, 3)
    weightUnit        String?  @db.VarChar(8)

    // NEW — procurement metadata (per SOURCE row; flat — tiered/qty discounts are MAT-9)
    listPrice         Decimal? @db.Decimal(10, 2)
    discountPercent   Decimal? @db.Decimal(5, 2)
    effectiveFrom     DateTime?
    effectiveTo       DateTime?
    minQty            Int?
    leadTimeDays      Int?
    packageQty        Decimal? @db.Decimal(10, 2)   // e.g. sold in boxes of 10 — recovered from the dropped ManufacturerProduct (needed by MAT-3/5/6)
    packageUnit       String?  @db.VarChar(50)
    isPreferred       Boolean  @default(false)
    isInStock         Boolean?

    Distributor       Company? @relation("DistributorPrices", fields: [distributorId], references: [id])
    Manufacturer      Company? @relation("ManufacturerPrices", fields: [manufacturerId], references: [id])

    // was @@unique([materialId, selectedXValueId, selectedYValueId]) — now includes the source:
    @@unique([materialId, selectedXValueId, selectedYValueId, selectedZValueId, distributorId, manufacturerId])
    @@index([distributorId])
    @@index([manufacturerId])
}

The house row IS the variant. The source-less (all-source-null) MAP row per cell is the variant’s canonical record — it holds the variant’s own sku, barcode, weight/weightUnit, and the house cost, and is what maps to a Shopify ProductVariant. Source rows are offers against it (distributor sku + cost + lead time). The plan must ensure one house row exists per cell (this also covers the “one house row per cell” half of the nullable-unique caveat below).
MySQL nullable-unique caveat (plan-level). MySQL treats NULLs in a unique index as distinct, so the relaxed @@unique will not stop two source-less “house” rows (all-null source) for the same cell, nor enforce one row per cell for 0-axis (all-null axes). The plan must enforce “one house row per cell” / “one row per (cell, source)” in the model layer (or via a generated key column). Flagging here so it’s not lost.

Why no enums: the model adds booleans + free-text SKU; no fixed-set field. If one is later added, use the app’s enum convention (Prisma enum + const-array + GraphQL enum, PascalCase — like ApprovalStatus).

6. Pricing Integration (the centerpiece)

effectivePrice (computed)

Per source row: effectivePrice = (discountPercent != null && listPrice != null) ? listPrice × (1 − discountPercent/100) : value (value = the unit cost). Computed in the model layer (so MCP reads it) and exposed on the GraphQL type.

Cheapest/preferred source for a cell (or material)

Among the active source rows (not deleted/archived; within [effectiveFrom, effectiveTo] as of now) for a given cell — or across all cells for the material-level any-cell case — resolve: preferred (isPreferred) wins if set, else lowest effectivePrice (Q-c). Fall back to the source-less house row, then (0-axis) Material.unitCost.

The bestAvailableCost() upgrade (signature unchanged)

bestAvailableCost(materialId):
    # source + house rows now all live in MaterialAttributePrice —
    # axis cells for dimensional materials, an ALL-AXES-NULL row for 0-axis.
    cost = cheapest/preferred ACTIVE source effectivePrice for the material   // NEW (MAT-0)
    if (cost != null) return cost
    house = latest source-less MaterialAttributePrice.value                   // incl. the 0-axis all-null row
    if (house != null) return house
    return Material.unitCost ?? null      # legacy fallback during the unitCost migration

This reworks today’s hasAxis branch (which sent 0-axis to unitCost and skipped MAP): 0-axis now resolves from the all-null MAP row, with unitCost only as a transitional fallback.

Net effect: resolveMaterialSellPrice, the resolvedSellPrice TableFeed column, and every WO/IE/LEM consumer now rest on real source cost where it exists — automatically. Per §4.2 the material-level hook is the any-cell path; callers needing a specific cell resolve that cell’s cheapest source and pass costPrice.
Keep the SQL mirror honest. resolvedSellPrice (TableFeed) mirrors the cost->sell tiers as SQL. The plan must update it to read the cheapest active source effectivePrice (a correlated subquery) so list views match the service.

7. Company & Catalogue-Readiness

  • Company detail tabs (by join-existence): a Products view for a company that appears as manufacturerId on any source row (materials it makes, SKUs); a Products & Pricing view for a company that appears as distributorId (material / its prices / lead time / preferred). Added to allTabOptions; no company-type gating.
  • Catalogue fields — the variant’s own sku, barcode, weight/weightUnit live on the MAP house row (per variant), not Material, because they’re size-specific (a 2″ vs 3″ elbow differ). Standard catalogue value now (own SKU, scan code, shipping weight); also the Shopify-forward set. No isPublishedToShopify; images via AssetReference (referenceTable = "Material").

8. API Surface

No new top-level GraphQL types — the source fields extend the existing MaterialAttributePrice type + its create/update inputs, plus a computed effectivePrice. Material gains bestDistributorCost (null when no active source). Mutations on MaterialAttributePrice with a source set validate it against a live MaterialCompany of the matching role (reject otherwise; new suppliers go through MAT-10’s confirm-then-create). MCP: extend the existing material-pricing tools (set/upsert a price row with a source) + a query for “sources for a material”; thin → model per the golden rule.

10. Open Questions / Decisions Needed

Q-a. Migrate the 0-axis price from unitCost into an all-null MAP row Decided

Axis columns are already nullable (PR #7211) — no schema-nullability work needed. The move: backfill existing Material.unitCost into an all-axes-null MaterialAttributePrice row (the house price), rework bestAvailableCost’s hasAxis branch to resolve 0-axis from MAP, and keep unitCost as a transitional read-fallback.

Decided (chat): yes — this is the whole point: 0-axis SKUs then carry multiple manufacturer/distributor sources exactly like dimensional cells. unitCost becomes legacy; deprecate/remove in a later cleanup once nothing reads it.

Q-b. Are Materials generic specs or already brand-specific? CEO / users

Does the team create generic Materials (“R-30 batts”) or brand-specific ones (“Owens-Corning R-30”)? The source-on-grid model works either way, but it decides data-entry conventions and how much the manufacturer dimension is used. Needs a business answer — ask CEO / users.

Lean: assume generic (sources differentiate) until told otherwise; nothing in the schema blocks the other choice.

Q-c. Cheapest vs preferred for the cost basis pricing

When an active isPreferred source exists but another is cheaper, which sets the LEM cost basis?

Lean: preferred-wins when set, else lowest effectivePrice. (Distinct from MAT-10’s display “no primary” — this is a per-price procurement choice.)

Q-d. SKU columns — one or three? scope

You asked for “a SKU column.” Since a row has both a distributor and a manufacturer, do we keep just sku (the orderable distributor SKU), or also carry manufacturerSku + upc for reference/Shopify?

Lean: ship sku now; add manufacturerSku/upc as optional reference columns (cheap, and barcode/upc is the Shopify-forward set).

Q-e. Removing a MaterialCompany still referenced by price rows data

With the gate, MAP source rows depend on a live MaterialCompany. When a user removes a MaterialCompany link that source price rows still reference (as distributorId/manufacturerId), do we block while referenced, cascade-archive the dependent price rows, or allow and leave orphaned price rows?

Lean: block while referenced — keeps the gate consistent both ways (no priced source that isn’t a declared supplier); the user archives the price rows first if they really mean to drop the supplier.

12. Acceptance Criteria

  • MaterialAttributePrice carries nullable distributorId/manufacturerId + sku (+ optional manufacturerSku/upc) + procurement metadata; a cell can hold many source rows + one house row.
  • One distributor can hold two rows for the same cell under different manufacturerIds, at different prices/SKUs.
  • 0-axis price lives in an all-axes-null MAP row (backfilled from Material.unitCost) and can carry sources; bestAvailableCost resolves 0-axis from MAP; unitCost kept as transitional fallback.
  • One-house-row-per-cell and one-row-per-(cell,source) are enforced (model layer, given the MySQL nullable-unique caveat).
  • effectivePrice = listPrice×(1−discount/100) when both present, else value; readable from GraphQL + model.
  • bestAvailableCost() returns the active cheapest/preferred source effectivePrice when one exists, else falls through to house/unitCost; signature unchanged; expired/archived excluded.
  • resolvedSellPrice TableFeed column reflects source cost (matches the service).
  • A source row’s distributorId/manufacturerId is rejected unless it references a live MaterialCompany of the matching role for that material; a not-yet-linked supplier is added via confirm-then-create; removal of a referenced link follows Q-e.
  • Company Products / Products & Pricing tabs show by join-existence; Material shows source pricing with a best marker.
  • The MAP house row carries the variant’s own sku/barcode/weight/weightUnit (not Material); no isPublishedToShopify; images via AssetReference.
  • No ManufacturerProduct/DistributorPrice models; build + prettier pass.
