Mobile Photo Question · Polish (Form Builder + Renderer)

The "photo" question type on mobile forms is half-finished — small thumbnails in a 4-column grid, awkward delete with no confirm, no captions, no min/max enforcement. Techs avoid filling photo questions and text photos to admins instead. This spec extracts the photo renderer into its own component, adds the missing affordances (2-column thumbnails, captions, min/max counter, swipe-to-delete with confirm, action-sheet camera/gallery picker, EXIF capture, server-side compression), and exposes per-question config in the desktop form builder. Path B build of WOX-08; closes the second of three #8 loose threads.

Estimate: 2-3 days Sequence: 1.33, parallel with WO-21 Requires: existing form infrastructure (F-01 form builder + mobile QA renderer) Enables: Closes Emma's #8 loose thread (photo polish); benefits all forms in the platform, not just WO forms

1. Business Case

The PHOTO question lives inline inside the mobile QA form switch (QAForm.tsx ~lines 689–801) — not a dedicated component, no per-question configurability, no captions, no min/max, no delete confirmation. Three pain points reported from the field:

  • Techs can't tell which photo is which after upload — no captions, tiny thumbnails. Forms become a wall of indistinguishable squares.
  • One tap on the wrong × deletes a photo with no confirmation. Lost evidence on safety forms is bad.
  • HIRA and condition-survey forms need a minimum number of photos to be compliant, but the mobile renderer can't enforce it. Form authors can't even ask for it.

This spec brings the photo question to the level of polish the rest of Appello's mobile UX has reached. Although it's tracked under the WO 1.33 sprint slot (because that's where the demand surfaced — WO field workflows lean on photo questions), the polish benefits every form in the platform: HIRAs, equipment inspections, daily logs, condition surveys, customer sign-off forms.

2. Scope

Already Built

  • DONE Mobile QA form rendering infrastructure (QAForm.tsx) with PHOTO as an inline question type
  • DONE Desktop form builder (QuestionnaireAddEditForm.tsx) with per-question type configuration patterns (text, multiple choice, date, etc.)
  • DONE Asset upload pipeline + AssetReference polymorphic join — used by photo answers today
  • DONE Existing form save → JobSafetyForm submission record path

In Scope (WO-22)

  • IN Extract PhotoQuestion.tsx as a dedicated mobile component (sibling to other QuestionTypes), replacing the inline switch case in QAForm.tsx
  • IN Mobile renderer polish: 2-column thumbnail grid (was 4-column micro-grid); captions overlaid on each thumbnail; large "+ Add photo" CTA; swipe-to-delete (or large × with confirmation); min/max counter ("3 of 5 minimum") with progress styling
  • IN Action sheet on "+ Add photo" — Camera / Gallery / Cancel (when allowGalleryImport = true; otherwise Camera only)
  • IN Form builder config card (PhotoQuestionConfig.tsx) added to QuestionnaireAddEditForm.tsx — exposes the new per-question fields
  • IN Schema additions on SafetyFormQuestion: photoMin, photoMax, captionMode (const: OFF / OPTIONAL / REQUIRED), allowGalleryImport, storeExif. Migration backfills sensible defaults on existing photo questions (photoMax = 10, others off / unset).
  • IN Caption storage on the photo answer (exact location — extending AssetReference with a caption column vs a new SafetyFormPhotoAnswer table — is an implementation-plan call; this spec asserts that captions persist with the photo and are rendered in form review)
  • IN EXIF / GPS capture on upload when the question's storeExif = true; surfaced in form review (desktop)
  • IN Server-side compression on upload — max 2MB stored in long-term storage; original asset retained for 30 days then purged. Default behavior; not per-question configurable in V1.
  • IN Min-photo enforcement at form submission — save blocked with inline error when count is below photoMin; clear pointer to the offending question
  • IN Max-photo enforcement at upload — Add CTA disables and shows tooltip when at photoMax
  • IN EXIF stripped from customer-facing PDF exports of forms — privacy default; no per-question opt-out in V1

Out of Scope

  • OUT Photo annotation / drawing on photos — out of scope; that's a forms-track future
  • OUT Multi-photo selection from gallery (i.e., "import 5 at once") — V1 is one-at-a-time. Promote later if techs ask.
  • OUT Reordering thumbnails — chronological only in V1 (capture order)
  • OUT Per-question opt-out from server compression — every photo compresses to 2MB; the original is purged after 30 days regardless
  • FUTURE Live-camera annotations / overlays on capture (timestamp watermark, GPS pin overlay, etc.)
  • FUTURE Voice-captioning ("describe this photo") — pairs with WOX-19 mobile voice features

Decided

✓ DECIDED — Caption lives on Asset (universal)

Add caption String? @db.VarChar(500) to the existing Asset model. Decision rationale: captions are useful for any asset — equipment files, drawings, signature stamps, photos in any context — not just photo-question answers on safety forms. Putting the column on Asset makes captions universal at zero extra cost. One asset → one caption is a clean mental model; the rare multi-reference case (same photo, different captions in different contexts) can live in the wrapping entity's description.

Rejected alternatives: a new SafetyFormPhotoAnswer model (overkill, fragments asset metadata across two places); AssetReference.caption (allows divergent per-reference captions but adds complexity for a marginal use case).

✓ DECIDED — GPS + capture time on Asset; capturedAt distinct from createdAt

Add gpsLatitude, gpsLongitude, capturedAt to Asset. capturedAt is meaningfully different from createdAt: a tech captures a photo at 9am offline, app queues it, uploads on reconnect at 2pm — createdAt = 2pm (DB row), capturedAt = 9am (EXIF). Matters for form-review timestamps, "was this photo taken at the right time?" audits, and chronological sort across queued uploads.

✓ DECIDED — Upload-time compression with 30-day original retention

Compress to 2MB at upload; keep the original 30 days then purge via a daily cron. Predictable storage state; the field upload UX is already tolerable on most networks. The 30-day retention covers the typical dispute / RFI lookback window.

4. Data Model

4.1 SafetyFormQuestion — new fields

// Added to existing SafetyFormQuestion model.
// All five are nullable / defaulted so existing photo questions
// continue to work with reasonable defaults applied at migration.

photoMin            Int?    @default(0)
photoMax            Int?    @default(10)   // hard ceiling 25 enforced in resolver
captionMode         String  @default("OFF") @db.VarChar(20)  // OFF | OPTIONAL | REQUIRED
allowGalleryImport  Boolean @default(true)
storeExif           Boolean @default(false)

4.2 Asset — caption + EXIF capture (universal, not photo-question-specific)

// Added to existing Asset model. caption + GPS + capturedAt apply to
// every Asset, not just photo-question answers — captioning equipment
// files / drawings / etc. is a future-friendly side benefit.
//   - capturedAt is meaningfully distinct from createdAt: a photo
//     captured offline at 9am and uploaded at 2pm has createdAt=14:00,
//     capturedAt=09:00. Used for form-review timestamps and
//     chronological sort across queued uploads.
//   - GPS lat/long set at upload time when the SafetyFormQuestion has
//     storeExif = true (or any future caller opts in).

caption       String?   @db.VarChar(500)
gpsLatitude   Decimal?  @db.Decimal(10, 7)
gpsLongitude  Decimal?  @db.Decimal(10, 7)
capturedAt    DateTime?

@@index([gpsLatitude, gpsLongitude], map: "Asset_gps_idx")

4.3 Migration

ALTER TABLE `SafetyFormQuestion`
    ADD COLUMN `photoMin`           INT          NULL DEFAULT 0,
    ADD COLUMN `photoMax`           INT          NULL DEFAULT 10,
    ADD COLUMN `captionMode`        VARCHAR(20)  NOT NULL DEFAULT 'OFF',
    ADD COLUMN `allowGalleryImport` BOOLEAN      NOT NULL DEFAULT TRUE,
    ADD COLUMN `storeExif`          BOOLEAN      NOT NULL DEFAULT FALSE;

ALTER TABLE `Asset`
    ADD COLUMN `caption`      VARCHAR(500)   NULL,
    ADD COLUMN `gpsLatitude`  DECIMAL(10, 7) NULL,
    ADD COLUMN `gpsLongitude` DECIMAL(10, 7) NULL,
    ADD COLUMN `capturedAt`   DATETIME(3)    NULL,
    ADD INDEX `Asset_gps_idx` (`gpsLatitude`, `gpsLongitude`);

-- Backfill: existing PHOTO questions get default photoMax=10, others stay NULL.
UPDATE `SafetyFormQuestion`
SET    `photoMax` = 10
WHERE  `questionType` = 'PHOTO' AND `photoMax` IS NULL;

5. API Surface

5.1 Type extension

extend type SafetyFormQuestion {
  photoMin: Int
  photoMax: Int
  captionMode: String!          # OFF | OPTIONAL | REQUIRED
  allowGalleryImport: Boolean!
  storeExif: Boolean!
}

5.2 Mutations — config

The existing createQuestion / editQuestion mutations gain optional inputs for the new fields. photoMax is rejected if > 25 (hard ceiling). captionMode validated against the const list.

5.3 Mutations — Asset upload (caption + EXIF)

The existing Asset upload mutation gains optional caption + GPS + captured-at parameters. Caption is enforced when the target context (e.g., the photo-question answer the asset is being attached to) declares captionMode = REQUIRED — that check runs at the form-answer attachment point, not on the Asset upload itself.

# Asset upload (existing mutation, extended):
uploadAsset(
  ...existing inputs,
  caption:       String,    # optional; universal — not photo-specific
  gpsLatitude:   Decimal,   # optional EXIF
  gpsLongitude:  Decimal,   # optional EXIF
  capturedAt:    DateTime   # optional EXIF; falls back to now() if absent
): Asset!

# Form-answer photo attachment uses the existing AssetReference path:
# AssetReference (assetId, referenceTable = "SafetyFormQuestionAnswer",
#                 referenceId = answer.id). The asset's caption + EXIF
# fields are read from the Asset itself — no additional storage needed
# in the answer record.

5.4 Validation

  • Submit-form mutation rejects when any photo question has fewer photos than its photoMin; error payload identifies the question id
  • Photo upload mutation rejects when the form answer already has photoMax photos
  • Photo upload mutation rejects when captionMode = REQUIRED and caption is null/empty

7. Acceptance Criteria

  1. Mobile photo questions render in a 2-column thumbnail grid with caption overlays, large × delete buttons (with confirmation), and a min-counter badge ("3 of 5 minimum").
  2. Tapping "+ Add photo" presents an action sheet with Camera / Gallery / Cancel options when the question's allowGalleryImport is true; collapses to Camera only when false.
  3. Form authors can configure photoMin, photoMax, captionMode, allowGalleryImport, and storeExif per photo question in the desktop form builder.
  4. The photoMax input in the form builder rejects values greater than 25 (hard ceiling).
  5. Form submission is rejected server-side when any photo question has fewer photos than its photoMin; the error response identifies the offending question.
  6. The mobile renderer prevents adding more than photoMax photos by disabling the Add CTA and showing a tooltip.
  7. When captionMode is REQUIRED, the photo upload mutation rejects an empty caption; the renderer prompts for a caption inline after photo capture.
  8. When storeExif is true on the question, GPS lat/long and capture timestamp (capturedAt from EXIF, distinct from the row's createdAt) are stored on the resulting Asset; surfaced in the desktop form-review view as a small GPS badge + capture-time tooltip per photo.
  9. Captions are stored on Asset.caption directly (universal, not photo-question-specific); editable by the user during photo capture and reflected in form review.
  10. EXIF / GPS data is stripped from customer-facing PDF exports of forms regardless of the question's storeExif setting.
  11. Uploaded photos are compressed server-side to a maximum of 2MB; the original is retained 30 days then purged by a daily cron.
  12. Existing photo questions in production continue to work after migration with sensible defaults (max 10, no min, captions off, gallery on, EXIF off).
  13. The mobile renderer, form builder config, and server-side validation share a common source-of-truth for the const-based captionMode values (no duplicated string literals).
