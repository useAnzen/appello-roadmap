MAT-9: Discount Management — Buy-Side Discounts (Implementation Plan)

Self-contained execution plan. Another agent should be able to pick this up cold, run the steps in order, and ship a PR. File paths are relative to the monorepo root (apps/api, apps/frontend). Read Pre-flight first. Companion spec: uis-MAT-9-discount-management.html (this is the plan; that is the spec + decision log). Code blocks are drop-in starting points — match surrounding style, don’t reformat neighbours.

Overview & Outcome

MAT-9 makes negotiated supplier discounts first-class by extending the existing Discount + DiscountAssignment system — no new top-level model. After this lands:

  • A Discount can be buy-side: a new direction (Sell|Buy) + nullable distributorId (the supplier). Everything else — Percent/FixedAmount, value, name, effective dates, ad-hoc — is reused as-is.
  • The same discount attaches at any tier just by choosing what to assign it to: per-cell (the MaterialAttributePrice.discountId FK shipped by MAT-0), per-material / category (two new DiscountAssignment.referenceModel values: Material, MaterialGroup), or global (Company, reused — disambiguated by direction:Buy).
  • One new resolver, resolveBuyDiscount(distributorId, materialId, mapRow), walks the cascade (per-cell › material › category › global, most specific wins, active-date filtered) and feeds MaterialAttributePrice.effectivePrice + MaterialPricingService.bestAvailableCost() + the resolvedSellPrice SQL mirror. No service signature changes.
  • A per-supplier discount library + scope assignments are managed on the supplier Company detail page; the source-price row gets a per-cell discount picker (select existing / +ad-hoc).
The vast majority is reuse. Discount/DiscountAssignment are already on BaseAuditableModel with full CRUD, and the assignment GraphQL already exposes attachDiscount / detachDiscount / createAdHocDiscountAndAttach / reorderDiscountAssignments / syncDiscountAssignments / discountsForEntity. The genuinely new code is: 2 columns + 1 enum, 2 new referenceModels, the cascade resolver, the pricing-integration wiring, and one frontend tab.

Conventions

  • Golden rule: logic in models/ + services/; resolvers stay thin.
  • Enum convention (single source of truth): Prisma enum (PascalCase) + a const-array+type in types/, imported into the model’s modelFields as { type: "enum", options: { enums: [...x] } } and into GraphQL as ${x.join("\n")}. Mirror approvalStatuses (TimeSheetRecord) / DiscountType.
  • No instanceId — single-instance app; do not add tenant columns.
  • gql definitions at the bottom of files; no triple-quote GraphQL descriptions; React components as FC arrow fns; boolean/shorthand JSX props last.

What you are NOT doing

  • No new top-level model — the CEO draft’s standalone DistributorDiscount (and its dead manufacturerProductId) is dropped; it duplicated Discount.
  • No per-job discount override (Vanos “override within a Job, per sheet”) — deferred. Future home: allow Job on the buy side and consult it ahead of the supplier tiers. Do not build it now.
  • No volume/quantity-break discounts; no price-book import (MAT-3 populates these same structures); no auto-application to customer invoices; no mobile.
  • No change to any sell-side behaviour — existing discounts backfill to direction:Sell and resolve exactly as today.

Add the cascade resolver — returns the most-specific active buy-side discount for a (distributor, material, cell), or null:

// Rank: per-cell(4, the row FK) > Material(3) > MaterialGroup(2) > Company/global(1).
public async resolveBuyDiscount(
    distributorId: string,
    materialId: string,
    mapRow: { discountId: string | null; materialGroupId: string }
): Promise<IDiscount | null> {
    const now = new Date();
    const activeDiscount = {
        isDeleted: false, isArchived: false,
        direction: "Buy", distributorId,
        AND: [
            { OR: [{ effectiveFrom: null }, { effectiveFrom: { lte: now } }] },
            { OR: [{ effectiveTo: null }, { effectiveTo: { gte: now } }] }
        ]
    };

    // 4. per-cell — the row's own FK
    if (mapRow.discountId) {
        const cell = await prisma.discount.findFirst({ where: { id: mapRow.discountId, ...activeDiscount } });
        if (cell) return cell as IDiscount;
    }

    // 3→1. material → category → global, via buy-side assignments for THIS distributor.
    // One query, then pick by rank (avoids 3 round-trips).
    const rows = await this.prisma.findMany({
        where: {
            isDeleted: false, isArchived: false,
            OR: [
                { referenceModel: "Material",      referenceId: materialId },
                { referenceModel: "MaterialGroup", referenceId: mapRow.materialGroupId },
                { referenceModel: "Company",       referenceId: distributorId }   // global
            ],
            Discount: { ...activeDiscount }
        },
        include: { Discount: true }
    });
    const rank: Record<string, number> = { Material: 3, MaterialGroup: 2, Company: 1 };
    const best = rows.sort((a, b) => (rank[b.referenceModel] ?? 0) - (rank[a.referenceModel] ?? 0))[0];
    return best ? (best as unknown as { Discount: IDiscount }).Discount : null;
}
Why the Company/global assignment exists: a global buy-side discount is a DiscountAssignment(referenceModel:"Company", referenceId:distributorId) whose Discount.direction = Buy. direction on the Discount is what stops it colliding with a sell-side discount on the same Company. The library query (Step 4) is the picker source; assignment is how a library discount becomes a scoped, applied tier.
Tie-break within a tier: if a distributor has two active discounts at the same tier (e.g. two Material assignments for one material), pick deterministically — recommend lowest resulting cost (best for the buyer), else most-recently-created. Apply the same rule in the resolver and the SQL mirror (Step 6). Flag for review.

6.1 resolvedSellPrice SQL mirror — widen to the cascade

MAT-0’s mirror joins Discount on map.discountId (per-cell only). Replace that single join with a per-row resolved (type, value) derived from a ranked UNION over the tiers, all direction='Buy' + active-dated, for the row’s distributorId; then apply it to COALESCE(map.listPrice, map.value) exactly as MAT-0 does:

-- per source row `map` (joined to its Material `mat` for materialGroupId):
LEFT JOIN LATERAL (
    SELECT t.type, t.value
    FROM (
        -- 4. per-cell
        SELECT 4 AS rank, dd.type, dd.value FROM Discount dd
          WHERE dd.id = map.discountId AND dd.direction='Buy'
            AND dd.isDeleted=0 AND dd.isArchived=0
            AND (dd.effectiveFrom IS NULL OR dd.effectiveFrom <= NOW())
            AND (dd.effectiveTo   IS NULL OR dd.effectiveTo   >= NOW())
        UNION ALL
        -- 3/2/1. material / category / global via assignments for this distributor
        SELECT (CASE da.referenceModel WHEN 'Material' THEN 3 WHEN 'MaterialGroup' THEN 2 ELSE 1 END) AS rank,
               dd.type, dd.value
          FROM DiscountAssignment da
          JOIN Discount dd ON dd.id = da.discountId
            AND dd.direction='Buy' AND dd.distributorId = map.distributorId
            AND dd.isDeleted=0 AND dd.isArchived=0
            AND (dd.effectiveFrom IS NULL OR dd.effectiveFrom <= NOW())
            AND (dd.effectiveTo   IS NULL OR dd.effectiveTo   >= NOW())
         WHERE da.isDeleted=0 AND da.isArchived=0
           AND ( (da.referenceModel='Material'      AND da.referenceId = map.materialId)
              OR (da.referenceModel='MaterialGroup' AND da.referenceId = mat.materialGroupId)
              OR (da.referenceModel='Company'       AND da.referenceId = map.distributorId) )
    ) t
    ORDER BY t.rank DESC
    LIMIT 1
) disc ON TRUE
-- effectivePrice for the row =
--   CASE WHEN disc.value IS NULL THEN map.value
--        WHEN disc.type='Percent' THEN COALESCE(map.listPrice,map.value)*(1-disc.value/100)
--        ELSE GREATEST(COALESCE(map.listPrice,map.value)-disc.value, 0) END
Keep the mirror and the service in lockstep (same lesson as MAT-0). The rank DESC LIMIT 1 ordering must match resolveBuyDiscount()’s rank + the Step-5 tie-break. mat is the Material join already present in the cost-basis query (for materialGroupId) — reuse it.
