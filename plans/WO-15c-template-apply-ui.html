WO-15c Work Orders Implementation Plan

Work Order Templates · Apply on WO Create + Planned Crew Advisory

Operational layer on top of WO-15a (backend) and WO-15b (settings UI). The dispatcher picks a template at the top of the WO create form — desktop AND mobile; the form draft hydrates from previewWorkOrderTemplate across every section that has a slot for template content; structured equipment plans surface as launchers into the existing EquipmentAssignment form; structured labor plans render as a read-only advisory; submit serializes the current draft into the workOrderTemplateApplication input on createJob. Post-save (desktop), the same labor advisory continues on the WO detail Schedule tab as a live tally sidebar.

Step 1 · Form-state architecture for the create form

Before any picker UI, we need the form draft buffer to be capable of holding template-derived rows and tracking which rows came from the template. This is a thin extension of whatever state the existing WO create form already exposes via useForm.

1.1 New types — useWorkOrderTemplateApply.types.ts

Co-located with the apply hook (Step 3). Defines the in-form draft shapes that the hook hydrates and that submit serializes.

1.2 Where the state lives

All of the above lives as a single useState<IWorkOrderTemplateApplyState> inside the WO create form component (next to the existing useForm()). The apply hook (Step 3) returns setters that mutate this slice. Checklist/Materials rows that are also tracked by the existing line-item state in useForm are kept in one place — the apply state — and the regular line-item sections receive their data via props from the form (no double bookkeeping).

Why not push everything into the existing useForm body? The provenance/archive bookkeeping is template-specific; folding it into useForm would pollute every WO create form whether or not a template is applied. Keeping it adjacent and feeding the existing sections via props keeps the WO create form's core state clean.

Step 3 · Apply hook — fetch preview, hydrate draft, track provenance

3.1 Hook surface

export const useWorkOrderTemplateApply = () => {
    const [state, setState] = useState<IWorkOrderTemplateApplyState>(EMPTY_STATE);
    const [previewQuery] = useLazyPreviewWorkOrderTemplateQuery({ fetchPolicy: "no-cache" });

    const apply = async (templateId: string): Promise<void> => { … };
    const switchTo = async (templateId: string): Promise<void> => { … };  // assumes confirm already happened

    // Row-level setters used by every section component.
    const setChecklistItems = (next: IChecklistDraft[]) => { … };
    const archiveChecklistRow = (rowId: string) => { … };
    const setMaterialItems = (next: IMaterialDraft[]) => { … };
    const archiveMaterialRow = (rowId: string) => { … };
    const setFieldDefault = (documentAttributeId: string, value: string) => { … };
    const setEquipmentPlanSelections = (templatePlanId: string, selections: IDeferredEquipmentAssignment[]) => { … };

    return { state, apply, switchTo, setChecklistItems, archiveChecklistRow, setMaterialItems, archiveMaterialRow, setFieldDefault, setEquipmentPlanSelections };
};

3.2 apply(templateId) behavior

  1. Call previewQuery({ variables: { templateId } }).
  2. Map each preview.checklistItems[] to IChecklistDraft with rowId: nanoid(), templateChecklistItemId: item.id, provenance: "template".
  3. Same mapping for materials and field defaults.
  4. For equipment plans, build IEquipmentPlanDrafts with selections: [] (user hasn't picked specific equipment yet).
  5. For labor plans, build ILaborAdvisoryRow entries (read-only — they never become editable rows on the create form).
  6. For form wrappers, build IFormsSummaryDraft entries with the resolved form name (already in the preview payload).
  7. setState replaces the entire applyState in one pass; existing user-added rows in the form's regular state are preserved by the section components themselves.

3.3 Row identity rules (provenance lifecycle)

  • Template-seeded row: provenance: "template", templateChecklistItemId: <id>. Editing the row's label/description bumps to provenance: "user-edit" but keeps the template id (so we can preserve the "this came from the template, but it's been changed" indicator if product wants it in V2 — for V1 just show FROM TEMPLATE as long as the row originated there).
  • Row added inline by the user: provenance: "user-add", templateChecklistItemId: null.
  • Row removed by the user from the template seed: moved to archivedChecklistRowIds[], removed from checklistItems[]. This is just so the row stays hidden in the UI without us forgetting it existed; the archived list is not sent to the server (the resolver only sees what's in checklistItems).

3.4 Switch flow

switchTo is identical to apply but assumes the confirmation modal (Step 4) has already resolved. It wholesale replaces state — anything the user manually added or edited during the previous template's session is wiped, matching the "Replace" semantics in Mockup 5.

What about user-added rows from the underlying form (non-template)? Those live in the existing form's useForm state, not in applyState. Switching templates only blows away the applyState slice. The standard WO create form fields stay as the user left them.

Step 4 · Switch-template confirmation modal

Component: WorkOrderTemplateSwitchModal.tsx, co-located with the banner.

4.1 Flow

  1. Banner's "Switch template" button reuses the same CustomCombobox dropdown; selecting a different template fires onSwitchRequested(newTemplateId).
  2. Parent form opens the modal via the existing useConfirm hook from @useanzen/shared-utils with custom body content (current template name → new template name; warning that manual edits in this session will also be cleared).
  3. On confirm: call applyHook.switchTo(newTemplateId).
  4. On cancel: state untouched, banner reverts to applied state with the current template still showing.

The Mockup 5 visual (red destructive button) is achieved via the useConfirm options that already support a danger variant — no bespoke modal component required if the existing API covers it. If the styling doesn't match, drop in a thin WorkOrderTemplateSwitchModal.tsx wrapping Modal from @useanzen/ui; do not reach for raw HTML.

Step 5 · Field defaults + "FROM TEMPLATE" indicator wiring

5.1 Template-tier default resolution

WO-15a's previewWorkOrderTemplate already resolves the value tier per DAA (template > DAA defaultValue). When a template is applied, the apply hook builds an IFieldDefaultDraft[] keyed by documentAttributeId.

5.2 Form-render context

The DAA-driven WO field renderer (existing code path) currently consults the DAA defaultValue through whatever context it already reads. Extend that consumption:

  • Add an optional templateFieldDefaults input to the existing context (find the provider at the top of the WO create form's DAA renderer).
  • The renderer's "compute initial value" function checks templateFieldDefaults[documentAttributeId]?.value first, falls back to DAA defaultValue, falls back to empty.
  • When the user types into the field, the renderer calls the existing field setter — and also calls applyHook.setFieldDefault(documentAttributeId, newValue) so the apply state stays the source of truth for the submit payload.
Don't try to merge into useForm values directly. Field values are already managed by the existing DAA renderer's state. The apply state stores them only so we can build the fieldDefaults array on submit. Reading the value from two places creates drift — the renderer wins for display; the applyState mirror is for serialization.

5.3 "FROM TEMPLATE" badge

Tiny pill component co-located: FromTemplateBadge.tsx (single 8-line FC). Used wherever a row, field, or section header needs the indicator. No styling override knobs — it's the same pill everywhere (semantic colors per CLAUDE.md: bg-success-light text-on-success-light).

The DAA renderer wraps the field label in <FormControlLabel> already (or however the existing labels render); add a sibling <FromTemplateBadge> when templateFieldDefaults[id] exists.

Step 6 · Checklist + Materials seeded rows

6.1 Checklist section

The WO checklist editor on the create form (built in WO-14, mounted as WorkOrderChecklistSection on the existing create form) already accepts an items array and onChange callback per the WO-14 plan. Extend its props to receive the apply hook's row list:

If WorkOrderChecklistSection currently controls its own state internally, lift the state up — same pattern as WO-15b §4b (controlled component contract). The component becomes a presentational/coordinator layer that delegates to the parent for canonical state.

6.2 Photo-required carry-through

Per AC 5 (spec § 7): each IChecklistDraft preserves photoRequired from the template snapshot. The checklist row component (built in WO-14, ChecklistItemRow) already renders the camera glyph when this flag is set — no new code, just make sure the field plumbs through.

6.3 Materials section

Same pattern as checklist: the existing WO Materials section accepts items / onItemsChange / onArchiveRow / renderRowBadge. Template materials seed in with their quantity (variant TBD per Mockup 2 — the row is a placeholder until the user picks a specific MaterialVariant, but it serializes as-is on submit because the resolver in WO-15a accepts variant-less seeds).

6.4 "FROM TEMPLATE" provenance after edit

Per the Step 3.3 rule, editing a template-seeded row bumps it to provenance: "user-edit". For V1, renderRowBadge shows the badge for both "template" and "user-edit" rows (origin-based). Per AC 3 (spec § 7), the badge "persists for traceability while the value is the template's default" — V1 keeps it simple and shows the badge as long as the row was template-originated, regardless of subsequent edits.

Step 7 · Free-form Labor/Equipment line item seeding

The WO-15a snapshot returns labor plans and equipment plans in the standard preview. Per WO-15b/WO-15a, plans are structured when they have a tradeLevelId (labor) or equipmentCategoryId (equipment), and free-form when those FK fields are null.

7.1 Routing in the apply hook

preview.laborPlans.forEach((plan) => {
    if (plan.tradeLevelId) {
        laborAdvisory.push({ … });            // -> structured -> advisory callout (Step 9)
    } else {
        labourLineItems.push({                 // -> free-form -> regular WO Labor section
            templateLaborPlanId: plan.id,
            description: plan.description,
            plannedHours: plan.plannedHours,
            provenance: "template"
        });
    }
});

preview.equipmentPlans.forEach((plan) => {
    if (plan.equipmentCategoryId) {
        equipmentPlans.push({ … });           // -> structured -> selection prompt (Step 10)
    } else {
        equipmentLineItems.push({              // -> free-form -> regular WO Equipment section
            templateEquipmentPlanId: plan.id,
            description: plan.description,
            quantity: plan.quantity,
            plannedHours: plan.plannedHours,
            provenance: "template"
        });
    }
});

7.2 Where the free-form items go

Free-form labor and equipment line items materialize in the regular WO Labor / WO Equipment line item sections via the same prop pattern as checklist/materials. They are fully editable: the user can change description, hours, qty, even delete them. They serialize through the standard WO line item path on createJob (not the workOrderTemplateApplication input) — that's why the apply hook tags them with provenance: "template" for the badge but otherwise treats them like any other line item.

Why are free-form line items not in workOrderTemplateApplication? The application input (per WO-15a) is for things that need the audit FK linking the row back to the template's plan — structured equipment selections, etc. Free-form rows are just text+numbers and have no equivalent server-side concept, so they go through the existing line item pipeline. The cost is that "this WO line item came from a template" is not preserved server-side — V1 accepts that; we can revisit if reporting needs it.

Step 10 · Structured Equipment prompts + EquipmentAssignment deferred-commit

10.1 Prompt component — WorkOrderTemplateEquipmentPrompt.tsx

Per equipment plan row, two states (Mockups 2 + 3):

  • Unresolved: amber banner with the plan's qty + category + planned hours, "Open assignment form" button.
  • Resolved: green row showing each selected equipment + optional operator/dates, "Edit" button to re-open the form.

Multiple selections per plan are supported (qty > 1 implies multiple specific assets) — the prompt shows a row per selection.

10.2 Existing EquipmentAssignment form — deferred-commit mode (desktop + mobile)

Both apps/frontend and apps/mobile have their own EquipmentAssignment form. Apply the same two prop additions to both; the deferred-commit contract is identical. Add two new props:

interface IEquipmentAssignmentFormProps {
    // ...existing props
    equipmentCategoryFilter?: string;   // pre-applies category, hides category picker
    deferredCommit?: {                  // when set, form returns payload to caller instead of writing
        onSubmit: (payload: IDeferredEquipmentAssignment) => void;
        existing?: IDeferredEquipmentAssignment;   // for re-edit
    };
}
  • When deferredCommit is set, the form's normal "submit creates an EquipmentAssignment row" wiring is bypassed — it just builds the payload and hands it back to onSubmit.
  • When equipmentCategoryFilter is set, the category field is locked and the equipment picker is constrained to that category. No backend change — Solr/TableFeed already accepts a category filter via the standard where.
Open this form via the existing flyout/modal mechanism the EquipmentAssignment surface already uses (likely useFlyout per CLAUDE.md UI conventions). The prompt component dispatches the flyout open call with the deferred-commit props and consumes the resolved payload via setEquipmentPlanSelections on the apply hook.

10.3 Submit-time commit

On createJob submit (Step 11), the apply hook serializes resolved selections into equipmentSelections on workOrderTemplateApplication. Per spec § 7 AC 12, EquipmentAssignment rows are created in the same transaction as the Job (WO-15a's resolver handles this — see WO-15a §8c). Unresolved plans (no selections) are not blocking — the structured plan stays as advisory on the WO snapshot, and the dispatcher can fill it later from the WO-16 EquipmentAssignment surface (Pending Business Decision §1, leaning "allow").

10.4 Operator / dates / notes passthrough

The IDeferredEquipmentAssignment payload carries every field the EquipmentAssignment form collects (operatorUserId, checkoutAt, checkinAt, notes). The workOrderTemplateApplication.equipmentSelections input must accept these as part of each selection — confirm WO-15a's input shape covers them; if not, this surfaces a small WO-15a addendum (extend the existing input, not a separate mutation).

Step 11 · Submit — build workOrderTemplateApplication payload

11.1 Helper — buildWorkOrderTemplateApplicationInput.ts

Co-located with the apply hook. Pure function: takes IWorkOrderTemplateApplyState, returns the workOrderTemplateApplication input shape from WO-15a (or null if no template applied).

export const buildWorkOrderTemplateApplicationInput = (
    state: IWorkOrderTemplateApplyState
): WorkOrderTemplateApplicationInput | null => {
    if (!state.appliedTemplateId) return null;
    return {
        templateId: state.appliedTemplateId,
        checklistItems: state.checklistItems.map((row) => ({
            id: row.templateChecklistItemId,            // null when user-added
            label: row.label,
            description: row.description ?? null,
            orderNo: row.orderNo,
            photoRequired: row.photoRequired
        })),
        materialItems: state.materialItems.map((row) => ({
            id: row.templateMaterialItemId,
            materialId: row.materialId ?? null,
            materialVariantId: row.materialVariantId ?? null,
            quantity: row.quantity,
            description: row.description ?? null
        })),
        formWrapperIds: state.formsSummary.map((f) => f.templateFormWrapperId),
        fieldDefaults: state.fieldDefaults.map((d) => ({
            documentAttributeId: d.documentAttributeId,
            value: d.value
        })),
        equipmentSelections: state.equipmentPlans
            .filter((p) => p.selections.length > 0)
            .flatMap((p) => p.selections.map((s) => ({
                equipmentPlanId: p.templatePlanId,
                equipmentId: s.equipmentId,
                operatorUserId: s.operatorUserId ?? null,
                checkoutAt: s.checkoutAt ?? null,
                checkinAt: s.checkinAt ?? null,
                notes: s.notes ?? null
            })))
    };
};

11.2 Wire into the existing createJob call

The WO create form's onSubmit already calls useCreateJobMutation. One-line addition:

const result = await createJob({
    variables: {
        data: {
            ...existingJobInput,
            workOrderTemplateApplication: buildWorkOrderTemplateApplicationInput(applyState)
        }
    }
});

If workOrderTemplateApplication is null, the mutation behaves exactly as it does today (no-op extension).

11.3 Post-submit behavior

  • WO-15a's resolver bumps WorkOrderTemplate.lastUsedAt + useCount as part of the apply path.
  • The returned Job's appliedWorkOrderTemplateId is set — the redirect to the detail page lands on a WO that will trigger the Step 12 advisory.
  • If the mutation fails, the apply state is preserved — the form re-renders with the same hydrated content the user was working on. No retry / undo logic in V1.

Step 12 · Planned Crew advisory sidebar (post-save, WO detail Schedule tab — desktop only)

This is the second half of WO-15c — the post-save companion to the create-form advisory. Per the spec In Scope list, the labor advisory continues on the WO detail Schedule tab with a live tally.

Desktop only. The post-save Schedule tab + Planned Crew sidebar live on the WO detail page, which is desktop in 1.33 (per WO-16). The create-form template picker (Steps 2-11) ships on both desktop and mobile; the post-save advisory is desktop-only because the surface it lives on doesn't yet exist on mobile.

Client-side, no new GraphQL needed. For each plan with a tradeLevelId:

const scheduledCount = jobSchedules.filter((s) =>
    s.User?.EmployeeAgreement?.TradeLevels?.some((tl) => tl.id === plan.tradeLevelId)

            .if(hasTemplate && laborPlans.length > 0, "col-span-2")
            .list()}>
            <JobScheduleCalendarPage {...existingProps} />
        </div>
        {hasTemplate && laborPlans.length > 0 && (
            <WorkOrderPlannedCrewAdvisory
                laborPlans={laborPlans}
                jobSchedules={data.job.JobSchedules ?? []}
            />
        )}
    </div>
);

12.5 Live tally during the user's session

The tally just consumes whatever JobSchedules Apollo cache holds for the Job. When the user drags a user onto the calendar and the existing JobSchedule mutation (from WO-16 or whatever predates it) writes a new row, Apollo's cache update on that mutation refreshes the parent query — the advisory re-renders with the new count automatically.

If the JobSchedule mutation in the existing codebase doesn't already refetch / update job.JobSchedules, add a refetchQueries entry on the mutation call site pointing at the Schedule tab's query. Single-line change.
