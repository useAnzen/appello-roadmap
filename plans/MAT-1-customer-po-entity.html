MAT-1: Customer PO Entity (Implementation Plan)

Self-contained execution plan. Another agent should be able to pick this up cold, run the steps in order, and ship a PR. Every file path is relative to the monorepo root (apps/api, apps/frontend). Read the Pre-flight section first. Companion spec: uis-MAT-1-customer-po-entity.html (this file is the plan; that is the spec + decision log). Code blocks are drop-in starting points grounded in the named precedents on Release-v1.33.0 — match surrounding style, don’t reformat neighbours.

Overview & Outcome

The customer PO is already a first-class entity: PurchaseOrder (a deduplicated PO number) + a polymorphic PurchaseOrderAssignment join that ties it to Jobs / EstimateChangeOrderRecords / JobBills, all wired into the shipped multi-PO roll-up and invoice dropdowns. MAT-1 enriches that entity — it does not rebuild it. After this lands:

  • PurchaseOrder carries metadata: companyId (the customer who issued it), contactId, issuedDate, amount, terms, description — additive columns, no data backfill.
  • PurchaseOrderModel is brought into the BaseAuditableModel framework (it is a bespoke class today) so the new fields get standard validation + permissions, and terms / description are declared type: "wysiwyg". All existing bespoke methods (getAllForJob, handleCreate/EditPOSync, …) are preserved verbatim — existing consumers are unaffected.
  • A PO detail page at /purchase-orders/[id] with tabs: Overview (metadata), Linked Records (read from PurchaseOrderAssignment — Job / Estimate / CO / Invoice), Files (the customer’s signed PO PDF via Asset / AssetReference).
  • A Purchase Orders tab on the Company detail page, filtered by the new companyId.
Decisions baked into this plan (settled with the user; see spec).
  • Enrich, don’t rebuild: extend the live PurchaseOrder + keep PurchaseOrderAssignment. No direct jobId FK (job linkage stays via assignments).
  • Deferred to MAT-5 (supplier PO): type (CustomerPO/SupplierPO), status lifecycle, PurchaseOrderLineItem, and SPO-#### auto-numbering. poNumber stays user-entered (a customer PO number comes from the customer).
  • No instanceId — Appello is single-instance; models do not carry one (the live PurchaseOrder has none). Do not add it.
  • No custom fields (the DocumentAttribute system) — PO fields are few and stable; fixed columns are correct.
  • No standalone global /purchase-orders index list — reach a PO via its job, the company tab, or a linked record.

This is an EXTENSION + a framework conversion — not a new model

Everything already exists: model PurchaseOrder + model PurchaseOrderAssignment (schema.prisma:5566–5590), the model class apps/api/src/models/PurchaseOrder.ts, the resolver apps/api/src/graphql/models/PurchaseOrder.ts (registered in graphql/schema.ts), and the type apps/api/src/types/PurchaseOrder.types.ts. Do not scaffold a new model and do not run new-data-model. MAT-1 adds columns + methods to these files. The one structural change is that PurchaseOrderModel is a plain hand-rolled class today and must become a BaseAuditableModel subclass (Step 3) to declare fields the standard way — this is how type: "wysiwyg" is even expressible.

Why the conversion is safe. BaseAuditableModel needs no specific audit columns — DbModelBase.createItem only writes createdById if the model declares it (_DbModelBase.ts:1350), and MaterialAttributePrice and Note both extend it with no createdById/updatedById columns. The four abstract methods can be no-ops (as in MaterialAttributePrice). Existing consumers call the bespoke methods (getAllForJob, handleCreate/EditPOSync, assignExistingPOToEntity, …), which you keep unchanged — the conversion adds base methods, it does not alter the existing ones.

3.2 Convert the class — add the framework scaffold, keep every existing method

Change the class declaration from a bare class PurchaseOrderModel { … } to a BaseAuditableModel subclass, and add the required members at the top. Do not delete or alter the existing methods (getForEntity, getAllForJob, checkForPoForEntity, findOrCreateForJob, assignToEntity, removeAssignmentsForEntity, cleanupOrphanedPurchaseOrders, syncEntityPurchaseOrders, assignExistingPOToEntity, transferECOPurchaseOrdersToJob, handleCreatePOSync, handleEditPOSync) — they stay verbatim below the new scaffold.

import { BaseAuditableModel } from "./base/_BaseAuditableModel";
import { FullModel, IField, IPurchaseOrder } from "../types";
import prisma from "./_prismaClient";
import { nanoid } from "nanoid";

class PurchaseOrderModel extends BaseAuditableModel<IPurchaseOrder> {
    public name = "PurchaseOrder";
    name_plural = "PurchaseOrders";

    protected prisma = prisma.purchaseOrder;

    protected modelFields: IField<IPurchaseOrder>[] = [
        {
            name: "poNumber",
            type: "string",
            options: {
                isRequiredOnCreate: true,
                canCreate: true,
                canEdit: true,
                isFilterable: true,
                isSortable: true,
                isSelectable: true
            }

        { name: "contactId", type: "string", options: { canCreate: true, canEdit: true } },
        { name: "issuedDate", type: "datetime", options: { canCreate: true, canEdit: true, isSortable: true } },

        { name: "description", type: "wysiwyg", options: { canCreate: true, canEdit: true } }

    // methods below; an orphaned PO is already soft-deleted via cleanupOrphanedPurchaseOrders).
    public archiveChildren(): Promise<void> { return Promise.resolve(); }
    public restoreChildren(): Promise<void> { return Promise.resolve(); }
    public async getRelatedDeleteCount(): Promise<Record<string, number>> { return {}; }
    public async deleteChildren(): Promise<void> { return Promise.resolve(); }

    // ===== existing bespoke methods stay here, unchanged =====
    // getForEntity, getAllForJob, checkForPoForEntity, findOrCreateForJob,
    // assignToEntity, removeAssignmentsForEntity, cleanupOrphanedPurchaseOrders,
    // syncEntityPurchaseOrders, assignExistingPOToEntity, transferECOPurchaseOrdersToJob,
    // handleCreatePOSync, handleEditPOSync
Permissions — no new PO permission; governance stays with the parent. The base only enforces a permission check for models registered in permissionsByReferenceModel — “child/detail models without their own permission mapping are allowed through; their parent resolver is responsible for authorization” (_DbModelBase.ts:1181–1205). MaterialAttributePrice converts the same way with no permission of its own. So do NOT seed a purchaseOrder permission and do NOT add PurchaseOrder to permissionsByReferenceModel — base create/edit/delete pass straight through, and PO creation/sync stays governed by the Job / ECO / JobBill flows exactly as today (a PO is only ever born through one of those). The only surfaces that need a gate are the new direct-access ones (detail page + Company tab) — they reuse an existing permission (see Step 5), not a new one.

3.3 New methods — only what the base doesn’t already give you

No custom create / edit / getById. The six metadata fields are plain modelFields (3.1–3.2), so the base methods handle them directly: createItem(data, userId) and editItem(id, data, userId) validate + persist them (that is the entire point of declaring them), and getItem(id, userId) returns the record by id. The detail page’s nested data (Company, Contact, Files, linked records) is populated by the GraphQL field resolvers (Step 4), so no eager-include fetch is needed either. Wire the GraphQL Query/Mutation straight to the base methods (Step 4).

Add only the two things the base genuinely doesn’t cover — a company-filtered list and the Asset file helpers (same pattern as Note):

// Company PO tab.
public async getForCompany(companyId: string): Promise<IPurchaseOrder[]> {
    return prisma.purchaseOrder.findMany({
        where: { companyId, isDeleted: false },
        orderBy: { issuedDate: "desc" }
    }) as Promise<IPurchaseOrder[]>;
}

// Files — reuse the Asset reference API.
public async attachFile(purchaseOrderId: string, assetId: string): Promise<void> {
    await new Asset().addReferencesToAsset(
        [{ referenceTable: "PurchaseOrder", referenceId: purchaseOrderId }],
        assetId
    );
}
public async detachFile(purchaseOrderId: string, assetId: string): Promise<void> {
    await new Asset().removeReferencesFromAsset(
        [{ referenceTable: "PurchaseOrder", referenceId: purchaseOrderId }],
        assetId
    );
}
public async getFiles(purchaseOrderId: string) {
    return prisma.asset.findMany({
        where: {
            References: { some: { referenceTable: "PurchaseOrder", referenceId: purchaseOrderId } },
            isDeleted: false
        }
    });
}
The bespoke in-context create paths are unchanged. findOrCreateForJob and handleCreate/EditPOSync still call prisma.purchaseOrder.create directly (they only set poNumber) — a PO born by typing a number on a job/estimate/invoice needs no metadata. Metadata is added later by editing the PO (base editItem) from the detail page.

type PurchaseOrder {

    amount: Float
    terms: String
    description: String
}

extend type Query {
    purchaseOrder(id: ID!): PurchaseOrder

    # existing, unchanged: purchaseOrdersForJob(jobId), checkForPoForEntity(...)
}

extend type Mutation {
    createCustomerPurchaseOrder(input: CustomerPurchaseOrderInput!): PurchaseOrder!
    editCustomerPurchaseOrder(id: ID!, input: CustomerPurchaseOrderInput!): PurchaseOrder!

    detachFileFromPurchaseOrder(purchaseOrderId: ID!, assetId: ID!): Boolean!

Add the field resolvers to Resolvers (alongside the existing PurchaseOrderAssignments resolver) and wire Query/Mutation to the model. Company / Contact resolve by id; Files calls getFiles:

Resolvers: {
    PurchaseOrderAssignments: async ({ id }) => /* existing */,
    Company: async ({ companyId }) => companyId ? prisma.company.findUnique({ where: { id: companyId } }) : null,
    Contact: async ({ contactId }) => contactId ? prisma.contact.findUnique({ where: { id: contactId } }) : null,
    Files: async ({ id }) => new PurchaseOrderModel().getFiles(id)
},
Query: {
    // existing purchaseOrdersForJob, checkForPoForEntity ...
    purchaseOrder: async (_, { id }, ctx) => new PurchaseOrderModel().getItem(id, ctx.userId),
    purchaseOrdersForCompany: async (_, { companyId }) => new PurchaseOrderModel().getForCompany(companyId)
},
Mutation: {
    // metadata are plain fields — base createItem/editItem handle them. jobId (create only)
    // is not a model field, so strip it and use the existing assignment path.
    createCustomerPurchaseOrder: async (_, { input }, ctx) => {
        const { jobId, ...data } = input;
        const model = new PurchaseOrderModel();
        const po = await model.createItem(data, ctx.userId);
        if (jobId) await model.assignToEntity(po.id, "Job", jobId);
        return po;
    },
    editCustomerPurchaseOrder: async (_, { id, input }, ctx) => {
        const { jobId, ...data } = input;   // jobId not editable here — assignment lives in the in-context flows
        return new PurchaseOrderModel().editItem(id, data, ctx.userId);
    },
    attachFileToPurchaseOrder: async (_, { purchaseOrderId, assetId }) =>
        new PurchaseOrderModel().attachFile(purchaseOrderId, assetId).then(() => true),
    detachFileFromPurchaseOrder: async (_, { purchaseOrderId, assetId }) =>
        new PurchaseOrderModel().detachFile(purchaseOrderId, assetId).then(() => true)
}
Why createItem/editItem directly. The metadata are declared modelFields, so the base methods validate (incl. wysiwyg length) and persist them with no custom wrapper. createItem must receive only model fields — strip the create-only jobId first and route it through the existing assignToEntity. No registration step: graphql/schema.ts already spreads PurchaseOrderResolvers.{Resolvers,Query,Mutation,typeDef} (lines 435, 632, 833, 1037). Confirm the context key for the current user id (ctx.userId vs ctx.user.id) against a neighbouring mutation.
