WO-15c Work Orders P1 - 1.33 Draft

Work Order Templates · Apply on WO Create + Planned Crew Advisory

The operational UI: a template picker at the top of the WO create form. Picking a template hydrates the form draft from previewWorkOrderTemplate — field defaults, forms, checklist, materials, and line items pre-populate; structured equipment plans surface specific-equipment selection prompts; structured labor and equipment advisories render read-only. Everything in the form remains editable; the user submits via the standard createJob path with a template-application payload. Also builds the Planned Crew advisory sidebar on the WO detail Schedule tab — the post-save companion to the create-form advisory (originally scoped under WO-16 but folded here since the advisory is template-driven). Desktop only in V1.

Estimate: 4-5 days Sequence: 1.33, after WO-15a + WO-15b + WO-16 Requires: WO-15a, WO-15b, WO-16 Enables: Real template usage in 1.33

1. Business Case

The previous two specs build the template system but expose it only to admins. WO-15c is the moment of value capture — a dispatcher creating a WO clicks a template and watches the form fill itself in. This is the demoable feature; everything before it was the foundation.

Per Corey's WOX-02 sketch the picker lives at the top of the create form (mirrors the "speed up creation" callout in his mockup). After apply, the form is a normal draft that the user can edit freely — the template is a starting point, not a contract. Snapshot semantics from WO-15a guarantee the WO is decoupled from the template after creation; subsequent template edits don't propagate.

2. Scope

Already Built

  • DONE WO-15a — previewWorkOrderTemplate resolver + createJob extension accepting workOrderTemplateApplication
  • DONE WO-15b — admin can build templates worth applying
  • DONE Existing WO create form (WO-3a/b/c) — every field this UI populates already exists and is editable
  • DONE WO-13 forms surface, WO-14 checklist surface (Create/Edit form integration) — the apply UI populates them via existing form-state hooks
  • DONE WO-16 (WO Detail Tabs — Schedule + Equipment Assignment) — provides the Schedule tab and EquipmentAssignment surface that this spec wires the advisory + template-applied assignments into. (The advisory itself ships in this spec — see In Scope below.)

In Scope (WO-15c)

  • IN Template picker banner at the top of the WO create form (desktop) with searchable list of active templates
  • IN On apply: fetch previewWorkOrderTemplate + hydrate form draft state across all the existing form sections
  • IN Visual indicator on each form field/row that was populated from the template (subtle "FROM TEMPLATE" badge or background tint)
  • IN Field default rendering — template-tier values supersede DAA defaultValue when a template is applied; existing form-render code path receives the template snapshot via context
  • IN Specific-equipment selection — each structured equipment plan renders as a prompt; clicking it opens the existing EquipmentAssignment form with category pre-filtered to the plan's equipmentCategoryId. The submitted assignment is captured in form draft state and committed alongside the WO at submit time. No new picker component — the existing EquipmentAssignment form does the picking.
  • IN Labor and equipment plan advisory rendering — read-only callout sections showing the planned crew / equipment categories. Includes pointer messaging that this advisory is informational only on create; actual scheduling happens on the WO detail page Schedule tab see WO-16 so users aren't confused when the callout disappears post-save.
  • IN Forms applied by the template render as a summary panel only ("3 forms will be attached when you save"); full management lives on the detail-page Form Submissions tab per WO-13
  • IN Free-form labor / equipment / materials from the template seed the regular line item sections; appear as standard editable line items with "FROM TEMPLATE" badges
  • IN Switch-template flow — if user picks a different template after one is already applied, a confirmation modal warns "Replace current template content with X?" then re-hydrates
  • IN Submit logic that builds the workOrderTemplateApplication payload from form draft state and submits it as part of createJob
  • IN Permission gate: any user with workOrder.create can use the picker; no separate permission
  • IN Planned Crew advisory sidebar on the WO detail Schedule tab — new WorkOrderPlannedCrewAdvisory.tsx component. Wraps the existing Schedule tab calendar in a 2-column layout (calendar left, advisory right) when the WO has an appliedWorkOrderTemplateId; calendar uses full width otherwise. Surfaces structured labor plans from the WO's applied template with a per-plan tally counting JobSchedule rows whose user holds the plan's tradeLevelId.
  • IN Free-form labor plans (no tradeLevelId) display in the advisory as descriptions only — no tally (nothing structured to count against).
  • IN Advisory sidebar gracefully hidden when the WO has no appliedWorkOrderTemplateId; calendar uses full width.
  • IN Advisory tally updates within the same user session as the dispatcher drags new users onto the calendar — no manual refresh.

Out of Scope

  • OUT Backend changes — the entire surface consumed lives in WO-15a
  • OUT Settings UI for template management — WO-15b
  • OUT Apply on WO edit — create only (mirrors WO-15a's create-only invariant)
  • OUT Mobile WO create template picker — desktop only in V1; revisit if dispatchers start creating WOs from mobile
  • OUT "Clear template" button that wipes template-derived content — once applied, content lives in form state and the user manually edits/removes anything they don't want
  • OUT Multi-template stacking on a single WO — one template per WO (matches WO-15a)
  • FUTURE AI-suggested templates based on customer / location / past WOs (matches WOX-22)

Pending Business Decisions

1. What if a structured equipment plan has no assignment created at submit time?

Lean: allow. The plan stays as advisory text on the WO; no EquipmentAssignment is created. The dispatcher can fill it in later from the EquipmentAssignment surface (WO-16). Alternative: block submit until all plans are resolved. Allowing matches the "templates are guidelines" framing. Confirm.

2. Switching template — confirm-and-replace, or merge?

Lean: confirm-and-replace. Merging two templates' content is messy (which template's checklist do you keep? both? deduped how?). Replace is unambiguous: the new template's content fully overwrites template-derived state, then the user re-edits if needed. Confirm.

4. Data Model

No schema changes. All template models, the audit FK on Job, and the snapshot/apply logic are defined in WO-15a.

5. API Surface

No new GraphQL types, queries, or mutations. The apply UI consumes:
  • workOrderTemplates — populates the picker dropdown (filtered to isActive: true)
  • previewWorkOrderTemplate(templateId) — fetches the snapshot package on apply / switch
  • createJob with the workOrderTemplateApplication input — submits the WO with the user's edits + equipment selections

5.1 Form-state → application payload

On submit, the apply UI builds the workOrderTemplateApplication input by serializing the current form state. Specifics:

workOrderTemplateApplication: {
  templateId,                                  // the originally-applied template
  checklistItems: form.checklistItems.map(i => ({  // includes user adds/edits/removes
    id: i.templateChecklistItemId ?? null,     // null = new, set = derived from template
    label: i.label,
    description: i.description,
    orderNo: i.orderNo,
  })),
  materialItems: form.materialItems.map(i => ({ ... })),
  formWrapperIds: form.forms.map(f => f.id),
  equipmentSelections: form.equipmentPlans
    .filter(p => p.selectedEquipmentIds.length > 0)
    .map(p => ({
      equipmentPlanId: p.templatePlanId,
      equipmentIds: p.selectedEquipmentIds,
    })),
  fieldDefaults: form.fieldDefaults.map(d => ({ ... })),
}

The form's draft state is the source of truth. Anything the user removed from the template's seed isn't in the payload; anything they added but not from the template is included with id: null. The resolver (in WO-15a) handles upserts correctly either way.

7. Acceptance Criteria

  1. The WO create form (desktop) shows a "Speed up creation" banner with a searchable picker listing only active templates.
  2. Picking a template and clicking Apply fetches previewWorkOrderTemplate exactly once and hydrates the form draft from the snapshot.
  3. Field defaults from the template populate the corresponding form fields with a "FROM TEMPLATE" badge; the user can edit any of them and the badge persists for traceability while the value is the template's default.
  4. Checklist and materials populate from the template inline on the create form (per WO-14 and WO-3 family); rows show a "FROM TEMPLATE" indicator; user can add, edit, or remove any row.
  5. Checklist items seeded from the template carry their photoRequired flag through to runtime; the WO-14 camera glyph appears next to those items so the user knows a photo will be required at tick time.
  6. Forms applied by the template render as a read-only summary panel ("3 forms will be attached when you save: ...") with a pointer to the detail-page Forms tab for post-save management; no inline form editing happens on the create form, matching WO-13's surface scope.
  7. Free-form labor and equipment template rows materialize as standard editable line items in the regular Labor / Equipment sections of the form, marked "FROM TEMPLATE".
  8. Structured labor plans render in a read-only "Planned crew (from template)" callout — they are not editable in the form and do not become line items. The callout includes pointer messaging directing users to the WO detail page Schedule tab see WO-16 for actual scheduling, so the disappearance of the callout post-save is not a surprise.
  9. Structured equipment plans render as inline prompts; clicking "Open assignment form" launches the existing EquipmentAssignment form with the plan's equipmentCategoryId pre-applied as a filter, in a deferred-commit mode that returns the user's selections to form draft state instead of writing immediately.
  10. Submitted EquipmentAssignment selections collapse the prompt to a resolved state showing chosen equipment + any operator / dates the user filled in; an Edit action re-opens the form to revise.
  11. Submitting the form calls createJob with a workOrderTemplateApplication payload that includes only what's in the current form state — user removals are honored, additions are included with null IDs.
  12. EquipmentAssignment rows are created in the same transaction as the Job for each resolved equipment selection; unresolved plans are not created and do not block submit.
  13. Picking a different template after one is applied opens the switch confirmation modal; confirming replaces all template-derived state with the new template's snapshot; cancelling leaves the current state untouched.
  14. If the user clears the picker (no template selected) without applying another, the form retains whatever state was last hydrated — there's no implicit "unapply" in V1.
  15. Cancelling the create form discards the hydrated state without affecting the template (no lastUsedAt bump occurs unless the WO is actually saved).
  16. The picker banner is hidden on mobile WO create flows in V1 (desktop-only).
  17. Users without workOrder.create permission cannot reach the WO create form, so the picker is unreachable.
  18. When a WO with an appliedWorkOrderTemplateId is opened, the Schedule tab renders the calendar in a 2-column layout with the Planned Crew advisory sidebar on the right; each WorkOrderTemplateLaborPlan appears with qty + planned hours.
  19. For each structured plan (with tradeLevelId), the advisory shows a tally "scheduled X of Y" counting JobSchedule rows on this Job whose user holds the plan's TradeLevel.
  20. For each free-form plan (no tradeLevelId), the advisory shows the description without a tally.
  21. Optional plan annotation text (the description on a structured plan) renders as a quoted note beneath the tally.
  22. The advisory sidebar is hidden entirely when the WO has no appliedWorkOrderTemplateId; the calendar uses full width in that case.
  23. Advisory tally updates within the same user session as the dispatcher drags new users onto the calendar — no manual refresh required.
